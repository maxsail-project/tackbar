# TackBar v0.6.5 — Simplified Pilot Onboarding & Web Consent Requirements

**Status:** Committed — implementation pending
**Scope:** simplify normal pilot entry with track-first onboarding and explicit web consent
**Baseline:** TackBar v0.6.4 — Sailor Activation Welcome Email
**Decision source:** `docs/v0.6.5-decisions.md`

---

## 1. Relationship to v0.6.4

v0.6.5 changes the route to explicit Sailor activation. It does not redefine
Sailor → Activity → Session semantics, normalized-email Sailor identity,
Session matching, ACTIVE-only shared visibility, Personal TackBar, Session
capability/expiration/renewal, Viewer behavior, OVH mailbox ingestion through
`share@tackbar.eu`, supported Vakaros CSV/CSV.GZ formats or the v0.6.4 welcome
email.

Consent continues to control shared visibility rather than technical ingestion
or Session matching. Existing manual Admin consent confirmation remains a
controlled operational fallback.

## 2. Release objective and target flow

### V6.5-OBJ-01 — Remove pre-registration from normal pilot entry

A Sailor MUST be able to begin the normal pilot flow by sharing a supported
track with `share@tackbar.eu`. Prior contact with
`maxsail.project@gmail.com` MUST NOT be required.

### V6.5-OBJ-02 — Keep consent explicit

Sending a track is a technical onboarding action and MUST NOT constitute
consent. Activation requires an explicit affirmative web action or the existing
controlled manual Admin fallback.

### V6.5-OBJ-03 — Preserve the established activation path

Web acceptance MUST reuse the existing consent activation semantics and then
continue through the existing v0.6.4 post-activation behavior.

The target flow is:

```text
supported first track
→ Sailor resolved or created
→ PENDING
→ Activity ingested and Session matching allowed
→ one automatic consent request for the current pending cycle
→ app.tackbar.eu/consent/<token>
→ explicit acceptance
→ ACTIVE
→ existing v0.6.4 activation behavior
→ Personal TackBar capability
→ welcome email
```

## 3. Track-first onboarding

### V6.5-ONB-01 — Normal entry point

The normal pilot entry point is `share@tackbar.eu`. Only successfully recognized
supported tracks enter this onboarding flow; arbitrary inbound email does not.

### V6.5-ONB-02 — PENDING technical processing

A supported track from a PENDING Sailor MAY be ingested, persisted and matched
to a Session. While the Sailor remains PENDING, their Activities MUST remain
excluded from shared Session responses and Personal TackBar MUST remain
ACTIVE-gated.

### V6.5-ONB-03 — ACTIVE ingestion remains unchanged

An ACTIVE Sailor continues through normal ingestion and MUST NOT receive a new
consent request merely because another track was processed.

## 4. Automatic consent-request email

### V6.5-REQ-01 — Trigger

After successful processing of a supported track, TackBar SHOULD attempt a
consent-request email only when the Sailor is PENDING and no request was
successfully sent for the current pending cycle.

Repeated mailbox review, duplicate processing, Admin refresh, Session creation
and additional tracks MUST NOT cause repeated automatic attempts in the same
pending cycle. At most one automatic attempt is made per pending cycle; after a
delivery failure, recovery is through explicit Admin resend/reissue rather than
an automatic retry.

### V6.5-REQ-02 — Required meaning

The request MUST explain that:

- TackBar received a sailing Activity from the recipient's email address;
- participation remains pending;
- the Activity is not exposed through shared TackBar Sessions while pending;
- explicit confirmation is required;
- the applicable participation conditions can be reviewed;
- acceptance activates participation; and
- ignoring the request does not activate participation.

### V6.5-REQ-03 — Content direction

The request is one plain-text bilingual email with English first and Spanish
second. Its approved subject is:

```text
Confirm your TackBar pilot participation / Confirma tu participación en TackBar
```

No language preference, localization infrastructure, HTML template system or
general content platform is introduced. Exact copy MAY remain in a focused,
tested implementation source file as it does for the v0.6.4 welcome email.

### V6.5-REQ-04 — Transport boundary

The request MUST reuse the established v0.6.4 outbound SMTP boundary. v0.6.5
does not introduce a queue, worker, scheduler, transactional-email SaaS or
automatic retry system.

## 5. Consent capability

### V6.5-TOK-01 — Purpose-specific capability

The public consent URL is conceptually:

```text
https://app.tackbar.eu/consent/<token>
```

The page belongs to the TackBar application at `app.tackbar.eu`, not to the
public-information `tackbar-web` site.

The token MUST be high entropy and non-guessable. It MUST be distinct from the
Sailor ID, email, Session capability and Personal TackBar capability. Possession
authorizes only this consent flow; it MUST NOT provide general authentication or
any other capability.

### V6.5-TOK-02 — Lifetime and expiry

A consent-request token is valid for exactly **28 days**. Expiry MUST NOT:

- activate the Sailor;
- delete Activity data;
- alter Session membership;
- alter Personal TackBar semantics; or
- invalidate the ability to issue an explicit new request when appropriate.

The lifetime is fixed for v0.6.5 and is not a new runtime configuration option.

### V6.5-TOK-03 — Agreement-version binding

Each request MUST be bound to the agreement version presented to the Sailor.
Acceptance MUST persist that version in consent-event history. A later agreement
version MUST NOT rewrite historical consent events.

The persistence shape remains an implementation detail provided these semantics
and existing repository conventions are preserved.

## 6. Consent page

### V6.5-WEB-01 — Decision content

The public TackBar application page SHOULD provide a concise participation
summary in English and Spanish as appropriate, a link to the complete canonical
pilot/privacy conditions and one clear affirmative action:

```text
Confirm participation / Confirmar participación
```

The complete conditions need not be duplicated in the UI.

### V6.5-WEB-02 — Explicit action only

Opening or viewing the page MUST NOT constitute consent. No GET request,
prefetch, link scanner or other passive behavior may activate a Sailor.

### V6.5-WEB-03 — Minimal private context

The page MUST expose only information needed for the participation decision. It
MUST NOT unnecessarily reveal the Sailor email, Activity details, Session
membership, Personal capability or other private context.

Malformed, unknown, expired or otherwise unusable tokens MUST fail safely and
MUST NOT reveal whether an email or Sailor exists, Activities, Sessions,
capability tokens or other private data.

## 7. Acceptance and activation

### V6.5-ACT-01 — Existing activation semantics

Valid explicit acceptance performs PENDING → ACTIVE through the existing
`SailorConsentService` activation path rather than a parallel implementation.
It MUST record a consent event whose source identifies web consent and whose
agreement version is the version bound to the request.

Successful acceptance MUST preserve the existing activation effects:

- established Session capability semantics are ensured;
- established Personal TackBar capability semantics are ensured; and
- the v0.6.4 welcome email is attempted.

Welcome-email delivery failure MUST NOT roll back ACTIVE consent.

### V6.5-ACT-02 — Idempotency

Repeated submission of an already accepted request MUST NOT add another granted
consent event, activate twice, regenerate a Personal TackBar or Session
capability, resend the welcome email or repeat any activation side effect. The
UI MAY truthfully report that participation is already confirmed.

Web acceptance MUST be retry-safe and avoid partial activation semantics.

## 8. REVOKED re-entry

The existing ingestion behavior is preserved:

```text
valid supported track from REVOKED Sailor
→ start new consent cycle
→ PENDING
```

This transition does not constitute renewed consent. The new PENDING cycle MAY
receive a new request and requires explicit acceptance before returning to
ACTIVE. This is existing behavior, not a new v0.6.5 domain concept.

## 9. Admin resend, reissue and fallback

### V6.5-ADM-01 — Explicit resend and reissue

- If the current request token remains valid, explicit Admin resend MUST reuse
  it.
- If the token has expired, explicit Admin reissue MUST create a new request and
  token.
- An accepted request MUST NOT be resent as a pending request.
- Sending, resending or reissuing MUST NOT change consent by itself.
- No automatic retry is introduced.

Manual Admin consent confirmation remains available as a controlled fallback.

### V6.5-ADM-02 — Delivery failure

Consent-request SMTP failure MUST NOT discard an Activity, change Session
matching, activate the Sailor, create false consent or mutate Personal or
Session capabilities. It MUST NOT invalidate an otherwise usable request token.

## 10. Focused tests and production validation

Focused regression coverage MUST include:

- unknown/new Sailor processing after a first valid supported track;
- PENDING ingestion and ACTIVE-only shared visibility;
- exactly one automatic request per pending cycle;
- no consent request for an ACTIVE Sailor;
- REVOKED + valid track → new PENDING cycle;
- the fixed 28-day token lifetime;
- valid, expired, malformed and unknown token handling;
- token entropy and separation from every other identifier/capability;
- agreement-version binding and preserved history;
- viewing/GET not granting consent;
- explicit PENDING → ACTIVE acceptance;
- repeated-acceptance idempotency;
- existing v0.6.4 activation and welcome effects executing once;
- consent-request SMTP failure and welcome SMTP failure boundaries;
- Admin valid-token resend and expired-token reissue; and
- manual Admin confirmation fallback.

The production validation target is:

```text
Vakaros track
→ share@tackbar.eu
→ OVH ingestion
→ PENDING
→ automatic consent-request email
→ app.tackbar.eu/consent/<token>
→ explicit confirmation
→ ACTIVE
→ welcome email
→ Personal TackBar usable
→ Activity visible according to existing ACTIVE sharing rules
```

## 11. Explicit non-goals

v0.6.5 does not introduce:

- account registration or Sailor username/password login;
- OAuth or social login;
- free-form consent-reply NLP;
- marketing campaigns or newsletters;
- an HTML-email or template-platform requirement;
- queues, workers, schedulers or background retries;
- transactional-email SaaS;
- automatic mailbox polling or a new mailbox provider;
- new file formats, including GPX, VKX or FIT;
- Garmin ingestion;
- Session matching changes;
- Personal or Session capability redesign;
- Viewer or analytics changes;
- general legal-document management; or
- consent handling in `tackbar-web`.
