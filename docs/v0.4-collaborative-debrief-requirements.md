# TackBar v0.4 — Collaborative Sailing Debrief Requirements

**Status:** Delivered and validated in v0.4.0

**Scope:** PoC / persisted Session to mobile-first collaborative debrief

**Baseline:** TackBar v0.3.1 Session Viewer

---

## 1. Relationship to the v0.3.x baseline

`docs/session-viewer-requirements.md` records the delivered v0.3.x Session
Viewer semantics and remains the baseline for:

- Activity selection and a maximum of two compared Activities;
- one shared absolute GPS/UTC Analysis Window;
- one shared `playbackTime`;
- replay speeds x1, x2, x5 and x10;
- map, summary and chart synchronization;
- presentation-only position interpolation;
- circular COG/HDG behavior.

Those semantics remain valid unless this document explicitly overrides them.
When a v0.4 requirement changes an architectural ownership decision from the
v0.3 document, the v0.4 requirement governs current work. Existing validated
Analysis Window, replay, comparison and circular-angle behavior must be
preserved.

---

## 2. Product objective

### V4-OBJ-01 — Persisted Session to collaborative debrief

TackBar v0.4.0 must allow sailors to open from the frontend a Session actually
persisted by TackBar, identify its sailing context, select one or two
Activities, retrieve their normalized tracks through the backend API, and use
the Session Viewer from a mobile/tablet device to perform a visual
collaborative debrief using the map, Analysis Window, replay, basic metrics and
charts.

The frontend must no longer depend on committed Session or track fixtures for
normal operation and must not access persistence directly.

The main transition is:

```text
v0.3.x

backend persistence        frontend fixtures
       │                         │
       └──────── X ──────────────┘


v0.4

ingestion
   ↓
Sailor / optional Boat context
   ↓
Activity
   ↓
Session
   ↓
backend persistence
   ↓
read-only FastAPI
   ↓
frontend
   ↓
Session Viewer
   ↓
Analysis Window
   ↓
Map + Metrics + Charts + Replay
   ↓
collaborative debrief around phone/tablet
```

The backend/frontend runtime connection is a technical prerequisite, but the
product goal is the real debrief workflow rather than HTTP endpoints alone.
v0.4 is not primarily an analytics release.

---

## 3. Collaborative debrief meaning

### V4-OBJ-02 — Collaboration happens around the device

Collaborative Sailing Debrief means several sailors use the visual evidence in
one Session Viewer to discuss what happened together:

```text
several sailors
      ↓
one phone/tablet
      ↓
open real Session
      ↓
select boats/Activities
      ↓
adjust time
      ↓
inspect map + metrics + charts + replay
      ↓
talk about what happened
```

It does not mean building chat, comments, discussion threads, messaging,
notifications, collaborative text editing or real-time multi-user
synchronization into TackBar.

## 4. Delivered domain: Sailor and Boat

Before v0.4, the implementation concept was transitional:

```text
Participant
- id
- name
- boat_name
- sailing_class
- sail_number
```

That representation mixed person identity and default boat metadata. v0.4
replaced it with `Sailor` as the person-level concept and `Boat` as a separate
sailing context:

```text
Sailor ↔ 0..N Boats

Activity
   ↓
sailing context
   ↳ Sailor
   ↳ Boat when known

Activities
   ↓
Session
```

This diagram expresses domain relationships. The delivered JSON model uses
stable internal UUIDs, `Activity.sailor_id`, optional `Activity.boat_id`, and
optional `Sailor.default_boat_id`; it does not imply database foreign keys.

### V4-DM-00 — Approved v0.4 domain direction

v0.4 replaced the transitional Participant runtime model with internally
identified Sailor and separate Boat entities. Activity references a required
Sailor and optional Boat. Email remains an external ingestion identity. A
Sailor may have an optional default Boat for automatic ingestion. Sailor↔Boat
usage is otherwise derived through Activities. Activity identity/deduplication
is based on stable Sailor identity plus attachment SHA-256. Session, normalized
track and Activity-based storage identities remain unchanged.

Existing Participant boat metadata may be applied to legacy Activities as an
explicit compatibility migration of the previous TackBar model; this must not
be presented as independently verified historical sailing context.

### V4-DM-01 — Sailor

A Sailor represents the person. A Sailor:

- has a stable internal TackBar UUID;
- has a human-readable name when known;
- may be associated with multiple Boats over time;
- may generate multiple Activities;
- may participate in multiple Sessions.

Normalized email is the external identity used by current email ingestion; it
is not the Sailor's internal identity. A Sailor may reference an optional
`default_boat_id` used when creating a new Activity through automatic
ingestion.

### V4-DM-02 — Boat

A Boat represents the boat/context used for sailing. Its relevant concepts are:

- stable technical identity;
- boat name when available;
- sailing class when available;
- sail number when available.

A Sailor may sail different Boats over time. Therefore:

```text
Sailor != Boat
email != Boat
```

### V4-DM-03 — Activity

An Activity remains one track received by TackBar. It requires `sailor_id` and
may contain an optional `boat_id` identifying the Boat used when known.

Activity must not be redefined as a race, day, training block or Session. v0.4
must not automatically merge or split Activities.

### V4-DM-04 — Legacy Participant compatibility

`Participant` is no longer an active runtime entity. It remains only as legacy
migration and historical terminology. The explicit one-time migration converts
legacy Participant data to Sailor/Boat persistence while preserving Activity,
Session, track, original and ingestion-history identities.

Applying legacy Participant Boat metadata to historical Activities is an
explicit compatibility policy, not independently verified historical Boat
usage. No `SessionParticipant` entity was introduced.

```text
→ frontend integration
```

Concrete REST paths and payload schemas were then delivered by focused API

## 6. v0.4 responsibility boundary

### V4-AR-01 — Backend ownership

The backend owns:

- persistence access;
- Session loading;
- Activity loading;
- Sailor/Boat/domain context resolution;
- normalized track loading;
- the read API contract;
- the storage abstraction;
- authorization later, when the pilot-access chapter is implemented.

### V4-AR-02 — Frontend ownership

For the current PoC, the frontend owns:

- selected primary Activity;
- optional comparison Activity;
- ephemeral Analysis Window;
- Analysis Window reconciliation;
- window sample filtering;
- selected metric;
- shared replay `playbackTime` and replay speeds;
- presentation interpolation;
- map and chart presentation;
- currently implemented summary calculations derived from normalized samples.

The existing tested frontend interaction and presentation logic must not be
moved to the backend merely to introduce the API. The same Analysis Window,
metric or replay calculation must not be duplicated in both layers.

This PoC ownership may evolve only when demonstrated product or performance
needs justify a new decision.

### V4-AR-03 — Independent sailing analytics direction

TackBar may reuse validated sailing-domain knowledge, algorithms and metric
definitions from MaxSail experimentation. Reusable TackBar sailing-analysis
logic should evolve as an independent Python analytics/domain layer or library
when a demonstrated need justifies it.

TackBar must not inherit MaxSail's Streamlit application architecture,
persistence structure or UI architecture. This direction does not claim that
a mature standalone analytics library is already delivered and does not expand
v0.4 into an advanced analytics release.

## 7. Delivered read-only API

### V4-API-01 — Viewer data

The narrow read-only backend API allows the frontend to obtain:

- recent Sessions;
- Session detail;
- Activities belonging to a Session;
- current Sailor/Boat context;
- canonical normalized track samples for selected Activities.

Delivered endpoints:

```text
GET /api/sessions
GET /api/sessions/{session_id}
GET /api/activities/{activity_id}/track
```

Session Activity details expose Sailor context and optional Boat context. The
canonical Activity track response exposes complete normalized samples with:

```text
utc
lat
lon
cog
sog
dist
hdg
heel
trim
```

### V4-API-02 — Storage isolation

The frontend must not:

- read `sailors.json`, `boats.json`, `activities.json` or `sessions.json`;
- read CSV.GZ track files directly;
- know `TACKBAR_DATA_DIR`;
- depend on filesystem paths.

`TACKBAR_DATA_DIR` remains entirely behind the backend boundary. Switching
between public TEST data and private runtime data must require backend
configuration only; frontend application logic remains identical.

## 8. Persistence policy

### V4-PS-01 — Continue JSON metadata and filesystem tracks

v0.4 continues using:

```text
JSON metadata + filesystem track/original files
```

SQLite is not a v0.4 prerequisite. Track-file volume alone does not justify a
metadata database migration.

> Migrate because TackBar requires database behavior, not because an arbitrary
> number of Activities has been reached.

### V4-PS-02 — Review indicators

The following should trigger measurement and review, not automatic migration:

- an individual metadata JSON collection approaching approximately 10–20 MB;
- persistence operations becoming visibly measurable in interactive/API
  latency;
- metadata scans or full-file rewrites consistently becoming a meaningful
  part of request latency;
- auxiliary indexes becoming increasingly complex solely to compensate for
  JSON lookup cost;
- approximately 100–200 ms of measured latency attributable mainly to metadata
  persistence/query work.

### V4-PS-03 — Strong database triggers

A database migration becomes a concrete architectural task when demonstrated
requirements include one or more of:

- multiple concurrent writers;
- multiple application workers modifying the same state;
- lost updates or locking problems;
- atomic multi-entity transactions;
- stronger referential integrity;
- repeated corruption or interrupted-write problems;
- materially complex relational querying;
- unacceptable measured persistence latency;
- operational complexity caused by maintaining JSON consistency.

Do not introduce a cloud database, Redis, queue or distributed infrastructure
for v0.4.

## 9. Relevant sailing intervals

### V4-SEG-01 — Manual isolation is sufficient

Meaningful sailing intervals may include a start, upwind leg, downwind leg,
complete race, training exercise, maneuver or another manually relevant
period.

For v0.4, the ephemeral Analysis Window is sufficient for sailors to isolate
the period under discussion. Activity data is not cut or modified.

The future direction remains:

```text
Analysis Window
      ↓
Saved/identified segment
```

Persisted segments and automatic detection of starts, legs, races or maneuvers
are strategically relevant but are not v0.4 completion requirements.

## 10. Viewer completion

### V4-VIEW-01 — Basic charts

The delivered v0.4 Viewer enables SOG, COG, HEEL and TRIM time series for one
or two selected Activities. Both Activities use the same selected metric,
Analysis Window and vertical `playbackTime` reference.

- SOG is an ordinary scalar time series in knots.
- COG uses a circular-aware 0°–360° presentation that avoids false lines
  through the north wrap.
- HEEL is a signed degree series; missing values remain gaps and a horizontal
  0° reference is shown.
- TRIM is a signed degree series with the same gap and 0°-reference behavior.

Missing values remain unavailable and are not invented. No Port/Starboard or
bow-up/bow-down interpretation is assigned to sensor sign.

HDG time series are out of scope unless explicitly decided later.

TWA, VMG, maneuver analytics, COG roses, histograms, rankings, start analytics,
advanced tactical analytics and automated gained/lost analysis remain outside
v0.4.

### V4-UX-01 — Focused post-integration review

The focused post-integration UX review was completed without redesigning the
Viewer. The delivered outcome preserves a mobile-first layout with responsive
phone/tablet behavior and includes:

- persisted recent Session navigation and Sailor/Boat/Activity labels;
- primary/comparison selection and explicit loading/error/no-overlap states;
- Analysis Window grouped directly with the map context;
- compact temporal-only Replay and playback-speed selector;
- current replay time associated with the scrubber;
- fixed map GPS/SOG/COG/HEEL telemetry;
- the refined Summary and SOG/COG/HEEL/TRIM metric selection.

The implementation remains intentionally small and does not introduce a design
system or UI framework.

### V4-VIEW-02 — Visual sampling must not affect analytical results

TackBar Activities may contain a high number of normalized samples. A typical
Activity may contain approximately two samples per second over several hours,
and the Session Viewer may compare two such Activities.

The Viewer MAY reduce, simplify or downsample samples when necessary for
efficient visual rendering.

Any such sampling is strictly a presentation optimization.

The complete set of valid normalized samples inside the current Analysis Window
remains the analytical dataset.

Therefore:

```text
canonical Activity track
        ↓
Analysis Window filtering
        ↓
complete window sample set
        ├── metrics / calculations
        ├── replay / temporal lookup
        └── visual sampling when useful
                    ↓
              map / chart rendering
```

### V4-VIEW-03 — Delivered Summary

The delivered Summary uses the complete valid normalized sample population
inside the shared Analysis Window and contains:

- Distance;
- Avg SOG;
- Max SOG;
- Dominant COG;
- Avg HEEL +;
- Avg HEEL −;
- Avg TRIM +;
- Avg TRIM −.

Avg SOG is distance travelled divided by elapsed sample time, not the
arithmetic mean of SOG samples. Max SOG is the maximum finite canonical SOG
sample. Positive HEEL/TRIM averages include only values greater than zero;
negative averages include only values less than zero. Exact zero is excluded
from both signed groups, missing/non-finite values are ignored, and negative
averages preserve their sign. No Max HEEL or Max TRIM metric or semantic sign
interpretation is introduced.

## 11. Pilot access is deferred to v0.5

### V4-PA-01 — No pilot-access implementation in v0.4

Invitation, `invited`/`active`/`revoked` states, privacy acceptance and unknown
sender rejection belong to the v0.5 Real Sailing Pilot chapter. The preserved
PA-01 through PA-07 requirements in the v0.3 baseline govern that future
chapter and are not v0.4 exit criteria.

v0.4 does not require:

- public self-registration;
- authentication or an authorization platform;
- an invite-management UI;
- privacy-acceptance workflow implementation.

Real private test data must remain outside Git and use `TACKBAR_DATA_DIR`.

## 12. Delivered implementation sequence

v0.4 was completed through focused, reviewable chapters:

1. **Requirements alignment:** v0.4 scope and responsibility boundaries.
2. **Sailor/Boat decision:** domain impact analysis and approved direction.
3. **Domain migration:** Sailor/Boat persistence and explicit legacy
   compatibility migration.
4. **Read Session API:** recent Sessions and Session detail.
5. **Read Activity track API:** complete canonical normalized samples.
6. **Frontend API integration:** persisted Sessions/tracks and removal of
   runtime frontend fixtures.
7. **End-to-end validation:** public TEST/private-root boundary and complete
   persisted Session flow.
8. **Viewer metrics completion:** refined Summary plus SOG/COG/HEEL/TRIM
   charts.
9. **Focused UX review:** mobile/tablet interaction refinements.
10. **Release stabilization:** complete backend/frontend regression checks and
    documentation alignment.

## 13. Definition of Done — achieved

TackBar v0.4.0 allows the frontend to open a Session persisted by TackBar,
identify the relevant Sailor, Boat and Activities, select one or two
Activities, retrieve canonical normalized tracks through the backend read API,
and perform a visual collaborative debrief from a phone/tablet using the
existing shared Analysis Window, map, replay, summary metrics and basic charts,
without frontend track fixtures or direct storage access.

Delivered and validated end-to-end flow:

```text
real/public TEST track
      ↓
ingestion
      ↓
Sailor / Boat context
      ↓
Activity
      ↓
automatic Session matching
      ↓
JSON/files persistence
      ↓
FastAPI read API
      ↓
Recent Sessions
      ↓
open Session
      ↓
Primary + optional Comparison
      ↓
Analysis Window
      ↓
Replay
      ↓
Map + Replay + Summary + SOG / COG / HEEL / TRIM
      ↓
sailors discuss together around the device
```

Private runtime data may be used for manual validation but must remain outside
Git.

## 14. Explicit non-goals

v0.4 does not include:

- authentication platform or public registration;
- pilot invitation or privacy-acceptance workflow;
- in-application chat/comments;
- multiple simultaneous frontend users;
- automatic race, leg or maneuver detection;
- persisted Saved Segments as an exit criterion;
- GPX, Garmin or Vakaros VKX ingestion;
- SQLite migration;
- cloud or distributed infrastructure;
- advanced analytics;
- automatic Activity merge/split;
- more than two simultaneously compared Activities.

## 15. Resolved and deferred decisions

### Resolved in v0.4

- Participant-to-Sailor migration and legacy compatibility policy;
- internal Sailor UUID and normalized external email identity;
- separate Boat persistence, optional Sailor default Boat and optional
  Activity Boat relationship;
- required Activity Sailor relationship;
- read-only Viewer endpoints and response contracts;
- frontend Session and Activity track API types.

### Still deferred

- v0.5 invitation, activation, privacy acceptance and access enforcement;
- persisted Saved Segments and automatic sailing-interval detection;
- database migration unless demonstrated operational needs justify it;
- GPX, Garmin and Vakaros VKX ingestion;
- advanced sailing analytics and HDG time-series presentation.
