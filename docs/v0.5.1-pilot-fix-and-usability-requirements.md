# TackBar v0.5.1 — Pilot Fix & Usability Requirements

**Status:** Current requirements
**Scope:** Minor operational/usability release
**Baseline:** TackBar v0.5.0 — Real Sailing Pilot
**Primary focus:** Admin usability improvements discovered during real pilot operation

---

## 1. Relationship to v0.5.0

v0.5.1 is a minor release built on the delivered and validated v0.5.0
Real Sailing Pilot.

It does not redefine the v0.5.0 product model or operational workflow.

The following remain unchanged unless explicitly stated in this document:

- Sailor → Activity → Session domain model;
- Activity identity and deduplication;
- Session matching;
- consent states and transitions;
- ACTIVE-only shared visibility;
- capability URL semantics;
- Session expiration and renewal;
- Gmail ingestion and reprocessing;
- persistence model;
- Session Viewer behavior;
- Analysis Window, replay and metrics.

v0.5.1 focuses exclusively on small operational and usability improvements
identified while running the real pilot.

---

## 2. Release objective

### V051-OBJ-01 — Pilot usability

TackBar v0.5.1 MUST improve the administrator's ability to understand and
operate real pilot data without introducing new product-domain behavior.

The primary objective is to make existing Sailors, Activities and Sessions
easier to identify and inspect operationally.

Derived Admin information MAY be added where it can be calculated from the
existing persisted domain model.

Such derived information MUST NOT introduce new persisted domain semantics.

---

## 3. Scope principles

v0.5.1 MAY:

- enrich Admin API responses;
- derive operational summaries from existing Activities, Sailors and Sessions;
- improve Admin presentation;
- improve readability of dates, sailing intervals and relationships;
- add focused regression tests for those improvements.

v0.5.1 MUST NOT, unless explicitly added to this requirements document:

- redesign Session matching;
- change consent behavior;
- change capability authorization;
- change Session membership;
- change Activity identity;
- change ingestion semantics;
- modify Viewer behavior;
- add new persistence concepts;
- introduce new infrastructure;
- introduce advanced sailing analytics.

---

## 4. U-01 — Admin Session operational context

Admin → Sessions MUST expose enough context to identify a Session as a real
sailing outing.

For each Session, Admin MUST expose:

- `created_at`;
- real sailing interval derived from associated Activities;
- unique ACTIVE Sailors represented in the Session;
- consent coverage across unique Sailors;
- existing internal Activity count;
- existing shareable Activity count;
- capability state;
- expiration.

Sailing interval semantics:

`sailing_start = min(Activity.start_time)`

`sailing_end = max(Activity.end_time)`

Sailor consent coverage MUST count unique Sailors, not Activities.

These values are derived Admin information and MUST NOT be persisted as new
Session domain fields.

---

## 5. U-02 — Admin Sailor operational context

Admin → Sailors MUST expose enough context to understand the Sailor's
participation history.

For each Sailor, Admin SHOULD expose summary information including:

- Activity count;
- unique Session count;
- most recent sailing interval.

Sailor detail MUST expose the Sessions in which that Sailor participates.

Each Session summary SHOULD contain:

- Session ID;
- sailing interval;
- number of Activities belonging to that Sailor in the Session;
- capability state;
- expiration;
- usable capability path when allowed by existing semantics.

Historical Session membership MUST remain visible to Admin for ACTIVE,
PENDING and REVOKED Sailors.

The shared-visibility rule remains unchanged:

`Activity shared ⇔ Sailor.consent_status == ACTIVE`

All Sailor/Session relationship information introduced by v0.5.1 is derived
from existing domain data and MUST NOT create new persisted reverse
relationships.

---

## 6. Acceptance criteria

v0.5.1 is ready when:

1. Admin Sessions clearly distinguish Session creation time from real sailing
   time.
2. Admin Sessions expose unique ACTIVE Sailors and consent coverage.
3. Existing internal/shareable Activity-count semantics remain unchanged.
4. Admin Sailors expose Activity and Session participation summaries.
5. Admin Sailor detail exposes relevant Session history.
6. PENDING and REVOKED Sailors retain internal participation visibility in
   Admin.
7. No new derived Admin information is persisted as domain state.
8. Existing Session matching, consent, capability, ingestion and Viewer
   behavior remain unchanged.
9. Backend and frontend regression suites remain green.
