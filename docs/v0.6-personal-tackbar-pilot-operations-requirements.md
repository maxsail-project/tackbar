# TackBar v0.6.x — Personal TackBar & Pilot Operations Requirements

**Status:** Current v0.6 release-family requirements  
**Current release:** `v0.6.1 Mahon — Pilot Operations`  
**Baseline:** TackBar v0.5.1 Pilot Fix & Usability  
**Decision source:** `v0.6-decisions.md`

---

## 1. Release-family structure

The v0.6 family preserves the validated v0.5.x pilot semantics unless explicitly changed here.

### v0.6.0 baseline

v0.6.0 delivered the Personal TackBar/productization baseline, including:

- Personal TackBar / My Sessions;
- stable personal capability access for ACTIVE Sailors;
- Admin personal-capability management;
- TackBar visual-brand consolidation;
- MPL-2.0 transition for TackBar-owned source code.

### v0.6.1 Mahon — Pilot Operations

v0.6.1 is the Mahon operational release. Its committed scope is intentionally small:

- Admin ingestion disposition, Discard/Restore and filtering;
- focused operational fixes needed for reliable pilot use;
- small Viewer presentation refinements already validated for Mahon;
- release validation/hardening.

Multi-provider email ingestion and broader Session-maintenance usability are not part of v0.6.1.

After v0.6.1 is published, patch numbers such as v0.6.2 and v0.6.3 remain available for hot-fixes. Uncommitted functional follow-up in this release family is labelled **Future 0.6.x** until explicitly assigned.

## 2. Preserved baseline

The following remain unchanged unless explicitly overridden below:

- Sailor → Activity → Session domain model;
- Activity as one received track;
- stable internal Sailor identity;
- normalized email as the current external ingestion identity;
- current Activity and Session persistence;
- current Session matching;
- PENDING / ACTIVE / REVOKED consent states;
- backend-enforced ACTIVE-only shared Session visibility;
- Session capability URLs;
- Session expiration and renewal;
- existing Session Viewer semantics;
- JSON metadata + filesystem track/original persistence;
- email as the track-sharing channel;
- Gmail as the current mailbox provider;
- Admin as the operational control surface;
- current mobile/tablet-first frontend direction.

## 3. Personal TackBar baseline

### V6-PER-01 — Personal capability

An ACTIVE Sailor MUST be able to have one current personal capability token used to access Personal TackBar.

The public token MUST:

- be distinct from the internal Sailor ID;
- be distinct from Session capability tokens;
- be generated using an adequately unpredictable random mechanism;
- not expose normalized email or another guessable identifier as the credential.

Conceptual route:

```text
/me/<personal-access-token>
```

### V6-PER-02 — No Sailor login

Personal TackBar MUST NOT require username/password login, an external identity provider or a general authentication platform in v0.6.x.

### V6-PER-03 — ACTIVE gate

Personal Session history MUST be exposed only while the Sailor is ACTIVE at request time and the personal capability is valid.

PENDING/REVOKED Sailors MUST NOT receive that history.

Consent changes MUST NOT automatically destroy the personal token and MUST NOT delete persisted Activities or tracks.

### V6-PER-04 — Read-only My Sessions

My TackBar MUST expose read-only Session participation history derived through:

```text
Sailor → Activity → Session
```

A Session MUST appear once even when the Sailor has multiple Activities in it.

A new persisted `sailor.session_ids` relation MUST NOT be introduced for this purpose.

Presentation SHOULD normally be most recent sailing first.

### V6-PER-05 — Reuse collaborative Viewer

Opening an available Session MUST reuse the existing collaborative Session Viewer and existing shared capability/lifetime/ACTIVE-only visibility rules.

The personal capability MUST NOT bypass shared Session authorization.

A standalone Activity Viewer, personal Session Viewer variant or duplicated Viewer implementation is not required.

### V6-PER-06 — Unavailable Sessions remain history

Expired, revoked or otherwise unavailable Sessions MUST remain visible as participation history but MUST NOT expose a fabricated usable shared capability.

### V6-PER-07 — Preserve Session lifetime and renewal

Personal access MUST NOT renew Sessions or override shared capability state.

Existing Admin renewal remains the mechanism for Session lifetime management.

Renewal MUST NOT create, regenerate or un-revoke a capability implicitly.

### V6-PER-08 — Personal capability administration

Admin MUST be able to:

- inspect personal capability state;
- copy the current personal capability URL when usable;
- regenerate the personal capability;
- revoke the personal capability.

Regeneration MUST invalidate the previous token.

Personal-capability revocation MUST NOT change Sailor consent.

## 4. Ingestion administrative maintenance — v0.6.1

### V6-ADM-01 — Technical status remains unchanged

Technical ingestion status remains conceptually separate from administrative disposition.

At minimum:

```text
processed
failed
```

### V6-ADM-02 — Administrative disposition

Each ingestion record MUST support:

```text
active
discarded
```

Existing/legacy records without the field MUST be treated/migrated compatibly to `active`.

Disposition MUST NOT replace technical processing status.

### V6-ADM-03 — Discard

Admin MUST provide semantic `Discard`.

Discarding an ingestion MUST:

- retain the ingestion record;
- preserve technical processing status;
- preserve deduplication knowledge;
- preserve provider/message identity;
- preserve any persisted original attachment;
- preserve any Activity already created;
- preserve Session membership;
- preserve consent state;
- preserve Session and personal capabilities;
- avoid mutating remote mailbox state merely because the record was discarded administratively.

Discard MUST NOT trigger automatic reprocessing.

### V6-ADM-04 — Restore

Admin MUST provide semantic `Restore` from `discarded` to `active`.

Restore MUST NOT automatically reprocess the ingestion.

Restore MUST NOT recreate or alter Activity/Session membership, technical status, consent or capabilities.

### V6-ADM-05 — Filtering

Admin MUST allow ingestion records to be filtered independently by:

```text
Status:
All / Processed / Failed

Disposition:
All / Active / Discarded
```

No filters MUST preserve the existing all-record view and existing ordering.

### V6-ADM-06 — Physical deletion is separate

v0.6.1 MUST NOT implement partial physical Activity/track/original deletion as an incidental ingestion-maintenance action.

Physical deletion/anonymization requires a separate policy covering Activity, Session references, Personal TackBar history, originals, normalized tracks, ingestion history, deduplication state, retention and backups.

## 5. Email ingestion baseline

### V6-ING-01 — Email remains the sharing channel

Email MUST remain the supported track-sharing channel for v0.6.1.

### V6-ING-02 — Gmail remains the provider baseline

The existing Gmail provider adapter MUST remain supported for v0.6.1 Mahon.

OVHcloud/second-provider support and generalized multi-provider mailbox ingestion are explicitly outside v0.6.1.

They remain **Future 0.6.x** until explicitly promoted into a concrete release.

They MUST NOT be automatically assigned to v0.6.2 or v0.7.0.

### V6-ING-03 — Preserve provider-independent downstream semantics

Deferring a second provider MUST NOT introduce new Gmail-specific Activity, Session, normalization, deduplication or Viewer semantics.

### V6-ING-04 — Provider state is not TackBar state

Remote provider flags such as `unread` MUST NOT become TackBar's processing source of truth.

TackBar MUST continue to maintain its own ingestion records.

## 6. Session operations — v0.6.1

### V6-SES-01 — Preserve Session semantics

v0.6.1 MUST NOT redefine:

- Session matching;
- technical Activity membership;
- ACTIVE-only shared visibility;
- Session expiration;
- Session renewal semantics;
- Session capability authorization.

### V6-SES-02 — Existing maintenance actions remain available

Admin MUST preserve:

- Renew Session lifetime;
- Copy usable capability URL;
- Regenerate capability;
- Revoke capability.

### V6-SES-03 — Deterministic Admin ordering

The Admin Session list MUST present Sessions deterministically by real derived `sailing_start` descending, so the most recent sailing appears first.

Sessions without a usable `sailing_start` SHOULD appear after Sessions with real sailing timestamps, with a deterministic stable tie-breaker.

This ordering MUST NOT change Session persistence, matching or shared Viewer behavior.

Broader Session-maintenance usability remains **Future 0.6.x**.

## 7. Session Viewer map presentation — v0.6.1

### V6-MAP-01 — Quiet basemap

The Session Viewer MUST use the configured OpenFreeMap Positron basemap for the Mahon release.

The intent is to keep geographic context visually secondary to sailing tracks.

Changing the basemap MUST NOT alter track geometry, replay, metrics or domain semantics.

### V6-MAP-02 — Preserve functional track colors

Existing functional primary/comparison track colors MUST remain independent from decorative TackBar brand colors.

The Mahon release MUST NOT change track colors merely to match the brand palette.

### V6-MAP-03 — Standard manual map navigation

The Session Viewer MUST expose the standard MapLibre navigation/compass control used by the current implementation.

Manual rotation/reset MUST affect map camera presentation only.

It MUST NOT modify GPS coordinates, track geometry, Activity data, Session data, Analysis Window or replay state.

Automatic wind-up orientation, TWD input and custom wind controls are not required in v0.6.1.

## 8. Visual brand baseline

### V6-BRD-01 — Official name and tagline

Primary product name:

```text
TackBar
```

Preferred short tagline:

```text
Sail. Debrief. Learn.
```

### V6-BRD-02 — Canonical visual source

`tackbar-web` remains the canonical reference for the shared name, official SVG logo family, core palette and preferred tagline.

### V6-BRD-03 — Core palette

| Color | Value |
| --- | --- |
| Navy | `#013663` |
| Blue | `#0383CC` |
| Pale | `#E3EAF0` |
| Background | `#F7F9FB` |
| White | `#FFFFFF` |

Functional sailing, comparison, telemetry and status colors MUST remain distinguishable from decorative brand colors.

### V6-BRD-04 — Incremental consistency

Brand consolidation MUST remain incremental and MUST NOT trigger a complete frontend redesign or design-system rewrite.

Readable contrast, visible focus states, touch-target sizing and mobile/tablet outdoor usability MUST be preserved.

## 9. Licensing baseline

### V6-LIC-01 — MPL-2.0

TackBar-owned application and public website source code use MPL-2.0 prospectively.

### V6-LIC-02 — Historical MIT versions

Existing tags/releases distributed under MIT MUST NOT be rewritten or described as if their historical MIT grants were revoked.

v0.6.1 MUST NOT be expanded to include:

- OVHcloud ingestion or another second mailbox provider;
- generalized multi-provider email ingestion;
- broad Session-maintenance redesign;
- Sailor username/password login;
- external identity-provider login;
- web track upload;
- My Activities / standalone personal Activity access;
- physical Activity/track/original deletion;
- automatic scheduled mailbox polling;
- canonical logical track fingerprinting;
- GPX ingestion;
- VKX ingestion;
- FIT ingestion;
- Garmin Connect;
- direct Vakaros cloud integration;
- Saved Analysis Segments;
- automatic wind-oriented map mode;
- advanced maneuver detection;
- new advanced sailing analytics;
- Session matching redesign;
- database migration;
- complete frontend redesign.

The following are valid future v0.6-family candidates but are not assigned to a specific patch:

## 12. Relationship to v0.7.0

v0.7.0 remains focused on file-format independence:

```text
GPX → VKX → FIT
```

All formats MUST converge on the same canonical TackBar normalized track and existing Activity → Session → Viewer flow.

The v0.7 scope also owns the canonical logical duplicate fingerprint contract.

Deferred v0.6 operational work MUST NOT be automatically moved into v0.7.

---

## 13. Mahon release acceptance

Before publishing v0.6.1 Mahon, validation MUST confirm the complete real pilot flow remains operable:

```text
Gmail
→ ingestion
→ Sailor
→ Activity
→ Session
→ consent
→ Personal TackBar
→ Session Viewer
→ collaborative debrief
```

Validation SHOULD combine focused automated regression with real manual operational checks on representative sailing data and a tablet/mobile Viewer.
