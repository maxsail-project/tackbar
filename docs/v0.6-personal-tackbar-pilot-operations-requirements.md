# TackBar v0.6.0 — Personal TackBar & Pilot Operations Requirements

**Status:** Proposed requirements based on closed product decisions  
**Scope:** Mahón-ready pilot / simple Sailor access, ingestion maintenance and visual-brand consolidation  
**Baseline:** TackBar v0.5.1 Pilot Fix & Usability  
**Decision source:** `v0.6-decisions.md`

---

## 1. Relationship to v0.5.x

v0.6.0 extends the delivered Real Sailing Pilot without redefining validated
Session Viewer, Session-matching, consent or shared-capability semantics.

The following remain baseline unless explicitly overridden here:

- Sailor → Activity → Session domain model;
- stable internal Sailor identity with normalized email as the current external
  ingestion identity;
- Activity as one received track;
- current Activity and Session persistence;
- current Session matching;
- PENDING / ACTIVE / REVOKED consent states;
- backend-enforced ACTIVE-only shared Session visibility;
- Session capability URLs;
- Session expiration and renewal;
- existing Session Viewer semantics;
- JSON metadata + filesystem track/original persistence;
- email as the track-sharing channel;
- Gmail as the current mailbox provider;
- Admin as the operational control surface;
- current mobile-first frontend direction.

v0.6.0 focuses on **simple personal Sailor access, practical ingestion
maintenance and coherent TackBar brand presentation**, with the smallest scope
needed for an operational pilot release.

---

## 2. Product objective

### V6-OBJ-01 — Personal TackBar

TackBar v0.6.0 MUST provide an ACTIVE Sailor with a stable, non-guessable,
read-only personal access path to Sessions in which that Sailor participated.

The intended flow is:

```text
ACTIVE Sailor
     ↓
personal capability URL
     ↓
My TackBar / My Sessions
     ↓
Sessions I participated in
     ↓
available Session → existing Session Viewer
expired/unavailable Session → truthful state
```

### V6-OBJ-02 — Operational pilot evolution

v0.6.0 MUST improve pilot operation without introducing a full account system
or a new domain model.

It MUST support ingestion administrative maintenance through:

- a disposition separate from technical processing status;
- semantic `Discard` / `Restore` operations;
- filtering by technical status and administrative disposition.

Existing Gmail ingestion and existing Session maintenance operations remain the
pilot baseline. Multi-provider mailbox ingestion and broader Session-maintenance
usability improvements are not required for v0.6.0.

### V6-OBJ-03 — Visual brand consolidation

v0.6.0 MUST progressively adopt the existing `tackbar-web` visual identity as
the canonical visual reference for the application.

The release MUST adopt:

- the existing official SVG logo system from `tackbar-web/assets/logo/`;
- the canonical core color palette from `tackbar-web/assets/styles.css`;
- reusable frontend visual tokens for the core brand colors;
- consistent brand usage in Personal TackBar and existing public-facing UI.

This requirement MUST NOT be used as justification for a complete frontend
redesign.

### V6-OBJ-04 — Licensing transition

The TackBar application and TackBar public website code MUST transition to
Mozilla Public License 2.0 as part of the v0.6.0 project boundary, subject to a
relicensing/provenance review before the license files are changed.

Historical versions already released under MIT MUST NOT be retroactively
rewritten.

## 3. Personal TackBar access

### V6-PER-01 — Personal capability

An ACTIVE Sailor MUST be able to have one current personal capability token
used to access Personal TackBar.

The public token MUST:

- be distinct from the internal Sailor ID;
- be distinct from Session capability tokens;
- be generated using an adequately unpredictable random mechanism;
- not expose normalized email or another guessable identifier as the credential.

The exact public route is an API/UI contract detail. A conceptual route is:

```text
/me/<personal-access-token>
```

### V6-PER-02 — No Sailor login

Personal TackBar MUST NOT require a username/password, external identity
provider or general authentication platform in v0.6.0.

Possession of the current valid personal capability is the personal-access
mechanism for this release.

### V6-PER-03 — ACTIVE gate

A valid personal capability MUST expose personal Session history only while the
Sailor is ACTIVE at request time. PENDING/REVOKED Sailors MUST NOT receive this
history. Consent changes MUST NOT automatically destroy the personal token.
This access rule MUST NOT delete persisted Activities or tracks.

### V6-PER-04 — Read-only My Sessions

My TackBar MUST expose a read-only My Sessions history. A Session belongs in
that history when at least one Activity owned by the Sailor is associated with
it. Each Session MUST appear once even with multiple own Activities.

Membership MUST be derived through `Sailor → Activity → Session`, without a
new persisted relation such as `sailor.session_ids`. Activities remain internal
domain entities, not the primary personal surface.

Use existing/derived context sufficient to recognize Sessions, such as sailing
date/time or interval and current shared-access availability. Presentation
SHOULD normally be most recent first.

### V6-PER-05 — Reuse the existing collaborative Viewer

Opening a Session MUST reuse the existing Session Viewer under existing shared
capability, lifetime and ACTIVE-only visibility rules. The personal capability
grants access to the personal space, not arbitrary Activities or Sessions.
It MUST NOT bypass shared authorization.

v0.6 MUST NOT introduce a standalone Activity Viewer, personal Session Viewer
variant or duplicated Viewer implementation. My Activities and standalone personal
Activity access are future considerations, not committed v0.6 core scope.

### V6-PER-06 — Unavailable Sessions remain history

Expired, revoked or otherwise unavailable Sessions MUST remain visible as
participation history, truthfully marked unavailable to open. No usable shared
capability may be fabricated. This does not grant individual Activity viewing.

### V6-PER-07 — Preserve Session lifetime and renewal

Personal access MUST NOT renew Sessions or override shared capability state.
Existing Admin renewal remains the mechanism to extend or restore lifetime
where current rules allow. If an otherwise valid existing capability becomes
usable again, the Sailor may open that Session from My TackBar again.
Renewal does not create, regenerate or un-revoke a capability. Session
membership and Activity/track retention semantics remain unchanged.

### V6-PER-08 — Personal capability administration

Admin MUST be able to:

- inspect whether a Sailor has personal access configured;
- copy the current personal capability URL when usable;
- regenerate the personal capability;
- revoke the personal capability.

Regeneration MUST invalidate the previous token.

Revocation MUST prevent the revoked token from granting personal access and
MUST NOT change Sailor consent.

These operations MUST use backend services/repositories rather than direct
frontend JSON editing.

## 4. Ingestion administrative maintenance

### V6-ADM-01 — Technical status remains unchanged

Existing technical ingestion status remains conceptually separate from
administrative maintenance.

The technical status MUST continue to represent processing outcome, including
at least:

```text
processed
failed
```

### V6-ADM-02 — Administrative disposition

Each ingestion record MUST support an administrative disposition equivalent to:

```text
active
discarded
```

The default disposition for existing/normal ingestion records SHOULD be
`active`.

Disposition MUST NOT replace technical processing status.

### V6-ADM-03 — Discard

Admin MUST provide a semantic `Discard` operation.

Discarding an ingestion MUST:

- retain the ingestion record;
- preserve its technical processing status;
- preserve deduplication knowledge;
- preserve provider/message identity;
- preserve the original attachment when already persisted;
- preserve any Activity already created;
- preserve Session membership;
- preserve consent state;
- preserve Session and personal capabilities;
- avoid mutating remote mailbox state merely because TackBar discarded the
  record administratively.

### V6-ADM-04 — Restore

Admin MUST provide a semantic `Restore` operation that changes a discarded
ingestion back to the normal active administrative disposition.

Restore MUST NOT reprocess the ingestion automatically unless the administrator
explicitly invokes the existing reprocess operation.

### V6-ADM-05 — Ingestion filtering

Admin MUST allow ingestion records to be filtered by both technical status and
administrative disposition.

At minimum the UI/API MUST support the conceptual combinations:

```text
Status:
All / Processed / Failed

Disposition:
All / Active / Discarded
```

### V6-ADM-06 — Physical deletion is separate

v0.6.0 MUST NOT implement a partial physical `Delete Activity/Track` operation
as an incidental ingestion-maintenance action.

Physical deletion/anonimization requires a separate policy covering Activity,
Session references, Personal TackBar history, originals, normalized tracks,
ingestion history, deduplication state, retention and backups.

## 5. Email ingestion baseline and deferred multi-provider work

### V6-ING-01 — Email remains the sharing channel

Email MUST remain the supported track-sharing channel in v0.6.0.

### V6-ING-02 — Gmail remains the v0.6.0 provider baseline

The existing Gmail provider adapter MUST remain supported for v0.6.0.

Adding the TackBar mailbox hosted at OVHcloud and completing a generalized
multi-provider acquisition boundary are explicitly deferred from v0.6.0.
They remain valid future work but are not committed to v0.7.0 or another
specific release by this requirement.

### V6-ING-03 — Preserve provider-independent downstream semantics

Deferring a second mailbox provider MUST NOT introduce new Gmail-specific
Activity, Session, normalization, deduplication or Viewer semantics.

The existing downstream domain boundaries remain unchanged so a future provider
adapter can be introduced without redefining TackBar domain behavior.

### V6-ING-04 — Provider processing state is not TackBar state

Remote provider flags such as `unread` MUST NOT become TackBar's source of truth
for processing state.

TackBar MUST continue to maintain its own ingestion records.

## 6. Session maintenance baseline

### V6-SES-01 — Preserve Session semantics

v0.6.0 MUST NOT redefine:

- Session matching;
- technical Activity membership;
- ACTIVE-only shared visibility;
- Session expiration;
- Session renewal semantics;
- Session capability authorization.

### V6-SES-02 — Existing maintenance actions remain available

Admin MUST preserve the existing Session operations:

- renew Session lifetime;
- copy usable capability URL;
- regenerate capability;
- revoke capability.

Broader Session-maintenance presentation/filtering work is explicitly deferred
from v0.6.0. Small focused pilot fixes MAY be made when they correct existing
behavior without changing established Session semantics or API contracts.

## 7. Visual brand requirements

### V6-BRD-01 — Official TackBar brand name

The primary product name MUST remain:

```text
TackBar
```

The preferred short tagline for public-facing brand use is:

```text
Sail. Debrief. Learn.
```

### V6-BRD-02 — Core visual direction

The v0.6.0 visual direction MUST remain:

- nautical;
- clean;
- contemporary;
- slightly informal rather than corporate;
- readable on mobile/tablet;
- suitable for outdoor sailing use;
- consistent across app and public website.

The brand MUST NOT depend on beer/alcohol imagery.

### V6-BRD-03 — Core color palette

v0.6.0 MUST use `tackbar-web/assets/styles.css` as the canonical visual reference
and adopt its existing core palette:

| Color | Value | `tackbar-web` CSS token |
| --- | --- | --- |
| Navy | `#013663` | `--color-navy` |
| Blue | `#0383CC` | `--color-blue` |
| Pale | `#E3EAF0` | `--color-pale` |
| Background | `#F7F9FB` | `--color-background` |
| White | `#FFFFFF` | `--color-white` |

This palette replaces the obsolete teal/coral brand palette.
The application MUST centralize these values in explicit reusable frontend
tokens/variables. The website token names above identify the source values;
application token names remain implementation details.

### V6-BRD-04 — Palette roles

The visual token system MUST distinguish the existing website palette roles:

- `Navy`: primary brand identity, text and primary action surfaces;
- `Blue`: brand accent;
- `Pale`: pale surfaces and dividers;
- `Background`: page background;
- `White`: light surfaces and reversed content.

Color combinations MUST preserve readable contrast. Functional sailing,
comparison, telemetry and status colors MUST remain independent from, and
visually distinguishable from, decorative brand colors. Existing functional
colors MAY remain outside the core brand palette.

### V6-BRD-05 — Official logo system

v0.6.0 MUST reuse the existing official SVG logo system under
`maxsail-project/tackbar-web/assets/logo/`, including:

- logo/lockup: `tackbar-logo.svg` and `tackbar-logo-inverted.svg`;
- wordmark: `tackbar-wordmark.svg` and `tackbar-wordmark-inverted.svg`;
- compact mark: `tackbar-mark.svg` and `tackbar-mark-inverted.svg`;
- claim/tagline: `tackbar-claim.svg`, `tackbar-claim-inverted.svg`,
  `tackbar-logo-claim.svg` and `tackbar-logo-claim-inverted.svg`.

The application MUST select suitable existing variants for light/dark surfaces
and constrained spaces. It MUST NOT redraw or invent new logo artwork as part
of consolidation. Any favicon/app-icon-compatible derivative SHOULD reuse the
existing compact SVG mark and preserve its artwork.

### V6-BRD-06 — Logo quality constraints

The official logo MUST be:

- legible at small sizes;
- simple;
- recognizably nautical without relying on generic clip-art;
- compatible with the TackBar name and visual direction;
- usable in app header, website, README/presentation material and screenshots.

The logo design MUST NOT encode product behavior or domain semantics that are
not otherwise part of TackBar.

### V6-BRD-07 — Application consistency

The application MUST progressively adopt the canonical `tackbar-web` identity
through small, focused changes to:

- Personal TackBar;
- shared public-facing headers/navigation;
- primary buttons/links;
- relevant cards/surfaces;
- Session Viewer framing where appropriate.

v0.6.0 MUST preserve validated Viewer usability. Brand consolidation MUST NOT
trigger a full frontend redesign or require a full component-library or
design-system rewrite.

### V6-BRD-08 — Public website consistency

`tackbar-web` MUST remain the canonical visual reference for the shared TackBar
name, official SVG logo family, core color palette and preferred tagline.
The application adopts this existing identity rather than defining a new one.

The application MAY copy the required SVG assets into its own frontend asset
tree. Visual consistency MUST NOT require coupling application and website
architectures or source trees, or runtime dependency on `tackbar-web` to serve
application branding assets.

### V6-BRD-09 — Regression/accessibility baseline

Brand consolidation MUST preserve:

- readable text/background contrast;
- visible focus states;
- touch-target sizing already expected by the mobile-first UI;
- functional distinction of primary/secondary actions.

No visual-brand change may knowingly make the existing Session Viewer harder to
use outdoors or on a phone/tablet.

## 8. Licensing requirements

### V6-LIC-01 — Main application license

The TackBar application repository MUST transition from MIT to the unmodified
Mozilla Public License Version 2.0 text, using SPDX identifier:

```text
MPL-2.0
```

before the v0.6.0 release is published.

### V6-LIC-02 — TackBar Web license

The `maxsail-project/tackbar-web` repository MUST transition from MIT to
MPL-2.0 as part of the same project licensing decision.

### V6-LIC-03 — Provenance review

Before relicensing, the project MUST review current source provenance and
existing copyright/license notices sufficiently to identify third-party code
that cannot simply be relicensed by TackBar.

Valid third-party notices MUST be preserved.

### V6-LIC-04 — Historical MIT versions

Existing tags/releases distributed under MIT MUST NOT be rewritten or described
as if their previous MIT grants were revoked.

The MPL transition applies prospectively from the new project version/state.

### V6-LIC-05 — Contributions remain open

Project documentation SHOULD make clear that normal forks and pull requests
remain welcome under MPL-2.0 and that contributors must have the right to submit
their contribution.

A CLA is not required by v0.6.0.

### V6-LIC-06 — Code license is not a data license

Relicensing TackBar source code MUST NOT publish or relicense private pilot data,
participant emails, GPS tracks, originals or runtime data as open data.

## 9. Explicit non-goals for v0.6.0

v0.6.0 does NOT require:

- Sailor username/password login;
- third-party authentication;
- editable Sailor profile;
- web track upload;
- My Activities / standalone personal Activity access;
- standalone Activity Viewer or duplicated personal Session Viewer;
- web consent flow;
- automatic consent-reply interpretation;
- automatic outbound email;
- a second mailbox provider or OVHcloud ingestion;
- generalized multi-provider mailbox ingestion;
- scheduled mailbox polling;
- broader Session-maintenance filtering/presentation beyond focused pilot fixes;
- canonical post-normalization track fingerprinting or logical track deduplication
  beyond the existing raw attachment SHA-256 behavior (planned for v0.7.0);
- physical Activity/track deletion;
- GPX support;
- VKX support;
- FIT support;
- Garmin Connect;
- direct Vakaros cloud integration;
- QR Session sharing;
- Saved Analysis Segments;
- new advanced sailing analytics;
- Session matching redesign;
- database migration;
- full frontend redesign;
- a large design-system dependency.

## 10. Acceptance criteria

v0.6.0 is ready when:

1. An ACTIVE Sailor can open a non-guessable personal capability URL.
2. My Sessions returns only Sessions derived through the Sailor's Activities,
   without a persisted Sailor-to-Session relation.
3. PENDING/REVOKED Sailors do not receive personal Session history through personal
   capability access.
4. Personal TackBar remains read-only.
5. Unavailable Sessions remain history but cannot be opened; available Sessions
   reuse the existing shared Viewer and authorization.
6. Admin can inspect/copy/regenerate/revoke personal access. Regeneration
   invalidates the old token; revocation does not change consent and consent
   changes do not automatically destroy the personal token.
7. Admin ingestion distinguishes technical status from active/discarded
   administrative disposition.
8. Discard/Restore does not delete or roll back existing Activity/Session data.
9. Admin can filter ingestion history by technical status and administrative
   disposition.
10. Existing Gmail ingestion remains supported and existing downstream domain
    semantics remain unchanged.
11. Admin retains the existing Session lifetime/capability maintenance actions.
12. Existing v0.5.x consent, Session matching and Session Viewer behavior
    remains intact.
13. TackBar adopts the canonical `tackbar-web` core palette through reusable tokens.
14. The application reuses the official `tackbar-web/assets/logo/` SVG family,
    selecting the appropriate primary, compact, light and inverted variants.
15. Personal TackBar progressively adopts the existing `tackbar-web` identity
    without architectural or runtime coupling between repositories.
16. Brand work does not introduce a full frontend redesign or reduce mobile
    usability/accessibility.
17. The main TackBar repository is MPL-2.0 after provenance review.
18. `tackbar-web` is MPL-2.0 after provenance review.
19. Historical MIT releases/tags remain untouched.
