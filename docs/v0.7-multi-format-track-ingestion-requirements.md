# TackBar v0.7.0 — Multi-Format Track Ingestion Requirements

**Status:** Proposed requirements based on the current v0.7.0 product direction  
**Scope:** GPX, VKX and FIT ingestion / canonical normalization / post-normalization logical deduplication  
**Baseline:** TackBar v0.6.x Personal TackBar & Pilot Operations  
**Decision source:** `v0.7-decisions.md`

---

## 1. Relationship to v0.6.x

v0.7.0 extends the TackBar ingestion boundary from provider independence to
source-format independence.

Unless explicitly overridden here, v0.7.0 MUST preserve:

- Sailor → Activity → Session;
- Activity as one received/resolved track;
- Sailor identity and consent semantics;
- Personal TackBar authorization semantics;
- existing Session matching;
- Session capability, expiration and renewal semantics;
- existing Session Viewer behavior;
- Gmail + OVHcloud acquisition-provider boundary;
- existing ingestion history and original preservation;
- existing raw attachment SHA-256 exact-file duplicate behavior;
- JSON metadata + filesystem persistence;
- current Admin operational model.

v0.7.0 MUST NOT create format-specific downstream domain models.

---

## 2. Product objective

### V7-OBJ-01 — Multi-format ingestion

TackBar v0.7.0 MUST accept the existing supported Vakaros CSV/CSV.GZ baseline
and add:

1. GPX;
2. VKX;
3. FIT;

in that implementation and validation order.

### V7-OBJ-02 — One canonical track flow

All supported formats MUST converge on one TackBar canonical normalized track
representation before downstream Activity/Session processing.

Conceptually:

```text
CSV/CSV.GZ ─┐
GPX ────────┤
VKX ────────┼→ parse/extract → normalize → canonical track
FIT ────────┘                         ↓
                               Activity → Session → Viewer
```

### V7-OBJ-03 — Logical duplicate resolution

v0.7.0 MUST define and validate a deterministic post-normalization fingerprint
contract suitable for Sailor-scoped logical duplicate resolution across the
supported canonical normalization paths.

The contract MUST be closed before canonical fingerprints become durable
persisted identity data.

---

## 3. Format-adapter boundary

### V7-FMT-01 — Format and provider are separate

Email acquisition provider and attachment file format MUST remain independent
concerns.

A GPX/VKX/FIT parser MUST NOT depend on whether the file came through Gmail or
OVHcloud.

### V7-FMT-02 — Format adapters

Each supported file format MAY have a dedicated parser/extractor adapter.

The adapter MAY own:

- format detection/validation;
- source sample extraction;
- source-specific unit conversion;
- source metadata extraction;
- deterministic parsing errors.

The adapter MUST NOT redefine:

- Sailor identity;
- consent;
- Activity;
- Session;
- Session matching;
- capability authorization;
- Viewer semantics.

### V7-FMT-03 — Preserve existing formats

Existing Vakaros CSV/CSV.GZ ingestion MUST continue to work.

Adding GPX/VKX/FIT MUST NOT remove or silently alter the established supported
CSV path.

### V7-FMT-04 — Sequential validation

GPX MUST be integrated and validated before VKX is promoted.

VKX MUST be integrated and validated before FIT is promoted.

This requirement favors small validated increments over implementing all formats
at once.

---

## 4. Canonical normalized track

### V7-NOR-01 — Required minimum fields

A successfully normalized sailing track MUST provide the minimum navigation
baseline:

- UTC/GPS sample timestamp;
- latitude;
- longitude;
- SOG;
- COG.

These fields form the minimum data needed by the current TackBar navigation and
Viewer baseline.

### V7-NOR-02 — SOG derivation

When the source format does not provide usable SOG directly, TackBar MUST be
able to derive SOG from GPS positions and timestamps using a deterministic,
documented and regression-tested normalization algorithm.

### V7-NOR-03 — COG derivation

When the source format does not provide usable COG directly, TackBar MUST be
able to derive COG from GPS positions and timestamps using a deterministic,
documented and regression-tested normalization algorithm.

COG MUST retain circular-angle semantics.

### V7-NOR-04 — Reuse validated calculation knowledge

The v0.7.0 implementation MAY reuse validated SOG/COG calculation knowledge
from maxSail analytics.

Such reuse MUST be extracted or adapted behind TackBar's normalization boundary
and MUST NOT reintroduce the previous Streamlit application architecture.

### V7-NOR-05 — Optional HEEL and TRIM

HEEL and TRIM MUST remain optional.

When the source does not provide a valid value, TackBar MUST preserve the value
as unavailable rather than inventing or synthesizing it.

### V7-NOR-06 — HDG remains distinct

HDG/heading MUST remain distinct from COG.

TackBar MUST NOT derive HDG from COG.

If true heading is unavailable from the source/normalization input, it MUST
remain unavailable.

### V7-NOR-07 — Deterministic normalized output

For equivalent input data and the same normalization-contract version, TackBar
MUST produce deterministic canonical normalized output suitable for regression
testing and later fingerprinting.

### V7-NOR-08 — No per-format Viewer semantics

Missing optional telemetry in GPX/VKX/FIT MUST NOT create a separate Viewer
product.

Existing Viewer behavior MUST handle only the metrics actually available under
the established missing-data rules.

---

## 5. GPX requirements

### V7-GPX-01 — GPX support

TackBar MUST support representative sailing GPX files as the first v0.7.0
format increment.

### V7-GPX-02 — Required source viability

A GPX file MUST contain enough valid time/position information to construct the
minimum canonical navigation baseline.

A GPX file that cannot produce a valid timestamped GPS track MUST fail
diagnostically and MUST NOT create a partial Activity.

### V7-GPX-03 — Derived navigation

GPX normalization MUST derive SOG and COG when they are absent from the source
and enough timestamped GPS samples exist.

### V7-GPX-04 — Optional extensions

GPX extensions MAY be inspected when useful, but v0.7.0 MUST NOT make
vendor-specific GPX extensions a requirement for the minimum GPX path.

---

## 6. VKX requirements

### V7-VKX-01 — VKX support

TackBar MUST add VKX after GPX has been integrated and validated.

### V7-VKX-02 — Canonical convergence

VKX-specific telemetry MUST be mapped into the same canonical TackBar model.

The presence of richer VKX sensor data MUST NOT redefine Activity, Session or
Viewer semantics.

### V7-VKX-03 — Optional telemetry preservation

Where VKX provides valid HEEL, TRIM, HDG or other already-supported canonical
telemetry, the adapter SHOULD preserve it according to the canonical
normalization contract.

Unsupported additional telemetry MAY remain outside v0.7.0 scope.

---

## 7. FIT requirements

### V7-FIT-01 — FIT support

TackBar MUST add FIT after VKX has been integrated and validated.

### V7-FIT-02 — File support is not Garmin Connect

FIT ingestion MUST remain a file-format capability.

It MUST NOT introduce Garmin Connect / Activity API integration.

### V7-FIT-03 — Canonical convergence

FIT data MUST normalize to the same canonical TackBar track model and existing
Activity → Session → Viewer flow.

---

## 8. Canonical fingerprint and deduplication

### V7-DED-01 — Preserve raw attachment hash

TackBar MUST retain raw attachment SHA-256 as the fast exact-byte duplicate
check.

Raw hash and canonical fingerprint MUST remain separate concepts.

### V7-DED-02 — Fingerprint after normalization

A canonical track fingerprint MUST be computed only after the supported input
has been parsed and normalized into the v0.7 canonical track representation.

It MUST NOT depend on:

- email provider;
- provider message identity;
- filename;
- received/processing timestamps;
- runtime filesystem paths;
- arbitrary container metadata;
- Activity ID.

### V7-DED-03 — Fingerprint input contract

Before fingerprint persistence is enabled, v0.7.0 MUST explicitly decide and
regression-test whether the identity input is:

- the complete normalized canonical sample representation; or
- a documented stable subset of canonical fields.

The choice MUST be validated using representative existing CSV plus GPX, VKX
and FIT fixtures.

### V7-DED-04 — Deterministic serialization

The fingerprint contract MUST define:

- fingerprint version;
- included fields;
- row ordering;
- timestamp format;
- numeric serialization/precision;
- missing-value representation;
- encoding;
- record separators/framing;
- hash algorithm.

### V7-DED-05 — Sailor-scoped identity

Canonical duplicate resolution MUST be scoped by stable Sailor identity.

Two different Sailors MUST NOT be collapsed because their canonical
fingerprints match.

### V7-DED-06 — Duplicate outcome

When an ingestion resolves to an existing Activity for the same Sailor under the
canonical fingerprint contract:

- a second Activity MUST NOT be intentionally created;
- a duplicate Session MUST NOT be created;
- existing Session membership MUST NOT be mutated unnecessarily;
- the ingestion record SHOULD remain diagnostically useful.

### V7-DED-07 — Cross-format validation

The test suite MUST include representative cases where equivalent track content
is expressed through more than one supported normalization path.

Exact equivalence expectations MUST follow the fingerprint contract established
under `V7-DED-03`; v0.7.0 MUST NOT use fuzzy/tolerance-based duplicate matching
as a substitute for deterministic canonical identity.

### V7-DED-08 — No fuzzy deduplication

v0.7.0 MUST NOT collapse tracks merely because they have similar:

- time intervals;
- sample counts;
- routes;
- start/end positions;
- derived SOG/COG profiles.

Approximate track equivalence requires a separate future product decision.

---

## 9. Ingestion and persistence behavior

### V7-ING-01 — Original preservation

The original received attachment MUST continue to be preserved according to the
existing ingestion persistence semantics.

### V7-ING-02 — Diagnostic failure

Malformed, unsupported or non-normalizable files MUST produce a diagnostic
ingestion failure and MUST NOT create a partial Activity.

### V7-ING-03 — Reprocess

Existing reprocess-from-original behavior MUST continue to work for the new
supported formats.

### V7-ING-04 — No mailbox-state coupling

Format parsing or failure MUST NOT use remote provider flags such as unread/read
as TackBar processing state.

### V7-ING-05 — Persistence baseline

v0.7.0 MUST NOT require a database migration.

Canonical normalized tracks and any new fingerprint metadata MUST fit the
existing persistence approach unless implementation evidence demonstrates a
specific unmet requirement.

---

## 10. Viewer and analytics compatibility

### V7-VIEW-01 — Preserve Viewer semantics

v0.7.0 MUST preserve:

- one/two-Activity comparison;
- shared GPS/UTC Analysis Window;
- single playback time;
- existing map/replay semantics;
- circular-angle handling for COG/HDG;
- current missing-data behavior.

### V7-VIEW-02 — No new advanced analytics

SOG/COG derivation needed to normalize GPX or another format is ingestion/
normalization work.

It MUST NOT be used as justification for maneuver detection, tactical analysis,
gained/lost calculations or other advanced analytics in v0.7.0.

---

## 11. Explicit non-goals for v0.7.0

v0.7.0 does NOT require:

- Garmin Connect;
- direct Vakaros cloud integration;
- web track upload;
- additional email providers;
- automatic mailbox polling;
- ZIP ingestion;
- arbitrary additional archive/container formats;
- fuzzy duplicate matching;
- HEEL/TRIM synthesis;
- HDG derivation from COG;
- new advanced sailing analytics;
- maneuver detection;
- Session matching redesign;
- Viewer redesign;
- database migration.

---

## 12. Acceptance criteria

v0.7.0 is ready when:

1. Existing Vakaros CSV/CSV.GZ ingestion still works.
2. Representative GPX sailing files normalize successfully into the canonical
   TackBar track representation.
3. GPX without source SOG/COG can obtain deterministic SOG/COG from timestamped
   GPS samples.
4. GPX validation occurs before VKX promotion.
5. Representative VKX files normalize through the same downstream model.
6. VKX validation occurs before FIT promotion.
7. Representative FIT files normalize through the same downstream model.
8. Gmail/OVH acquisition behavior is independent from attachment format.
9. A successful normalized track contains UTC time, latitude, longitude, SOG
   and COG.
10. Missing HEEL/TRIM values remain unavailable rather than synthesized.
11. HDG is not derived from COG.
12. Format-specific parsing does not create format-specific Activity, Session
    or Viewer models.
13. Malformed/non-normalizable files fail without partial Activity creation.
14. Originals remain preserved and reprocessable.
15. The raw attachment SHA-256 exact-file check remains available.
16. The canonical fingerprint identity field set has been explicitly closed
    using representative multi-format fixtures before fingerprint persistence.
17. The canonical fingerprint serialization/version contract is deterministic
    and regression-tested.
18. Canonical duplicate resolution remains Sailor-scoped.
19. A canonical duplicate does not intentionally create a second Activity or
    unnecessary duplicate Session.
20. No fuzzy duplicate matching is introduced.
21. Existing Session matching and Session Viewer semantics remain intact.
22. No database migration or unrelated infrastructure expansion is required.
