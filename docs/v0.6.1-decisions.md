# TackBar v0.6.1 — OVH Mailbox Ingestion Decisions

**Status:** Closed decisions  
**Date:** 12 September 2026  
**Objective:** replace Gmail as the operational production mailbox with the TackBar OVHcloud mailbox while preserving the existing provider-independent TackBar pipeline.

---

## 1. Release assignment

The previously deferred OVHcloud mailbox work is promoted from **Future 0.6.x** to **v0.6.1**.

This is a focused operational release. It does not reopen unrelated v0.6.0 decisions.

---

## 2. Production mailbox

The operational track-sharing address for v0.6.1 is:

```text
share@tackbar.eu
```

The mailbox is hosted on OVHcloud Zimbra Starter.

The validated access mechanism is:

```text
IMAP over TLS
imap.mail.ovh.net:993
```

Authentication uses the mailbox username/password supplied at runtime.

The mailbox password is an operational secret and MUST NOT be committed to the repository.

---

## 3. Gmail relationship

v0.6.1 replaces Gmail as the production ingestion mailbox.

The Gmail adapter may remain available in the codebase for rollback, comparison or future use, but production mailbox review is expected to use OVHcloud.

v0.6.1 does not require both providers to run simultaneously.

Once production is configured for OVHcloud, Gmail OAuth refresh-token renewal is no longer part of the production ingestion operating path.

---

## 4. Provider boundary

OVHcloud is an acquisition adapter only.

It must convert mailbox messages into the existing `InboundEmail` model and then hand them to the common ingestion flow.

The following remain provider-independent and unchanged:

- Sailor identity semantics;
- supported Vakaros CSV/CSV.GZ parsing;
- normalization;
- raw attachment SHA-256 exact-file deduplication;
- Activity creation;
- Session matching;
- consent;
- Personal TackBar;
- capability/lifetime behavior;
- Admin ingestion semantics;
- Session Viewer.

No OVH-specific domain model is introduced.

---

## 5. Provider message identity

TackBar continues to own processing state in ingestion history.

Remote `Seen`/`Unread` flags are not TackBar state.

For OVH IMAP messages, provider-message identity is based on:

```text
UIDVALIDITY + UID
```

under the distinct OVH provider key.

The RFC `Message-ID` header is useful diagnostic metadata but is not the primary provider identity contract.

---

## 6. Sender identity

Existing sender-email identity semantics remain unchanged.

The outer sender of the received message is the Sailor identity used by ingestion.

v0.6.1 does not inspect forwarded-message bodies or nested headers to recover an original sender.

Operationally, tracks intended for a given Sailor should be sent to `share@tackbar.eu` from that Sailor's email address under the current identity rules.

---

## 7. Consent and product email identity

The existing human-operated consent flow under the MaxSail Project remains unchanged for this stage.

`share@tackbar.eu` is specifically the track-sharing ingestion mailbox.

Creating `info@tackbar.eu`, introducing automatic outbound email or moving consent communication to TackBar mailboxes are not part of v0.6.1.

---

## 8. Production pilot data

The current production pilot contains only a small controlled set of test/pilot data.

A one-time clean restart of TackBar runtime pilot data is approved for the v0.6.1 production cutover if useful.

No migration feature is required for the existing production dataset.

This decision does not define a general deletion/anonymization product workflow.

Code, server configuration and secrets are outside the reset boundary.

---

## 9. Mailbox operation

Admin-triggered manual mailbox review remains the v0.6.1 operational model.

Automatic scheduled polling remains future work.

The implementation should make provider selection explicit enough to remove hard-coded Gmail assumptions from mailbox review without introducing speculative generalized infrastructure.

---

## 10. Validated feasibility evidence

Before assigning this release, the following was manually validated against the real OVHcloud mailbox:

- `share@tackbar.eu` created and active;
- webmail authentication successful;
- IMAPS authentication successful from a development PC;
- IMAPS authentication successful from the TackBar production VPS;
- real external email received by the mailbox;
- real Vakaros `.csv.gz` attachment fetched successfully through IMAP;
- IMAP UID, RFC `Message-ID`, sender, receive date, subject, filename and attachment bytes were available;
- attachment SHA-256 could be calculated from fetched bytes.

Therefore the technical feasibility spike is considered **PASS**.

---

## 11. Explicit non-goals

v0.6.1 does not include:

- Gmail + OVH simultaneous production acquisition;
- automatic mailbox polling;
- outbound email;
- `info@tackbar.eu`;
- consent redesign;
- forwarded sender reconstruction;
- new track formats;
- logical/canonical post-normalization fingerprints;
- domain-model changes;
- Session matching changes;
- Admin redesign;
- Viewer changes;
- database migration;
- advanced analytics.

---

## 12. Release validation

Implementation validation should use focused backend tests during development and a separate broader release-validation gate afterward.

A real production-like end-to-end validation must prove:

```text
real email → share@tackbar.eu → OVH IMAP adapter → InboundEmail
→ existing ingestion → Activity → Session → existing Viewer
```

Repeated mailbox review must remain idempotent for the same OVH message.
