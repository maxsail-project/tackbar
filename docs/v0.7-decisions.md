# TackBar v0.7.0 — Consolidated Decisions

**Status:** Draft — release direction closed; fingerprint identity details intentionally remain to be closed after representative multi-format normalization is validated  
**Date:** 8 September 2026  
**Objective:** make TackBar independent from the incoming track file format while preserving one canonical Activity → Session → Viewer flow.

---

## 1. Governance rule

TackBar v0.7.0 starts from the validated v0.6.x baseline.

Existing product and domain semantics are not reconsidered unless a v0.7.0
decision explicitly changes them.

The following remain baseline:

- Sailor → Activity → Session;
- Activity as one received track resolved by TackBar;
- stable internal Sailor identity;
- existing consent and Personal TackBar access semantics;
- existing Session matching;
- existing Session capabilities, expiration and renewal;
- existing Session Viewer semantics;
- JSON metadata + filesystem persistence while adequate;
- provider-independent downstream ingestion;
- Gmail + OVHcloud as email acquisition adapters;
- preservation of original received attachments;
- raw attachment SHA-256 as the existing exact-file duplicate check;
- Admin as the operational control surface.

v0.7.0 is a **file-format normalization release**, not a new account,
analytics, ingestion-provider or infrastructure release.

---

## 2. Product objective

v0.7.0 has three coordinated goals:

1. accept additional sailing track formats without creating format-specific
   Activity, Session or Viewer semantics;
2. converge all supported formats on one canonical TackBar normalized track
   representation;
3. define and introduce post-normalization logical duplicate detection only
   after the multi-format canonical representation is sufficiently understood.

The intended flow is:

```text
email provider
      ↓
attachment
      ↓
format detection / parser
      ↓
format-specific extraction
      ↓
TackBar canonical normalization
      ↓
canonical normalized track
      ↓
logical duplicate resolution
      ↓
Activity → Session → Viewer
```

Acquisition provider and source file format are separate concerns.

---

## 3. Supported format order

The agreed implementation and real-data validation order is:

```text
1. GPX
2. VKX
3. FIT
```

The existing Vakaros CSV / CSV.GZ path remains supported.

Each new format is integrated and validated before the next format is promoted.

This order is an implementation/validation sequence, not permission to redefine
downstream domain behavior per format.

---

## 4. Canonical normalized track

### 4.1 One convergence model

All supported source formats must converge on the same TackBar normalized track
model before Activity creation, Session matching and Viewer consumption.

v0.7.0 must not create:

- GPX Activities;
- VKX Activities;
- FIT Activities;
- format-specific Sessions;
- format-specific Viewer semantics.

The source format remains acquisition/provenance metadata.

### 4.2 Minimum navigation baseline

The canonical normalized track must provide, at minimum when a valid sailing
track can be constructed:

- UTC/GPS sample time;
- latitude;
- longitude;
- SOG;
- COG.

SOG and COG are part of the minimum TackBar navigation baseline.

### 4.3 Derived SOG and COG

A source format such as GPX may not provide SOG and/or COG directly.

When required, TackBar may derive SOG and COG from the source's GPS positions
and timestamps using one deterministic, documented and regression-tested
normalization algorithm.

This derivation is part of track normalization and does not create a new sailing
analytics feature.

Validated calculation knowledge from maxSail analytics may be reused, but
v0.7.0 must preserve TackBar's independent normalization boundary rather than
coupling the product architecture to the old Streamlit application.

### 4.4 Optional telemetry

HEEL and TRIM are optional canonical telemetry.

When the source does not provide them, TackBar does not invent them.

The same rule applies to other source-specific sensor data unless separately
promoted into the canonical contract.

### 4.5 COG and HDG remain distinct

COG and HDG/heading remain different concepts.

TackBar must not derive HDG from COG.

If a source provides a valid true heading/HDG value that the normalized model
supports, it may be preserved as heading data. If it is unavailable, it remains
unavailable.

---

## 5. Source-format adapters

Each supported format may have its own parser/extractor.

A format adapter is responsible for:

- recognizing/validating the supported input;
- extracting source samples and available metadata;
- converting source values/units into inputs suitable for normalization;
- reporting deterministic parsing/validation errors;
- preserving relevant source provenance.

A format adapter must not own:

- Sailor identity;
- consent;
- Activity identity;
- Session matching;
- Session capability semantics;
- Personal TackBar authorization;
- Viewer behavior.

---

## 6. Canonical fingerprint and logical deduplication

### 6.1 Why fingerprinting moves to v0.7.0

The post-normalization fingerprint is intentionally designed in v0.7.0 rather
than v0.6.0 because file-format diversity is needed to define a useful logical
track identity without freezing the contract around a single source format.

### 6.2 Two duplicate levels remain distinct

TackBar keeps:

```text
raw attachment SHA-256
```

for:

> Have these exact received bytes already been processed/resolved?

and introduces:

```text
canonical track fingerprint
```

for:

> Does this Sailor already have the same canonical normalized track identity?

The two mechanisms solve different problems.

### 6.3 Sailor-scoped logical identity

Logical track duplicate resolution remains scoped by stable Sailor identity.

Conceptually:

```text
sailor_id + canonical_track_fingerprint
```

Two different Sailors are not collapsed into one Activity because their
canonical tracks happen to match.

### 6.4 Fingerprint input is not yet frozen

The exact fingerprint identity field set is intentionally not fixed in this
draft.

Before persisted canonical fingerprints become identity data, v0.7.0 must use
representative GPX, VKX, FIT and existing normalized Vakaros CSV samples to
decide whether logical identity should hash:

- the full normalized canonical sample representation; or
- a deliberately smaller stable identity subset.

This decision must consider the fact that:

- SOG/COG may be source-provided in one format and derived in another;
- HEEL/TRIM may exist in one source and be absent in another;
- equivalent sailing data must not become different merely because of provider,
  filename or container metadata.

The decision must be closed before the fingerprint is persisted as durable
identity data.

### 6.5 Deterministic contract

Once the fingerprint input is selected, the contract must freeze and test:

- fingerprint version;
- included fields;
- row ordering;
- timestamp representation;
- numeric serialization and precision;
- missing-value representation;
- encoding;
- separators/record framing;
- hash algorithm.

Changing that contract later requires an explicit versioning/migration decision.

### 6.6 No fuzzy matching

v0.7.0 does not introduce approximate/tolerance-based duplicate detection.

Tracks with meaningfully different canonical identity input are not collapsed
merely because their time range, route or sample count is similar.

---

## 7. Error and persistence semantics

A malformed or unsupported attachment must not create a partial Activity.

The existing ingestion history and original-preservation semantics remain in
force.

Format-specific parsing failure must remain diagnosable without changing remote
mailbox state.

Reprocessing must continue to operate from the preserved original using the
current ingestion semantics.

Adding formats does not require a database migration.

---

## 8. Validation strategy

Each format is validated incrementally with representative real sailing files.

The expected order is:

```text
GPX
  ↓ validate normalization + SOG/COG
VKX
  ↓ validate richer sensor mapping
FIT
  ↓ validate device-format mapping
cross-format fixtures
  ↓ validate canonical identity/fingerprint
```

v0.7.0 should prefer small format-by-format increments rather than implementing
all parsers before validation.

---

## 9. Explicit non-goals for v0.7.0

v0.7.0 does not require:

- Garmin Connect / Activity API integration;
- direct Vakaros cloud integration;
- web track upload;
- additional email providers beyond the v0.6 baseline;
- automatic mailbox polling;
- ZIP/multi-file archive ingestion;
- arbitrary additional containers;
- fuzzy/semantic duplicate matching;
- HEEL/TRIM synthesis;
- HDG derivation from COG;
- advanced maneuver detection;
- new advanced sailing analytics;
- Session matching redesign;
- Session Viewer redesign;
- database migration;
- infrastructure expansion solely to support the new formats.

---

## 10. Decisions still to close before fingerprint persistence

The following are intentionally left open until representative multi-format
fixtures have been inspected:

1. exact canonical fingerprint field set;
2. whether SOG/COG used for identity are always normalized/derived by TackBar or
   may preserve source-provided values;
3. numeric precision/tolerance before deterministic serialization;
4. fingerprint versioning format and persisted metadata shape;
5. exact cross-format equivalence fixtures required for acceptance.

These are v0.7.0 design decisions, not v0.6.0 work.
