**Date:** 10 October 2026\
**Objective:** Evidence-driven evolution of the collaborative post-sailing debrief flow\
**Requirements:** [Collaborative Debrief Analytics](v0.7-collaborative-debrief-analytics-requirements.md)

## 1. Californian as a continuous release family

v0.7.x Californian began by rebaselining TackBar around collaborative debrief
analytics. v0.7.0 established the first maneuver-oriented analytical baseline
and later increments refined that delivered behavior.

After establishing that baseline, Californian operates as a continuous,
evidence-driven release family rather than as a fixed feature plan.

The governing flow is:

```text
real-sailing / product / operational evidence
→ focused GitHub Issue
→ explicit promotion decision
→ small implementation increment
→ proportional validation
→ later coherent v0.7.x release checkpoint
```

Open GitHub Issues remain pending work and do not become v0.7.x scope merely by
existing in the backlog.

A focused Issue may be promoted into v0.7.x when concrete real-sailing feedback,
product evidence, operational evidence or implementation findings justify the
change. Promotion applies only to the explicitly approved scope.

Promotion of one Issue does not:

- promote adjacent backlog items;
- implicitly broaden the release family;
- authorize unrelated refactoring;
- override existing domain, consent, persistence, ingestion, Session or Viewer
  semantics unless the promoted requirement explicitly changes them.

Previously deferred work may be reconsidered when new evidence justifies an
explicit promotion decision. This does not make the earlier deferral incorrect;
it records a later decision based on newer evidence.

## 2. Delivered objective and Viewer direction

The confirmed objective is focused collaborative debrief analytics:

Vakaros telemetry → canonical TackBar Activity → analytical event detection /
summaries → existing Session Viewer → sailors jump to useful moments →
collaborative debrief.

Maneuver-oriented analysis is delivered through the existing Viewer: neutral
events appear on the SOG timeline and in a compact sortable table, one row per
event. A table row or marker selects the event, moves shared `playbackTime` to
its center and focuses the corresponding Activity on the map without changing
the Analysis Window. This does not create a separate analytics product or
redefine the existing Summary.

The table prioritizes `Loss (m)`, `Loss (s)` and `Rec (s)`, then presents entry,
minimum and exit SOG, circular HDG change and duration. It retains a sticky
container-scoped header and horizontal mobile scrolling. Selected-row state is
stable across table/timeline interaction and clears when its Activity or
Analysis Window invalidates it.

The Analysis Window compact summaries also expose the existing dominant COG as
explicit directional context, and the fixed map telemetry remains readable when
focus is offset above it.

v0.7.1 places the selected maneuver's Loss distance, equivalent Loss time and
Recovery time beneath the compact Primary or Comparison summary that owns the
event. It reuses existing formatting and unavailable semantics, appears only
for an explicit valid selection and remains independent from replay movement.
The compact summaries retain whole-degree Dominant COG while omitting only its
visible `COG` label. Interval summaries, Summary-table presentation and fixed
instantaneous map telemetry retain their existing semantics.

## 3. Detector, boundaries and analytical ownership

The backend detector uses canonical HDG as the required signal and preserves
HDG/COG distinction. It segments on gaps over 1.5 seconds, applies local
circular smoothing and turn-rate calculation, seeds candidates at 4 degrees
per second and follows directional rotation at 0.5 degrees per second. Accepted
events last 3 through 30 seconds and satisfy deterministic heading-change,
coherence, sample-integrity and available multisensor-context checks. A
continuous segment needs at least 20 valid HDG samples.

Start/end delimit the accepted directional core. Center time is the
cumulative-rotation midpoint and is the sole event navigation time. Missing or
insufficient required telemetry returns unavailable analytics; it does not
fall back from HDG to COG or fabricate samples.

Detection and metrics are backend-owned. A capability-scoped Activity endpoint
enforces the existing Session and ACTIVE-only visibility boundary. The backend
persists strict per-Activity analytical artifacts, keyed by canonical-track
SHA-256 and algorithm version, and lazily regenerates missing, malformed or
stale artifacts. v0.7.0 closes on maneuver algorithm version `6`.

## 4. Evidence-driven, provisional metrics

The metric set is evidence-driven, provisional and expected to evolve during
v0.7.x. Real sailing validation may justify adding, removing or adjusting
metrics without redefining the whole release family.

The delivered contract includes start/center/end timestamps, duration, circular
HDG change, entry/minimum/exit SOG, recovery time, Loss distance and equivalent
Loss time. Missing inputs remain unavailable. HEEL and TRIM may support detector
validation when present but are not published maneuver metrics in v0.7.0.

This flexibility is deliberate: usefulness and telemetry quality must be
validated before an illustrative metric becomes a product commitment.
Each delivered calculation still needs explicit inputs, units, time semantics,
missing-data handling and deterministic regression coverage. Small additional
analytics require concrete sailing evidence, a debrief purpose and focused
scope review. This does not authorize unrelated feature expansion.

Delivered maneuver Loss uses pre-maneuver entry SOG as one constant reference.
It is the positive, piecewise-linear integral of the deficit between that
entry speed and actual canonical SOG from maneuver start through recovery,
using actual sample timestamps; Loss time divides the equivalent distance by
the same entry speed. SOG above entry speed contributes no negative Loss.
This is a compact debrief measure, not tactical gained/lost, VMG,
mark-relative or opponent-relative analysis, and it introduces no wind or
tactical interpretation. The detailed repeatable calculation and existing
recovery availability conditions are defined by V7-MET-03.

## 5. Neutral maneuver semantics

A significant sailing-direction change is initially a neutral maneuver event.
It is not automatically a tack or gybe. Reliable classification requires
real-data validation and a separate explicit promotion of that semantic.
TackBar must not reconstruct or invent wind merely to support classification.

This avoids claiming sailing meaning that the available telemetry has not
established. HDG and COG remain distinct, HDG is not derived from COG, angular
handling remains circular, and missing sensor values remain unavailable.
HEEL/TRIM signs do not gain unvalidated semantic labels.

## 6. Preserve the collaborative Viewer and domain baseline

Existing semantics remain unchanged unless a future requirement explicitly
changes them:

- Activity is one received track; no automatic merge/split;
- stable Sailor identity, optional Boat and existing Session matching;
- one or two selected Activities;
- one shared absolute GPS/UTC Analysis Window and one shared `playbackTime`;
- current map/replay model, charts and Summary;
- consent, ACTIVE-only shared visibility, Personal TackBar and Session
  capability, expiration and renewal rules;
- current CSV/CSV.GZ ingestion, provider boundaries, immutable originals and
  raw attachment SHA-256 exact-file duplicate checks;
- JSON metadata/filesystem persistence and private runtime data boundaries.

Events annotate Activities; they do not create races, legs, Sessions or Saved
Segments. Event selection moves the shared replay within the Analysis Window
without silently changing that window or introducing another clock.

## 7. Multi-format ingestion deferred

GPX, VKX and FIT ingestion, related cross-format canonical normalization and
canonical logical fingerprint/deduplication move together to:

**Status:** Future\
**Release:** Unassigned

They are no longer committed v0.7.0 or v0.7.x scope. No v0.8.x or other release
assignment is created. The earlier format sequence and fingerprint design
questions are not prerequisites for Californian analytics.

The long-term source-format-independent direction is preserved: future inputs
may converge on canonical Activities and the existing Session/Viewer flow.
Open GitHub Issues retain useful context; detailed future
contracts must be reconsidered when promoted. Raw attachment SHA-256 remains
the current exact-file mechanism. Garmin Connect remains a separate Future /
Unassigned integration, independent from FIT file support.

## 8. Advanced analytics constrained

Start analysis, automatic legs, gained/lost, tactics, automated coaching,
AI advice, maneuver scoring/ranking, wind/race reconstruction and Saved
Segments are not part of the initial scope. Advanced tack/gybe classification
requires reliable validation and explicit later promotion. New formats,
providers and database migration are excluded as well.

These constraints keep validation centered on useful maneuver-oriented debrief
instead of recreating MaxSail Analytics or speculative analytical breadth.
Future ideas in open GitHub Issues do not acquire a release commitment by
association.

## 9. Evidence-driven increment policy

Later v0.7.x work is selected incrementally from the GitHub Issue backlog.

A candidate increment requires:

- concrete real-sailing, product, operational or implementation evidence;
- explicit promotion into v0.7.x;
- narrow scope and explicit non-goals;
- reconciliation with existing requirements and decisions;
- preservation of existing behavior unless a change is deliberately approved;
- proportional testing and validation.

This policy supports small product, ingestion, usability, analytical,
operational and corrective increments when they improve the real TackBar
post-sailing workflow.

It does not authorize speculative architecture, unrelated refactoring or
automatic promotion of nearby backlog items.

## 10. Delivered decisions and release checkpoints

The decisions required for v0.7.0 are closed: detection inputs and thresholds,
event boundaries, metric subset and definitions, missing/noisy-data and gap
policy, Analysis Window filtering, center-time navigation, calculation/API
ownership, artifact invalidation and Viewer presentation.

The v0.7.1 presentation decision is also closed: selected Loss (m), Loss (s)
and Recovery (s) appear beneath the owning compact Activity summary; their
lifetime follows explicit valid maneuver selection; and only the visible
compact `COG` label is removed. Maneuver detection/calculation, API,
persistence, replay, Analysis Window and map-telemetry behavior are unchanged.

The v0.7.0 automated release gate covered detector and metric behavior,
persistence and invalidation, capability API behavior, complete frontend
regression, typecheck, production build and backend compilation. The v0.7.1
gate covers the complete frontend regression, typecheck and production build;
backend behavior is unchanged. Production deployment and real production
Viewer validation remain pending and MUST NOT be inferred from either gate.

Future v0.7.x patches are release checkpoints for coherent sets of explicitly
promoted and validated increments. A patch release does not need a complete
feature plan before those increments are selected.

Real-sailing, product, operational or implementation evidence may therefore
change the next v0.7.x priority while preserving the delivered baseline and the
explicit promotion discipline defined above.

Individual normalized maneuver profiles, aggregate Primary/Comparison profiles
and all other open backlog items remain uncommitted unless separately promoted.
