# TackBar v0.6.4 — Sailor Activation Welcome Email Decisions

**Status:** Closed  
**Release:** v0.6.4  
**Scope:** product and architecture decisions governing the Sailor activation welcome-email increment

---

## D6.4-01 — Singular release scope

v0.6.4 contains one product increment: `Sailor activation → welcome email`.
The post-v0.6.3 SailorDetail Session-card hierarchy fix is included because it
was committed after the published tag, but is not a second objective. This keeps
the release coherent without retroactively changing v0.6.3.

## D6.4-02 — Welcome email follows consent

Consent succeeds first; email delivery is secondary and non-transactional with
respect to consent. This keeps the existing human consent decision authoritative.

## D6.4-03 — One automatic activation email

Exactly one automatic attempt follows successful PENDING → ACTIVE Admin
confirmation. Other reads or operational events must not unexpectedly send mail.

## D6.4-04 — Sender identity

`share@tackbar.eu` is the authenticated sender and remains the track-sharing
destination. No `info@`, `noreply@` or additional mailbox is introduced.

## D6.4-05 — Independent SMTP configuration

SMTP and IMAP configuration remain independently replaceable. Matching runtime
values do not justify coupling credentials or protocols in the application.

## D6.4-06 — OVH SMTP baseline

Authenticated OVH SMTP over SSL/TLS on expected port 465 is the production
baseline, keeping the pilot on its existing operational provider.

## D6.4-07 — One bilingual message

One message contains English then Spanish. No language preference model is
introduced at pilot scale.

## D6.4-08 — Vakaros-only onboarding

The welcome message describes only the current Vakaros Connect sharing flow and
the two approved guide URLs, avoiding premature claims about future formats.

## D6.4-09 — Personal TackBar link included

The message uses the current Personal TackBar capability plus configured public
application origin, making the operational link explicit without request-header
URL construction.

## D6.4-10 — Sending never regenerates capability

Automatic send and resend must never regenerate capability. Capability changes
remain explicit Admin operations with their existing authorization semantics.

## D6.4-11 — Minimal delivery persistence

Persist the latest successful submission timestamp and current safe failure
indication, rather than a complete mail audit history, to meet pilot operations
without expanding the data model unnecessarily.

## D6.4-12 — Explicit Admin resend

Retry is human-operated and only for ACTIVE Sailors with usable personal access.
This provides recovery without autonomous delivery behavior.

## D6.4-13 — No retry infrastructure

No queue, worker, scheduler or SaaS is introduced. Synchronous post-consent
sending remains adequate for the current pilot.

## D6.4-14 — Delivery failure visible independently from consent

Admin must distinguish ACTIVE consent from failed email delivery so a transport
problem cannot be misread as a failed consent transition.

## D6.4-15 — Plain text sufficient

Plain text meets the operational need; HTML and a template system are deferred.

## D6.4-16 — Broader outbound email remains future

Other outbound messages require a separate explicit product decision so this
increment does not become a general communications platform.

## D6.4-17 — Personal first-person welcome copy

The approved welcome email uses a direct first-person voice from Maxi, a Snipe
sailor and the person behind TackBar. It remains one plain-text bilingual
message, with English first and Spanish second, the existing Vakaros-only
onboarding, the current Personal TackBar URL, the privacy warning and the
existing `Welcome to TackBar / Bienvenido a TackBar` subject. The exact copy is
the tested implementation in `backend/app/services/welcome_email.py`, not a
new template or localization system.
