# TackBar v0.5.0 — Real Sailing Pilot Requirements

**Status:** Proposed requirements based on closed product decisions  
**Scope:** PoC / controlled real-sailor pilot  
**Baseline:** TackBar v0.4.0 Collaborative Sailing Debrief  
**Decision source:** `v0.5-decisions.md`

---

## 1. Relationship to v0.4

v0.5.0 extends the delivered v0.4 collaborative debrief without redefining validated Viewer or Session-matching behavior.

The following remain baseline unless explicitly overridden here:

- Sailor → Activity → Session domain direction;
- Activity identity and deduplication;
- current Session matching;
- persisted Session and normalized Activity track APIs;
- Session Viewer semantics;
- one/two-Activity comparison;
- shared Analysis Window;
- replay;
- SOG/COG/HEEL/TRIM presentation and existing metrics;
- JSON metadata + filesystem track/original persistence.

v0.5.0 focuses on **controlled real-user operation, consent-aware visibility, Session capability access and minimal administration**.

---

## 2. Product objective

### V5-OBJ-01 — Real Sailing Pilot

TackBar v0.5.0 MUST allow a small controlled group of real sailors to participate in TackBar through a consent-aware workflow, share sailing tracks by email, have those tracks ingested into Activities and matched to Sessions, and access a collaborative Session through a non-guessable capability URL.

The intended PoC workflow is:

```text
invite / consent
      ↓
Sailor
      ↓
email track
      ↓
admin-triggered Gmail ingestion
      ↓
Activity
      ↓
existing Session matching
      ↓
ACTIVE-only shared visibility
      ↓
capability URL
      ↓
mobile collaborative debrief
```

### V5-OBJ-02 — Human-operated PoC

v0.5.0 MUST NOT require full operational automation.

The administrator MAY manually:

- send consent/invitation email through Gmail;
- review explicit consent replies in Gmail;
- trigger mailbox ingestion;
- confirm consent in TackBar Admin;
- send/copy Session links.

Automation MAY be added later but is not an exit criterion.

## 3. Consent domain

### V5-CNS-01 — Consent status

Sailor MUST have one current consent status:

```text
PENDING
ACTIVE
REVOKED
```

### V5-CNS-02 — Default state

A Sailor without confirmed consent MUST NOT be treated as ACTIVE.

A newly created Sailor requiring consent SHOULD enter `PENDING`.

### V5-CNS-03 — ACTIVE visibility rule

Only Activities belonging to an `ACTIVE` Sailor MAY be exposed through shared Session APIs and capability access.

Activities belonging to `PENDING` or `REVOKED` Sailors MUST be excluded server-side from shared responses.

Frontend-only hiding is insufficient.

### V5-CNS-04 — Processing independent from consent

A valid Activity MAY be ingested, persisted and matched to a Session while its Sailor is `PENDING` or `REVOKED`.

Consent controls **shared visibility**, not technical Session membership.

### V5-CNS-05 — Revoke

When a Sailor explicitly declines participation before consent is confirmed:

```text
PENDING → REVOKED
```

When previously granted consent is withdrawn:

```text
ACTIVE → REVOKED
```

Consent history MUST distinguish the pre-consent decline from the
post-consent withdrawal without introducing another consent status.

Existing Activities MUST immediately cease to be exposed through shared Session APIs.

The Activities are not automatically deleted as part of this transition.

### V5-CNS-06 — Re-entry

When a REVOKED Sailor starts a new participation cycle, for example by sending a new track:

```text
REVOKED → PENDING
```

The Sailor MUST not return to ACTIVE until consent is confirmed again.

### V5-CNS-07 — Consent history

TackBar MUST retain a minimal structured history of consent events sufficient to understand changes in state.

Event information MUST include at least:

- event type;
- timestamp;
- origin/source.

### V5-CNS-08 — Agreement version

TackBar MUST have a configured current agreement version.

When an administrator confirms consent, TackBar MUST record the current agreement version automatically.

The admin MUST NOT have to type the version manually for each confirmation.

### V5-CNS-09 — Manual confirmation

For v0.5.0, TackBar MUST support manual admin confirmation of consent after the administrator has reviewed an explicit acceptance reply in Gmail.

The operation MUST record at least:

- Sailor;
- transition to ACTIVE;
- confirmation timestamp;
- current agreement version;
- source indicating manual confirmation from email review.

TackBar MUST NOT require automated natural-language interpretation of the reply.

### V5-CNS-10 — Consent request tracking

For a PENDING Sailor, TackBar MUST distinguish between:

```text
consent_request_sent_at = null
→ consent must still be requested

consent_request_sent_at != null
→ request already sent; awaiting response
```

The admin UI and/or supporting scripts MUST make both groups identifiable.

## 4. Ingestion operation

### V5-ING-01 — Email remains the sharing channel

Email MUST remain the supported real-pilot track-sharing channel.

Gmail remains the PoC provider adapter for v0.5.0.

### V5-ING-02 — Admin-triggered mailbox review

v0.5.0 MUST provide an administrator operation equivalent to:

```text
Review mailbox now
```

This operation triggers Gmail candidate discovery and the existing provider-independent ingestion pipeline.

Automatic scheduled polling is not required for v0.5.0.

### V5-ING-03 — Script parity

A backend script MAY expose the same mailbox-review capability for diagnostics or operational fallback.

The Admin UI and script MUST reuse the same backend ingestion service rather than duplicate provider/domain logic.

### V5-ING-04 — Provider unread state

Gmail `unread` MUST NOT be the source of truth for TackBar processing state.

TackBar MUST maintain its own ingestion records.

### V5-ING-05 — Ingestion record

The ingestion record MUST contain enough information to support operational inspection and reprocesing.

The representation SHOULD cover the equivalent of:

- provider and provider message identifier;
- sender email;
- received timestamp when available;
- attachment filename;
- attachment SHA-256;
- persisted original reference/path;
- processing status;
- attempt count;
- last attempt timestamp;
- last error when present;
- resulting Activity ID when created/resolved;
- resulting Session ID when resolved.

Exact field names are implementation details.

### V5-ING-06 — Reprocess

The admin workflow MUST allow a known ingestion to be reprocessed.

Reprocessing MUST be idempotent with respect to existing Activity identity/deduplication and MUST NOT intentionally create duplicate Sessions or Activities.

### V5-ING-07 — Original preservation

TackBar SHOULD preserve the received original attachment under the private TackBar data root so a manual reprocess does not depend on the Gmail message remaining available indefinitely.

### V5-ING-08 — Single writer

Only one ingestion execution MAY modify TackBar persistence at a time.

The v0.5.0 human-operated flow may satisfy this through serialized admin operation; deployment automation introduced later MUST add an explicit lock/exclusion mechanism.

## 5. Admin requirements

### V5-ADM-01 — Minimal admin surface

TackBar MUST provide a deliberately small `/admin` operational surface for the PoC administrator.

It MUST NOT require a general user/role management platform.

### V5-ADM-02 — Admin protection

The Admin surface MUST be protected by one PoC administrator credential/secret or an equivalently simple private mechanism.

This mechanism is separate from Sailor Session access.

### V5-ADM-03 — Sailor overview

Admin MUST be able to identify Sailors by consent state and distinguish at least:

- ACTIVE;
- REVOKED;
- PENDING needing consent request;
- PENDING awaiting response.

### V5-ADM-04 — Consent actions

Admin MUST provide semantic operations equivalent to:

- `Confirm consent`;
- `Record withdrawal`;
- `Mark consent request sent`.

These operations MUST create/update the relevant structured consent history.

Direct arbitrary editing of `consent_status` is not the intended workflow.

### V5-ADM-05 — Ingestion operations

Admin MUST support:

- review mailbox now;
- inspect processed/failed ingestions;
- inspect last error when present;
- reprocess an ingestion.

### V5-ADM-06 — Session operations

Admin MUST allow inspection of at least:

- Session ID;
- creation time;
- expiration time;
- total internally associated Activities;
- number of currently shareable/visible Activities;
- capability URL/token state.

Admin MUST be able to regenerate/revoke the Session capability URL.

Admin MUST be able to renew a Session lifetime. Renewal MUST set
`expires_at` from the current UTC time, using 30 days by default or an explicit
positive duration of at most 365 days. It MUST preserve `created_at`, Session
membership and capability token/revocation state.

### V5-ADM-07 — Backend service boundary

Administrative modifications MUST go through backend services/repositories.

Frontend Admin MUST NOT read or write TackBar JSON files directly.

Scripts SHOULD reuse the same backend services.

Direct JSON editing MAY be used only as manual diagnosis, not as the normal update mechanism.

## 6. Session capability access

### V5-ACC-01 — No Sailor login for Session access

Opening a shared Session in v0.5.0 MUST NOT require Sailor authentication/login.

Possession of a valid Session capability URL is sufficient for access.

### V5-ACC-02 — Capability token

The shared access token MUST be distinct from the internal Session ID and MUST be generated using an adequately unpredictable random mechanism.

### V5-ACC-03 — Token creation

A Session MAY exist internally without a capability token.

The token SHOULD be created when the Session first contains at least one shareable Activity belonging to an ACTIVE Sailor.

### V5-ACC-04 — Shared Session filtering

A valid capability URL MUST expose only Activities whose Sailors are ACTIVE at request time.

If an ACTIVE Sailor becomes REVOKED, their Activities MUST disappear from subsequent shared Session responses without changing Session membership.

### V5-ACC-05 — Stable access during active period

The capability URL SHOULD remain stable for the active life of the Session unless the admin explicitly regenerates/revokes it.

### V5-ACC-06 — Regeneration

When the admin regenerates a capability token, the previous token MUST cease to authorize access.

## 7. Session lifetime

### V5-SES-01 — Session creation timestamp

Session MUST have a `created_at` timestamp or equivalent canonical creation time.

### V5-SES-02 — Session expiration

Session MUST have an `expires_at` timestamp.

For initial Session creation in v0.5.0:

```text
expires_at = created_at + 60 days
```

The 60-day rule is a PoC product rule, not a permanent business-policy commitment.

### V5-SES-03 — Expired Session access

After `expires_at`, the Session MUST no longer be accessible through its capability URL.

Expiration MUST NOT automatically delete Activity, track or original data.

### V5-SES-04 — Living Session

New compatible Activities MAY join the same Session according to the existing Session-matching implementation, regardless of when their email was received or whether the Session's shared access has expired.

Session expiration governs shared capability access, not technical Session membership. Therefore, after `expires_at`:

- `Session.activity_ids` MAY continue to grow through existing Session matching;
- adding an Activity MUST NOT reactivate shared access;
- adding an Activity MUST NOT create or rotate a capability token;
- any existing expired capability remains unusable;
- the Session, Activities, tracks and Session metadata remain persisted.

v0.5.0 MUST NOT redefine Session-matching thresholds or selection behavior.

Admin renewal is the explicit v0.5.0 operation for reopening shared access:

```text
new expires_at = current UTC time + renewal duration
```

The default renewal duration is 30 days and an explicit duration MUST be a
positive integer no greater than 365 days. Renewal MAY apply before or after
expiration and MUST preserve `created_at`, `activity_ids`, the capability token
and its revocation state. Consequently, renewal makes an existing non-revoked
capability usable again only when the Session has shareable `ACTIVE` content;
it does not create, rotate, un-revoke or regenerate a token. A new Activity, a
Sailor becoming `ACTIVE`, capability regeneration or a Session read MUST NOT
implicitly renew the Session.

## 8. Activity retention and privacy behavior

### V5-RET-01 — Personal Activity retention

Activities of an ACTIVE Sailor MAY remain stored as part of TackBar's service/history even after a shared Session expires.

### V5-RET-02 — Expiration is not deletion

Session access expiration and Activity data deletion are separate concepts.

v0.5.0 MUST NOT delete Activities merely because a Session reaches 60 days.

### V5-RET-03 — Withdrawal

When a Sailor becomes REVOKED, their Activities MUST stop being shared immediately.

Automatic physical deletion/anonimization on revocation is not required in v0.5.0 and is deferred to a later maintenance/privacy policy.

### V5-RET-04 — Admin access purpose

Admin access to personal tracks and metadata MUST be limited by product policy to operational purposes such as support, maintenance, reprocessing and consent management.

---

## 9. Pilot agreement content

### V5-AGR-01 — Plain-language conditions

The invitation/acceptance email or referenced agreement SHOULD explain in plain language that:

- TackBar receives, stores and processes sailing tracks to provide Sessions, debriefing, history and analysis;
- shared Sessions are accessible through capability links and expire after 60 days in the PoC;
- Activities may remain internally stored while the Sailor remains ACTIVE;
- withdrawing consent immediately stops shared visibility;
- further deletion/retention handling follows TackBar's maintenance/privacy process;
- authorized admin access exists for operation/support/maintenance;
- TackBar may use derived/aggregated analysis for product improvement where appropriate.

The agreement SHOULD avoid language claiming permanent ownership of all participant data.

---

## 10. Explicit non-goals for v0.5.0

v0.5.0 does NOT require:

- Sailor login/authentication;
- web consent token flow;
- automatic interpretation of consent replies;
- automatic outbound email;
- scheduled Gmail polling;
- QR sharing;
- Personal TackBar / My Activities UI;
- monetization or plans;
- automatic deletion/anonimization policy;
- alternate email provider;
- database migration;
- Session matching redesign;
- advanced analytics beyond the existing Viewer scope;
- general multi-admin role management.

---

## 11. Acceptance criteria

v0.5.0 is functionally ready for a controlled Real Sailing Pilot when:

1. Sailors have PENDING/ACTIVE/REVOKED consent state with minimal event history.
2. Admin can identify Sailors needing a consent request and those awaiting reply.
3. Admin can confirm consent after reviewing a Gmail acceptance and the Sailor becomes ACTIVE with timestamp/version recorded automatically.
4. Admin can record withdrawal and the Sailor's Activities immediately disappear from shared Session responses.
5. Admin can manually trigger Gmail ingestion.
6. Ingestion state is independent from Gmail unread status and provides enough context for diagnosis/reprocess.
7. Reprocessing a known ingestion is idempotent.
8. Activities continue to use the existing Session matching implementation.
9. Shared APIs expose only ACTIVE Sailor Activities.
10. A Session with shareable content can have a non-guessable capability URL distinct from its internal ID.
11. Capability URLs can be regenerated/revoked by Admin.
12. Sessions have `created_at` and `expires_at`, with PoC expiration at 60 days.
13. An expired Session capability no longer grants access but its Activities remain stored.
14. Existing v0.4 Viewer behavior remains intact for the Activities that are visible.
15. No change introduces direct frontend access to JSON/filesystem persistence.
