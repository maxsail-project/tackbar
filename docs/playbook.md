# TackBar collaboration playbook

This is TackBar's shared method for moving a GitHub Issue from analysis to an accepted, traceable increment. It is tool-independent and does not grant authority. [AGENTS.md](../AGENTS.md) governs agent operation, permissions, Git, continuous delivery, and release safety; the [AI Development Guidelines](ai-development-guidelines.md) own engineering principles. The [current specification index](current/index.md) routes to product contracts. If this playbook appears to conflict with them, follow the governing source and surface the discrepancy before implementation.

## Responsibilities and working modes

The product owner decides scope, unresolved product questions, authorization, and acceptance. An analysis assistant reconstructs evidence, frames decisions, prepares a bounded handoff, and reviews the result. A development agent implements the approved increment, runs relevant checks, and reports what it actually did. Independent review must remain distinct from implementation. A role describes responsibility; it neither requires a particular AI platform nor inherits permissions from one. Verify the current session's tools, access, model controls, and effective permissions before relying on them.

**Ordinary mode** is the default: the product owner controls normal development Git actions and acceptance unless expressly authorized otherwise. **Issue-scoped continuous mode** exists only under the authorization and conditions in [AGENTS.md](../AGENTS.md#issue-scoped-continuous-delivery-mode). Follow that source for eligibility, agent independence, binding model and effort, stops, branches, CI, closure, and release handling. The separate [Release Preparer](../agents/release-preparer.md), [Release Publisher](../agents/release-publisher.md), and [release workflow](workflows/release-preparation-workflow.md) retain their specialist roles. A tool's ability to perform an action is not authorization to do it.

## Reconstruct the real baseline

Begin with the updated Issue and relevant comments: decisions, authorizations, increment reconciliations, manual acceptance, and closure. Confirm the current branch, HEAD, working tree, and any remote state needed for the task. Identify delivered commits and inspect affected code, tests, and documentation before proposing more work. Respect existing increment numbering when the history supports it. An open Issue may have completed increments; a closed one does not by itself prove publication or deployment. Keep related Issues' scopes separate.

Read sources efficiently in the [AGENTS.md hierarchy](../AGENTS.md#instruction-hierarchy-and-reading-route): engineering principles; only the affected current specifications, including cross-domain contracts; the approved delta; then implementation and tests as evidence. Use versioned decisions for a specific provenance or discrepancy question. Consult specialist guidance when the task reaches that domain. Do not derive current requirements from historical conversation, an Issue title, GitHub Project order, or isolated code. Record what could not be accessed or verified. A material conflict or missing product decision needs resolution before implementation.

For a new analysis session, summarize **confirmed baseline, genuinely pending work, closed and open decisions, material risks, and the next coherent increment**. Mark assertions as verified, reported, proposed, or assumed where the distinction matters. Discuss only decisions that remain open; name a recommended option and its trade-offs. Use numbered decisions when several need the owner's approval. Do not reopen settled decisions without new evidence. The [Issue-start workflow](workflows/change-issue.md) gives the starting procedure; this playbook supplies the underlying method.

## Shape an Issue and pass the preparation gate

Use the current [Product / Engineering Increment form](../.github/ISSUE_TEMPLATE/change.yml) for Issue intake and the [release preparation form](../.github/ISSUE_TEMPLATE/release-preparation.yml) for its specialist case. The form supplies fields and documentation-impact classifications; the Issue records the problem, evidence, goal, baseline, proposed delta, exclusions, decisions, and observable acceptance. State uncertainty in an early proposal. An Issue's `Status`, including `Ready for implementation`, describes preparation, not authorization. Use the repository's `[#id]` title and one `group:*` label conventions; verify created metadata when Issue mutation is authorized. The release subtitle and other owner decisions belong in the Issue when applicable. Creating or changing an Issue still needs authorization under [AGENTS.md](../AGENTS.md#issues-scope-and-decisions).

Before handing off implementation, check that the **specific increment** has an approved delta, verified delivered baseline, relevant contracts and tests, closed material decisions, scope and non-goals, compatibility limits, observable acceptance, documentation impact, and a proportionate test strategy. A micro-fix may need only a few lines; a cross-domain change needs more evidence. Separate distinct kinds of work when that makes review or manual testing clearer, while keeping any required contract, code, and test update together. Group Issues only for a real dependency, without merging their authority or acceptance. If the gate is not met, identify the decision or evidence needed rather than filling it in by assumption.

## Hand off a bounded increment

The Issue and current specifications already hold the requirements. Give the development agent a compact, source-referenced prompt stating the increment and baseline, concrete delta, critical constraints, authorized documentation, checks, and handoff evidence. Keep the source documents linked instead of copying them. Use the established header fields: `Impact`, `Recommended development model/tool` (tool, model, and effort), `Test strategy`, and `Full regression`; include a suggested Conventional Commit with an Issue reference. The prompt header fixes the impact for that increment. Under continuous mode, follow [AGENTS.md](../AGENTS.md#issue-scoped-continuous-delivery-mode) for the authorized binding model and effort.

Implementation stays within the approved delta. Inspect code and focused tests first; reuse existing boundaries and patterns; avoid unrelated cleanup. [AGENTS.md](../AGENTS.md#product-and-engineering-boundaries) and the [guidelines](ai-development-guidelines.md) own domain and technology constraints. When documented functional behavior changes, follow their co-update rule for affected code, regression tests, and `docs/current/`. If a view's structure changes, check assertions depending on its order, columns, or count. Share test fixtures and helpers when repetition would obscure intent. A tool finding is a candidate: compare it with callers, contracts, and real exposure before calling it a defect or proposing an authorized fix.

## Verify, review, and accept

Choose validation by impact and changed behavior. Run focused tests and the applicable backend or frontend checks; use real sailing data when useful. Broader regression, manual validation, or a full gate needs a concrete reason. Distinguish checks executed locally from CI, manual product testing, release preparation, and production checks. If the environment cannot run a check, say so. The [SonarQube workflow](../.github/workflows/sonarqube.yml) and [validation scripts](../scripts/) provide repository mechanisms; inspect their current definitions rather than assuming a historical command or trigger still applies. For closing ordinary Issues, SonarQube is the default CI evidence: verify the completed run on the exact delivered SHA, its passed and skipped test counts, quality gate, and applicable build results.

Review the actual diff against the Issue, current contracts, and tests. Check scope, compatibility, privacy, dependencies, documentation authority, and every relevant test result. An agent's `PASS` is reported evidence until independently checked; state `FAIL`, `SKIP`, `NOT RUN`, or `DEFERRED` accurately. Where CI is used for delivery evidence, match the run to the exact delivered SHA, wait for completion, and inspect the relevant test, typecheck, build, and quality-gate results. A green gate does not replace review or human acceptance. Follow [AGENTS.md](../AGENTS.md#issue-scoped-continuous-delivery-mode) for continuous-mode failure limits and stop conditions; do not silently broaden a correction.

The product owner accepts the result under the applicable mode. Reconcile what was implemented with the approved criteria and record files, SHA when committed, actual model and effort or verification limits, checks run and not run, CI links, manual findings, and unresolved risks. If review changes a product decision or scope, obtain and record approval before the correction; preserve superseded decisions as history. A completion claim, Issue closure, publication, and deployment are distinct events. For manual checks, give the owner a short route to the candidate and the behaviors to inspect. The Issue remains the traceable work record; a `completed` closure has the meaning set by [AGENTS.md](../AGENTS.md#issues-scope-and-decisions).

## Git and context continuity

For authorized commits, use a concise English Conventional Commit describing the delivered change, with `Ref: #N` (or `Refs:` for genuinely linked Issues). Check the current [AGENTS.md Git rules](../AGENTS.md#git-release-and-production-safety) before staging, branching, merging, publishing, or deploying. It owns ordinary versus continuous authority and the current branch procedure. Release identity and preparation belong to the specialist sources, not this playbook.

Keep durable decisions and evidence in the appropriate Issue or repository artifact; a later session should not need a private conversation to continue. A short dated context note can carry genuinely unrecoverable background, but must not become a second rulebook or stale state ledger. At the next start, verify Issue state, commits, documentation, CI, and tool permissions again. Update this playbook when the proven method changes, following the governing rules; do not rewrite it for every Issue or release.
