# TackBar v0.6.5 — Simplified Pilot Onboarding & Web Consent Decisions

**Status:** Closed
**Release:** v0.6.5
**Scope:** product and architecture decisions governing track-first onboarding and explicit web consent

---

## D6.5-01 — Track-first pilot onboarding

The normal pilot entry point is a supported track sent to `share@tackbar.eu`.
Removing pre-registration keeps entry aligned with the action Sailors already
need to take without expanding the supported ingestion surface.

## D6.5-02 — Track submission is not consent

Sharing a track starts technical onboarding only. Keeping consent as a separate
affirmative decision prevents an operational action from being interpreted as
permission.

## D6.5-03 — PENDING technical processing remains allowed

PENDING tracks continue through ingestion and Session matching while remaining
excluded from shared responses. This preserves the established separation
between technical processing and shared visibility.

## D6.5-04 — Explicit web acceptance

Normal activation uses a clear affirmative action on a capability URL. This
reduces manual coordination while preserving explicit consent.

## D6.5-05 — Consent capability is purpose-specific and separate

The high-entropy consent token is distinct from Sailor identity and all Session
and Personal capabilities. Its possession authorizes only the consent decision,
avoiding accidental general authentication or access.

## D6.5-06 — Consent token lifetime is 28 days

A fixed 28-day window balances time for a Sailor to respond with bounded token
exposure and simple pilot operation. Expiry does not modify domain data or
consent state.

## D6.5-07 — v0.6.5 agreement version is bound to immutable evidence

The canonical agreement version for newly issued requests in this web-consent
flow is `v0.6.5`. The request records that version at issuance and acceptance
preserves it in consent history. Historical requests and consent events using
`v0.5.0` or another prior version remain immutable evidence when the configured
or current agreement version later changes.

## D6.5-08 — Consent interaction and conditions live in the TackBar app

`app.tackbar.eu` owns both the consent interaction at `/consent/<token>` and the
complete conditions at `/consent/conditions`. Consent is application behavior;
`tackbar-web` remains public information and marketing content outside the
consent lifecycle.

## D6.5-09 — Token decision page plus token-independent conditions

The token page presents a concise bilingual decision summary, links to the
complete canonical conditions and owns the explicit affirmative action. The
conditions page is bilingual, read-only, requires neither a token nor login and
contains no consent action. Separating these purposes avoids duplicating the
complete conditions in the decision UI.

## D6.5-10 — Opening the link is never consent

Only an explicit affirmative submission on the decision page grants consent.
Opening either the token link or the conditions page never changes consent
state. This prevents browser prefetching, security scanners or accidental page
views from activating a Sailor.

## D6.5-11 — Acceptance is idempotent

Repeated submission reports the already-confirmed outcome without duplicating
events or activation effects. This makes ordinary browser/network retries safe.

## D6.5-12 — Existing SailorConsentService activation semantics are reused

Web acceptance enters the established consent service rather than creating a
parallel transition. One authoritative activation path protects current consent
events, capability and visibility behavior.

## D6.5-13 — v0.6.4 welcome flow remains downstream

Successful activation continues through the existing welcome-email behavior.
v0.6.5 changes how explicit consent arrives, not what a successful activation
does afterward.

## D6.5-14 — Existing OVH SMTP boundary is reused

Consent requests use the outbound boundary already established for the welcome
email. A second transport or provider would add complexity without a pilot need.

## D6.5-15 — One bilingual consent-request message

One plain-text message contains English first and Spanish second. This matches
current pilot communication without introducing language preferences,
localization infrastructure or HTML templates.

## D6.5-16 — Existing REVOKED-to-PENDING behavior is preserved

A valid supported track from a REVOKED Sailor starts a new PENDING cycle, as the
current ingestion implementation already does. The transition is not renewed
consent and still requires explicit acceptance.

## D6.5-17 — Manual Admin confirmation remains fallback

Controlled manual confirmation remains available for operational recovery. It
is a fallback, not the normal track-first web-consent path.

## D6.5-18 — Resend reuses valid token; expired request is reissued

Explicit Admin resend keeps a valid request stable, while an expired request
receives a new token. This avoids unnecessary capability churn and makes expiry
meaningful.

## D6.5-19 — Mail delivery failure is independent from consent

Failed request delivery cannot activate a Sailor or alter Activities, Sessions
or capabilities. Failed welcome delivery likewise cannot roll back consent, so
transport state never becomes consent state.

## D6.5-20 — No automatic retry or messaging-platform expansion

Human-operated resend/reissue is sufficient for the pilot. Queues, workers,
schedulers, transactional-email SaaS and a general outbound messaging platform
remain outside this release.

Implementation may choose persistence and endpoint details consistent with
repository conventions. Those details do not reopen the closed product
decisions above.
