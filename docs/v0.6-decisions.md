# TackBar v0.6.x — Consolidated Decisions

**Status:** Closed product and architecture decisions for the v0.6 release family  
**Date:** 8 September 2026  
**Scope update:** 11 September 2026 — Mahon pilot release/versioning clarified  
**Objective:** preserve the validated v0.5.x pilot baseline, keep v0.6.1 narrowly focused on Mahon pilot operation, and keep later v0.6.x work uncommitted until explicitly assigned.

---

## 1. Governance rule

TackBar v0.6.x starts from the validated v0.5.x baseline.

Existing behavior is not reconsidered or redefined unless an explicit v0.6.x decision changes it.

The following remain baseline:

- Sailor → Activity → Session;
- Activity as one track received by TackBar;
- stable internal Sailor identity;
- normalized email as the current external identity for email ingestion;
- current Session matching;
- PENDING / ACTIVE / REVOKED consent states;
- backend-enforced ACTIVE-only shared visibility;
- Session capability URLs;
- Session expiration and renewal;
- the existing Session Viewer;
- shared Analysis Window;
- replay and delivered metrics/charts;
- JSON metadata + filesystem persistence while it remains adequate;
- email as a product track-sharing channel;
- Gmail as the current mailbox provider;
- Admin as the operational control surface.

No v0.6.x work may silently redefine domain, consent, capability, persistence, ingestion, Session matching or Viewer semantics.

## 2. Release family and versioning

### 2.1 v0.6.0 — Personal TackBar baseline

v0.6.0 is the functional/productization baseline that introduced or consolidated:

- Personal TackBar / My Sessions with stable personal capability access;
- Admin personal-capability operations;
- TackBar visual-brand consolidation based on `tackbar-web`;
- MPL-2.0 transition for TackBar-owned source code;
- existing v0.5.x pilot semantics preserved.

This baseline remains the foundation for the Mahon operational release.

### 2.2 v0.6.1 Mahon — Pilot Operations

The current release is:

```text
v0.6.1 Mahon — Pilot Operations
```

Its objective is the smallest coherent published build suitable for the Mahon pilot.

Committed operational scope is limited to:

- Admin ingestion administrative disposition (`active` / `discarded`);
- semantic `Discard` / `Restore`;
- ingestion filtering by technical status and disposition;
- small focused operational fixes required for reliable pilot use;
- release validation/hardening and final release reconciliation.

Delivered micro-fixes in this scope include:

- deterministic Admin Session ordering by real `sailing_start`, newest sailing first;
- a quieter OpenFreeMap Positron basemap in the Session Viewer;
- the standard MapLibre navigation/compass control for manual map rotation/reset.

These map changes are presentation-only. They do not change track geometry, replay, Activity/Session semantics or analytics.

### 2.3 Patch releases after Mahon

After v0.6.1 is published, patch-level corrections use normal patch numbering:

```text
v0.6.2
v0.6.3
...
```

These numbers are not pre-reserved for feature work. They remain available for hot-fixes and small corrective releases discovered after Mahon.

### 2.4 Future 0.6.x

Valid follow-up work in the v0.6 family that is not committed to a concrete patch is labelled:

```text
Future 0.6.x
```

A concrete version is assigned only when that work is explicitly promoted into a release.

## 3. Personal TackBar baseline

An ACTIVE Sailor may have one current stable, non-guessable personal capability URL.

Conceptually:

```text
/me/<personal-access-token>
```

The token:

- is not the internal `sailor_id`;
- is not the Sailor email;
- is distinct from Session capability tokens;
- grants access to the Sailor's personal space only;
- does not introduce username/password login.

My TackBar is read-only Session participation history derived through:

```text
Sailor → Activity → Session
```

Each Session appears once. Activities remain internal domain entities rather than the primary personal surface.

Available Sessions reuse the existing collaborative Session Viewer and existing shared-capability authorization. Personal capability access does not bypass Session capability, lifetime or ACTIVE-only visibility rules.

Expired, revoked or otherwise unavailable Sessions remain historical participation entries but are not fabricated into usable Sessions.

Consent remains the runtime gate: PENDING/REVOKED Sailors cannot access personal history even if a token persists.

Admin can inspect, copy when usable, regenerate and revoke the personal capability. Regeneration invalidates the previous token. Personal-capability revocation does not change consent.

## 4. Admin ingestion maintenance — v0.6.1 Mahon

### 4.1 Technical status and administrative disposition are separate

Technical status remains:

```text
processed / failed
```

Administrative disposition is:

```text
active / discarded
```

Disposition does not redefine processing outcome.

### 4.2 Discard / Restore

`Discard` changes only the administrative disposition to `discarded`.

A discarded ingestion:

- remains persisted;
- remains known to deduplication;
- retains technical status;
- retains provider/message identity;
- retains any preserved original;
- retains Activity references and any Activity already created;
- retains Session references/membership;
- does not change consent;
- does not change Session or personal capabilities;
- does not mutate remote Gmail/mailbox state.

`Restore` changes only the disposition back to `active`.

Restore does not automatically reprocess the ingestion.

### 4.3 Filtering

The Admin ingestion view supports independent filtering by:

```text
Status:      All / Processed / Failed
Disposition: All / Active / Discarded
```

Default/no-filter behavior continues to expose all records using the existing ordering.

### 4.4 Physical deletion remains separate

`Discard` is not `Delete`.

v0.6.1 does not introduce physical Activity/track/original deletion as a side effect of ingestion maintenance.

A future deletion/anonymization workflow must separately resolve Activity metadata, normalized tracks, originals, Session references, Personal TackBar history, ingestion history, deduplication identity, retention and backups.

## 5. Session operations

v0.6.1 preserves existing Session semantics and maintenance operations:

- inspect capability state and expiration;
- Renew;
- Copy capability URL;
- Regenerate capability;
- Revoke capability.

The Admin Session list is ordered deterministically by derived `sailing_start` descending, with the most recent real sailing first. This is an Admin presentation/operational correction only; it does not change Session persistence or matching.

Broader Session-maintenance usability remains **Future 0.6.x** and is not assigned to a concrete patch.

---

## 6. Email ingestion boundary

Email remains the supported track-sharing channel and Gmail remains the current mailbox provider baseline.

The previously considered Gmail + OVHcloud increment is not part of v0.6.1 Mahon.

Provider-specific acquisition must not define Activity, Session, normalization, deduplication or Viewer semantics.

Remote provider flags such as `unread` are not TackBar processing state; TackBar continues to own ingestion records.

Multi-provider email ingestion remains **Future 0.6.x**. It is not assigned to v0.6.2, another specific patch, or v0.7.0 by default.

---

## 7. Session Viewer map presentation

The Session Viewer continues to use MapLibre with a replaceable zero-cost/no-key style provider.

For v0.6.1 Mahon:

- OpenFreeMap Positron is the selected basemap style;
- existing functional track colors remain unchanged and distinct from decorative brand colors;
- the standard MapLibre navigation/compass control is enabled;
- manual rotation affects camera presentation only.

No wind-oriented automatic bearing, TWD input, custom wind control or advanced map analytics is committed to v0.6.1.

## 8. TackBar visual brand baseline

`tackbar-web` remains the canonical visual reference.

Core palette:

| Color | Value |
| --- | --- |
| Navy | `#013663` |
| Blue | `#0383CC` |
| Pale | `#E3EAF0` |
| Background | `#F7F9FB` |
| White | `#FFFFFF` |

Functional sailing, comparison, telemetry and status colors remain independent from decorative brand colors.

The official SVG family remains the source logo system, including logo/lockup, wordmark, compact mark and claim/tagline variants already maintained in `tackbar-web`.

Brand consolidation must remain incremental and must not trigger a full frontend redesign.

---

## 9. Licensing baseline

TackBar-owned application and website source code use MPL-2.0 prospectively.

Historical versions distributed under MIT retain their historical MIT grants; old tags/releases are not rewritten.

The code license does not publish or relicense pilot participant data, email addresses, GPS tracks, originals or private runtime metadata.

## 10. Explicit non-goals for v0.6.1 Mahon

v0.6.1 does not require:

- OVHcloud ingestion or a second mailbox provider;
- generalized multi-provider email ingestion;
- broad Session-maintenance redesign;
- Sailor username/password login;
- web track upload;
- My Activities / standalone personal Activity access;
- physical Activity/track deletion;
- automatic scheduled mailbox polling;
- new logical/canonical track fingerprinting;
- GPX ingestion;
- VKX ingestion;
- FIT ingestion;
- Garmin Connect;
- direct Vakaros cloud integration;
- Saved Analysis Segments;
- advanced maneuver detection;
- automatic wind-oriented map mode;
- new advanced sailing analytics;
- Session matching redesign;
- database migration;
- complete frontend redesign.

---

## 11. Relationship to v0.7.0

v0.7.0 remains focused on file-format independence.

Agreed implementation/validation order:

```text
1. GPX
2. VKX
3. FIT
```

All supported formats converge on one canonical TackBar normalized track and the existing Activity → Session → Viewer flow.

v0.7.0 also owns definition of the minimum canonical normalized data required for logical duplicate detection and the deterministic fingerprint/hash contract.

Deferred v0.6 operational work is not automatically absorbed into v0.7.0.

---

## 12. Mahon release closure

Before publishing v0.6.1 Mahon, validation must confirm the real pilot flow remains coherent end-to-end:

```text
Gmail
→ ingestion
→ Sailor
→ Activity
→ Session
→ consent
→ Personal TackBar
→ Session Viewer
→ collaborative debrief
```

Release closure should use focused automated regression plus real manual operational validation appropriate to the risk of the delivered changes.
