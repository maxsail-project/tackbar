# TackBar v0.6.0 — Consolidated Decisions

**Status:** Closed product and architecture decisions for preparing TackBar v0.6.0  
**Date:** 8 September 2026  
**Objective:** define the product, access, operational, ingestion, visual-brand and licensing decisions for the next TackBar increment while preserving the validated v0.5.x pilot baseline.

---

## 1. Governance rule

TackBar v0.6.0 starts from the validated v0.5.x baseline.

Existing behavior is not reconsidered or redefined unless a v0.6.0 decision explicitly changes it.

The following remain baseline:

- Sailor → Activity → Session;
- Activity as one track received by TackBar;
- stable internal Sailor identity;
- normalized email as the current external identity for email ingestion;
- current Session matching;
- PENDING / ACTIVE / REVOKED consent states;
- backend-enforced ACTIVE-only shared visibility;
- Session capability URLs;
- Session expiration and renewal;
- the existing Session Viewer;
- shared Analysis Window;
- replay and delivered metrics/charts;
- JSON metadata + filesystem persistence while it remains adequate;
- email as a product track-sharing channel;
- Admin as the operational control surface.

v0.6.0 is an incremental productization step. It does not introduce a general user-account platform, advanced sailing analytics, or speculative infrastructure.

---

## 2. v0.6.0 product objective

v0.6.0 has four coordinated goals:

1. give an ACTIVE Sailor a simple permanent entry point to their own Session participation history;
2. make pilot ingestion and Session maintenance easier to operate;
3. support Gmail and the TackBar OVHcloud mailbox through one provider-independent ingestion boundary;
4. establish a coherent TackBar visual brand and transition TackBar's own public source code to MPL 2.0.

The intended personal flow is:

```text
ACTIVE Sailor
      ↓
personal capability URL
      ↓
My TackBar
      ↓
Sessions I participated in
      ↓
accessible Session → existing Session Viewer
expired/unavailable Session → truthful state
```

The intended ingestion flow is:

```text
Gmail ───────┐
             ├─ provider adapter → common ingestion → normalization → Activity → Session
OVHcloud ────┘
```

## 3. Personal TackBar / My Sessions

### 3.1 Personal capability access

Each `ACTIVE` Sailor may have one current stable, non-guessable personal capability URL.

Conceptually:

```text
/me/<personal-access-token>
```

The final route is an implementation/API decision, but the access token:

- is not the internal `sailor_id`;
- is not the Sailor's email;
- is distinct from Session capability tokens;
- acts as the personal access credential for this release;
- is generated with adequate entropy;
- does not introduce username/password login.

### 3.2 Read-only My Sessions

My TackBar is a read-only personal Session history. A Session belongs in it
when at least one of the Sailor's Activities is associated with that Session.
Each Session appears once. Membership is derived through
`Sailor → Activity → Session`, not a persisted `sailor.session_ids` relation.

Existing/derived context such as sailing date/time or interval and shared-access
availability helps identify Sessions, normally most recent first. Activities
remain internal domain entities rather than the primary personal surface.

The Sailor cannot edit profiles, modify/delete Activities, upload tracks,
administer Sessions, change consent or access another Sailor's personal history.

### 3.3 One collaborative Viewer

Available Sessions open in the existing collaborative Session Viewer under the
existing shared capability, lifetime and ACTIVE-only visibility rules. Personal
capabilities authorize the personal space, not arbitrary Activity/Session access.
They do not bypass shared authorization.

My Activities, individual personal Activity history/access and single-Activity
viewing are not committed v0.6 core scope. They remain uncommitted future
considerations in `product-backlog.md`, not automatically v0.7 work. No second
Viewer product, personal variant or duplicated implementation is introduced.

### 3.4 Personal history and Session lifetime

Expired, revoked or otherwise unavailable Sessions remain participation history,
truthfully marked unavailable to open without fabricated usable capabilities.
This does not promise durable personal Activity viewing after Session expiration.

Existing Admin renewal can extend or restore lifetime under current rules.
If an otherwise valid existing capability becomes usable again, the Sailor may
open the Session again. Renewal does not create, rotate or un-revoke tokens;
personal access does not renew Sessions or change membership or retention.

### 3.5 Consent gate

Personal Session history is exposed only while the Sailor is ACTIVE at request
time and the personal capability is valid. PENDING/REVOKED Sailors do not receive
it. Consent changes do not automatically destroy the personal token; personal
capability revocation does not change consent. This is an access rule, not
physical deletion or anonymization.

### 3.6 Admin maintenance

Admin can:

- inspect whether personal access exists;
- copy the current personal capability URL when usable;
- regenerate the personal capability;
- revoke the personal capability.

Regeneration invalidates the previous token.

These actions are semantic backend operations, not direct JSON editing from the frontend.

## 4. Admin ingestion maintenance

### 4.1 Technical status and administrative disposition are separate

v0.6.0 explicitly separates:

```text
technical ingestion status
processed / failed
```

from:

```text
administrative disposition
active / discarded
```

The administrative disposition is an operational classification. It does not redefine whether ingestion technically succeeded or failed.

### 4.2 Discard / Restore

Admin can perform semantic actions:

- `Discard`;
- `Restore`.

A discarded ingestion:

- remains persisted;
- remains known to deduplication;
- retains its technical status;
- retains provider/message identity;
- retains any persisted original;
- does not roll back an Activity already created;
- does not change Session membership;
- does not change consent;
- does not change Session or personal capabilities;
- does not mutate the remote mailbox merely because it was administratively discarded.

`Restore` changes only the administrative disposition.

### 4.3 Admin filtering

The ingestion view can combine at least:

```text
Status:
All / Processed / Failed

Disposition:
All / Active / Discarded
```

### 4.4 Physical deletion remains separate

`Discard` is not `Delete`.

v0.6.0 does not introduce physical Activity/track/original deletion as a side effect of ingestion maintenance.

A real deletion workflow must separately resolve:

- Activity metadata;
- normalized tracks;
- originals;
- Session references/membership;
- Personal TackBar history;
- ingestion history;
- deduplication identity;
- retention policy;
- backups/restores;
- participant data-right requests.

That remains a future privacy/maintenance capability.

## 5. Gmail + OVHcloud email providers

### 5.1 Two supported entry providers

v0.6.0 keeps Gmail supported and adds the TackBar mailbox hosted at OVHcloud.

Gmail is not removed.

The release demonstrates that email provider choice is an acquisition concern rather than a TackBar domain concern.

```text
Gmail adapter ─────┐
                   ├─ common ingestion service
OVHcloud adapter ──┘
```

### 5.2 Provider boundary

Provider adapters are responsible for:

- discovering candidate messages;
- obtaining minimum message metadata;
- identifying a message within that provider;
- retrieving attachments;
- provider-specific connection and retrieval errors.

After attachment retrieval, the following remain provider-independent:

- source-format parsing;
- normalization;
- existing raw attachment SHA-256 exact-file duplicate handling;
- Activity creation/resolution;
- Session matching;
- persistence;
- Viewer behavior.

No Gmail-specific or OVHcloud-specific Activity/Session model is introduced.

### 5.3 OVHcloud access mechanism

The actual access mechanism for the TackBar OVHcloud mailbox is selected only after verifying the capabilities of the specific OVHcloud email product in use.

IMAP is a valid candidate if officially supported for the required operation, but v0.6.0 does not assume IMAP without that verification.

Mailbox credentials and secrets remain runtime configuration and are never committed to Git.

### 5.4 Human-operated mailbox review remains valid

Admin-triggered mailbox review remains sufficient for v0.6.0.

The UI may expose provider-specific review actions or a combined mailbox review, but all supported providers reuse the same downstream ingestion/domain service.

Automatic scheduled polling remains outside v0.6.0.

## 6. Session maintenance

v0.6.0 preserves the Session semantics delivered in v0.5.x.

It does not change:

- Session matching;
- Activity membership;
- ACTIVE-only shared visibility;
- Session creation/expiration semantics;
- renewal semantics;
- Session capability authorization.

Admin should make routine Session maintenance easy to understand.

Expected operational actions remain:

- inspect accessible/expired status;
- inspect capability state;
- inspect expiration;
- `Renew`;
- `Copy capability URL`;
- `Regenerate capability`;
- `Revoke capability`.

Presentation/filtering improvements should derive state from the existing model rather than create redundant persisted domain concepts.

## 7. TackBar visual brand

### 8.1 Brand consolidation becomes part of v0.6.0

v0.6.0 consolidates the application around the already accepted `tackbar-web`
visual identity. `maxsail-project/tackbar-web` is the canonical visual reference
for this incremental adoption.

The brand direction is:

- clean;
- nautical;
- contemporary;
- slightly informal rather than corporate;
- focused on sailing, debrief and learning;
- mobile-first and readable outdoors;
- consistent across the TackBar application, public website, documentation and presentation material.

The brand must not become visually dependent on beer/alcohol imagery. The social "bar" idea can remain part of TackBar's personality, but the product must remain inclusive for sailors who do not drink, minors and performance-focused athletes.

### 8.2 Brand name and tagline

The primary product name remains:

```text
TackBar
```

The preferred short brand tagline is:

```text
Sail. Debrief. Learn.
```

The product story remains about:

```text
sailing → sharing evidence → discussing what happened → learning
```

### 8.3 Official color palette

The canonical core palette comes from `tackbar-web/assets/styles.css`:

| Color | Value | `tackbar-web` CSS token |
| --- | --- | --- |
| Navy | `#013663` | `--color-navy` |
| Blue | `#0383CC` | `--color-blue` |
| Pale | `#E3EAF0` | `--color-pale` |
| Background | `#F7F9FB` | `--color-background` |
| White | `#FFFFFF` | `--color-white` |

This replaces the previously documented teal/coral palette, which is obsolete
as the v0.6 brand source of truth.

Usage direction follows the existing website:

- `Navy` provides the primary identity, text and primary action surfaces;
- `Blue` provides the brand accent;
- `Pale` provides pale surfaces and dividers;
- `Background` provides the page background;
- `White` provides light surfaces and reversed content.

The application should centralize these values in reusable frontend tokens.
Color combinations must preserve readable contrast; functional sailing,
telemetry and status colors remain independent from decorative brand colors.

### 8.4 Official logo

The existing SVG family in `maxsail-project/tackbar-web/assets/logo/` is the
official source logo system. v0.6 reuses this artwork rather than commissioning,
redrawing or inventing a new logo system.

The source assets include:

- logo/lockup: `tackbar-logo.svg`;
- wordmark: `tackbar-wordmark.svg` and `tackbar-wordmark-inverted.svg`;
- compact mark: `tackbar-mark.svg` and `tackbar-mark-inverted.svg`;
- claim/tagline: `tackbar-claim.svg`, `tackbar-claim-inverted.svg`,
  `tackbar-logo-claim.svg` and `tackbar-logo-claim-inverted.svg`.

Use the appropriate existing variant for the surface and available space,
preserving legibility at small sizes. Favicon/app-icon or raster derivatives,
where needed, must come from this SVG source family and preserve its artwork.

### 8.5 Application visual consistency

v0.6.0 should progressively apply the canonical `tackbar-web` identity to
Personal TackBar and existing public-facing TackBar UI through small, focused
increments. Brand consolidation MUST NOT trigger a full frontend redesign.

The priority is:

- shared color tokens;
- logo/wordmark usage;
- consistent typography hierarchy;
- consistent surfaces/buttons/links;
- preserving existing mobile-first usability;
- avoiding visual regressions in the Session Viewer and Admin.

Functional sailing colors that encode track comparison, telemetry or status
remain independent from, and distinguishable from, decorative brand usage.
Consolidation must preserve readable contrast, outdoor readability, mobile/tablet
usability, visible focus states and existing touch-target sizing.

### 8.6 Public website consistency

`tackbar-web` is the source visual reference for the shared product name,
official SVG logo family, core palette and preferred tagline. The application
adopts this identity progressively.

The application may copy the required SVG assets into its own frontend asset
tree. Visual consistency MUST NOT require architectural or runtime coupling
between the repositories; the application must not depend on the website to
serve its branding assets at runtime.

Real sailing photography and real product screenshots are preferred over generic SaaS-style illustration when marketing material is added.

## 8. Licensing

### 9.1 MPL 2.0 from v0.6.0

v0.6.0 marks the transition of TackBar's own public source code to:

```text
Mozilla Public License 2.0
SPDX-License-Identifier: MPL-2.0
```

The goal is to keep TackBar open to collaboration, forks and commercial use while applying MPL's file-level copyleft to covered source files.

### 9.2 Repository scope

The intended project-wide transition covers:

```text
maxsail-project/tackbar
maxsail-project/tackbar-web
```

Both move to MPL-2.0 as part of the v0.6.0 transition.

### 9.3 Provenance review before relicensing

Before changing license files, the project must review:

- current source provenance;
- external/third-party copied or vendored code;
- existing copyright notices;
- third-party licenses;
- prior external contributions, if any.

TackBar must not relicense third-party material it does not have the right to relicense.

Applicable third-party notices remain intact.

### 9.4 Historical MIT versions remain MIT

Previously distributed versions remain available under the MIT grants under which they were released.

v0.6.0 does not:

- revoke historical MIT permissions;
- rewrite old tags;
- rewrite old releases;
- rewrite repository history to pretend earlier versions were MPL.

### 9.5 Code license is not a data license

MPL applies to covered public source code.

It does not make the following open data:

- pilot participant data;
- email addresses;
- real GPS tracks;
- private originals;
- private runtime metadata;
- production/pilot data directories.

## 9. Explicit non-goals for v0.6.0

v0.6.0 does not require:

- Sailor username/password login;
- third-party authentication;
- editable Sailor profiles;
- web track upload;
- My Activities / standalone personal Activity access;
- a standalone Activity Viewer or duplicated personal Session Viewer;
- web consent flow;
- automatic consent-reply interpretation;
- automatic outbound email;
- automatic scheduled mailbox polling;
- canonical post-normalization track fingerprinting or logical track deduplication
  beyond the existing raw attachment SHA-256 behavior;
- physical Activity/track deletion;
- GPX ingestion;
- VKX ingestion;
- FIT ingestion;
- Garmin Connect;
- direct Vakaros cloud integration;
- QR Session sharing;
- Saved Analysis Segments;
- advanced maneuver detection;
- new advanced sailing analytics;
- Session matching redesign;
- database migration;
- complete frontend redesign;
- elaborate design-system infrastructure.

## 10. Relationship to v0.7.0

v0.6.0 demonstrates independence from email provider while preserving the
current downstream ingestion, normalization, Activity, Session and Viewer
semantics.

Canonical post-normalization track fingerprinting is intentionally deferred from
v0.6.0 to v0.7.0 so that its identity contract can be designed together with
multi-format track normalization rather than being frozen around the current
single-format baseline.

v0.7.0 extends the ingestion boundary to file-format independence.

The agreed implementation/validation order remains:

```text
1. GPX
2. VKX
3. FIT
```

All supported formats must converge on the same TackBar canonical track
representation and existing Activity → Session → Viewer flow.

As part of v0.7.0, TackBar will define the minimum canonical normalized data
needed for logical duplicate detection and then decide the deterministic
fingerprint/hash contract. SOG and COG are expected to be part of the minimum
navigation baseline; HEEL and TRIM remain optional when unavailable from the
source. Existing TackBar semantics that prohibit inventing missing sensor values
and prohibit deriving HDG from COG remain unchanged unless a separate explicit
decision changes them.
