# TackBar v0.6.1 — OVH Mailbox Ingestion Requirements

**Status:** Approved scope  
**Scope:** replace the operational Gmail mailbox with the TackBar OVHcloud mailbox for track ingestion  
**Baseline:** TackBar v0.6.0 Mahon — Pilot Operations  
**Decision source:** `docs/v0.6.1-decisions.md`

---

## 1. Relationship to v0.6.0

v0.6.1 is a focused operational follow-up to the delivered v0.6.0 pilot.

It promotes the previously deferred OVHcloud mailbox work into a concrete release without reopening unrelated v0.6.0 product decisions.

Unless explicitly overridden here, v0.6.1 MUST preserve:

- Sailor → Activity → Session;
- Activity as one received track;
- normalized sender email as the current external Sailor identity for email ingestion;
- current parsing and normalization behavior for supported Vakaros CSV/CSV.GZ attachments;
- current raw attachment SHA-256 exact-file deduplication behavior;
- current Session matching;
- current consent lifecycle and ACTIVE-only shared visibility;
- current Personal TackBar behavior;
- current Session capability, expiration and renewal semantics;
- current Admin ingestion disposition, Discard/Restore and reprocess behavior;
- current JSON metadata + filesystem persistence;
- current Session Viewer semantics and frontend behavior.

v0.6.1 MUST NOT introduce provider-specific Activity, Session, Sailor, consent or Viewer semantics.

---

## 2. Release objective

### V6.1-OBJ-01 — Operational mailbox replacement

TackBar v0.6.1 MUST support `share@tackbar.eu` as the operational track-sharing mailbox, hosted on OVHcloud Zimbra and accessed from the TackBar backend through IMAP over TLS.

The validated production connection profile is:

```text
protocol: IMAP over TLS
host: imap.mail.ovh.net
port: 993
mailbox: share@tackbar.eu
```

Credentials MUST be runtime configuration and MUST NOT be committed to the repository.

### V6.1-OBJ-02 — Remove Gmail OAuth as a production ingestion dependency

The production ingestion path MUST NOT require Gmail OAuth credentials or Gmail refresh-token renewal once OVHcloud ingestion is enabled.

The existing Gmail adapter MAY remain in the codebase for compatibility, rollback or local comparison, but production mailbox review for this release MUST use the configured OVHcloud mailbox.

v0.6.1 does not require simultaneous Gmail + OVHcloud ingestion.

### V6.1-OBJ-03 — Preserve the common ingestion pipeline

OVHcloud acquisition MUST produce the existing provider-independent `InboundEmail` boundary and then reuse the current downstream ingestion pipeline.

Conceptually:

```text
OVHcloud Zimbra / IMAP
        ↓
OVH IMAP adapter
        ↓
InboundEmail
        ↓
existing ingestion processing
        ↓
Sailor → Activity → Session → existing Viewer
```

The release MUST NOT duplicate parsing, normalization, Activity creation, Session matching or Viewer logic inside the OVH adapter.

## 3. OVH IMAP adapter behavior

### V6.1-ING-01 — Secure IMAP connection

The OVH adapter MUST connect using IMAP over TLS to the configured host and port.

Authentication MUST be non-interactive and suitable for the production VPS.

The mailbox password MUST be supplied through runtime configuration and MUST NOT be written to source code, tests, logs or versioned configuration.

### V6.1-ING-02 — Candidate message extraction

The OVH adapter MUST expose candidate messages through the existing `InboundEmail` model:

- `sender_email`;
- `subject`;
- `attachment_filename`;
- `attachment_bytes`;
- `provider_message_id`;
- `received_at`.

Candidate selection MUST preserve the current supported Vakaros CSV/CSV.GZ behavior. v0.6.1 MUST NOT expand source-file-format scope.

A message containing multiple supported attachments MUST continue to be rejected rather than silently creating ambiguous multiple Activities from one provider message.

### V6.1-ING-03 — Sender identity is unchanged

The outer message sender remains the email identity used for Sailor resolution.

v0.6.1 MUST NOT add forwarded-message header recovery, sender impersonation rules or manual sender remapping.

Therefore, pilot tracks intended to belong to a specific Sailor must arrive at `share@tackbar.eu` from that Sailor's email identity under the existing rules. A normal forward performed by another person changes the outer sender and is not equivalent to the original Sailor sending the track.

### V6.1-ING-04 — Stable provider message identity

OVH ingestion MUST persist a provider identity distinct from Gmail.

The IMAP message identity used for `provider_message_id` MUST be deterministic for the mailbox and robust against ordinary reconnects. The baseline identity is the mailbox `UIDVALIDITY` combined with the message `UID`.

The exact serialized separator is an implementation detail, but both values MUST participate in the identity.

The RFC `Message-ID` header MAY be retained for diagnostics if useful, but MUST NOT replace the IMAP UID identity contract because it may be absent, duplicated or preserved across forwards.

### V6.1-ING-05 — Remote mailbox flags are not TackBar state

Remote IMAP flags such as `Seen` or `Unread` MUST NOT become TackBar's processing source of truth.

TackBar MUST continue to use its own ingestion history for processed/failed state, retries, deduplication and administrative disposition.

Mailbox reads SHOULD avoid unnecessary remote-state mutation.

## 4. Mailbox review integration

### V6.1-REV-01 — One configured provider per review

The existing Admin-triggered mailbox review remains the operational model.

A review run MUST use the configured mailbox provider and provider identity rather than hard-coded Gmail behavior.

Production v0.6.1 MUST select the OVH IMAP provider.

### V6.1-REV-02 — Provider-independent deduplication boundary

Provider-message deduplication MUST continue to use the pair:

```text
provider + provider_message_id
```

The OVH provider identity MUST not collide with existing Gmail ingestion records.

Existing raw attachment SHA-256 behavior MUST remain unchanged.

### V6.1-REV-03 — Existing processing semantics remain unchanged

After a candidate becomes `InboundEmail`, the existing Sailor resolution, original preservation, parsing, normalization, Activity persistence, Session matching, ingestion history and Admin semantics MUST remain unchanged.

No OVH-specific downstream branch is permitted unless explicitly required by a later decision.

### V6.1-REV-04 — Failure handling

Provider connection/authentication failures MUST surface as mailbox-review failures without corrupting ingestion state.

Public/Admin error responses MUST remain safe and MUST NOT expose mailbox credentials.

Provider-specific diagnostics MAY be logged server-side when they do not include secrets.

---

## 5. Consent and outbound email

### V6.1-CNS-01 — Consent workflow is unchanged

v0.6.1 MUST NOT redesign consent.

The current human-operated consent workflow associated with the MaxSail Project remains unchanged for this stage.

`share@tackbar.eu` is the track-sharing ingestion address; it is not introduced as a new consent identity or outbound-mail system.

### V6.1-CNS-02 — No outbound mail scope

v0.6.1 MUST NOT introduce automatic outbound email, SMTP sending, automatic consent replies or a new `info@tackbar.eu` mailbox.

Those remain separate future decisions.

---

## 6. Production migration

### V6.1-MIG-01 — Clean pilot restart is allowed

For the current small pilot, production runtime data MAY be reset once as part of the human-controlled v0.6.1 migration.

No application-level data-migration feature is required to preserve the current pilot dataset.

This one-time operational reset MUST NOT be interpreted as a general TackBar data-deletion capability.

### V6.1-MIG-02 — Reset boundary

If the production reset is performed, it MUST target only TackBar runtime pilot data intended for replacement.

It MUST NOT delete or overwrite:

- application source code;
- systemd configuration;
- reverse-proxy configuration;
- TLS/domain configuration;
- unrelated server data;
- repository history.

Runtime secrets/configuration MUST be handled separately from pilot data.

### V6.1-MIG-03 — Human-controlled cutover

The cutover MUST remain an explicit operator action.

The migration sequence SHOULD be:

```text
implement + focused tests
→ local/controlled OVH ingestion validation
→ production runtime configuration
→ optional clean pilot-data reset
→ backend restart if required
→ real message to share@tackbar.eu
→ Admin mailbox review
→ Activity + Session + Viewer validation
```

Gmail production ingestion SHOULD only be considered retired after this end-to-end OVH validation passes.

---

## 7. Explicit non-goals

v0.6.1 does not include:

- simultaneous multi-provider polling;
- automatic mailbox polling/scheduling;
- outbound SMTP/email automation;
- `info@tackbar.eu`;
- consent redesign;
- forwarded-message sender reconstruction;
- GPX, VKX or FIT ingestion;
- canonical post-normalization track fingerprinting;
- Activity or Session semantic changes;
- physical data-deletion product workflows;
- database migration;
- Admin redesign;
- Session Viewer changes;
- advanced sailing analytics.

---

## 8. Acceptance criteria

v0.6.1 is acceptable when all of the following are true:

1. The backend can connect non-interactively from the production VPS to `imap.mail.ovh.net:993` using runtime-configured credentials.
2. A real email sent to `share@tackbar.eu` with one supported Vakaros attachment is exposed as one valid `InboundEmail`.
3. Sender, subject, receive time, filename and attachment bytes are preserved correctly.
4. Provider-message identity uses the OVH provider plus deterministic IMAP UID identity and repeated mailbox review does not create a duplicate ingestion for the same message.
5. The existing raw attachment SHA-256 behavior remains unchanged.
6. The message proceeds through the existing Sailor → Activity → Session pipeline without provider-specific domain behavior.
7. Existing consent, ACTIVE-only shared visibility, Personal TackBar, Session capability/lifetime and Viewer semantics remain unchanged.
8. Admin-triggered mailbox review works with OVH in production.
9. Production ingestion no longer depends on Gmail OAuth token renewal once OVH is selected.
10. Focused regression tests cover the OVH adapter, provider selection, provider-message deduplication and the common ingestion path.

---

## 9. Validation strategy

**Impact:** Medium  
**Recommended Codex model:** GPT-5.6 Sol / Medium  
**Test strategy:** targeted backend regression covering adapter extraction, mailbox-review provider selection, provider-message identity/deduplication and common ingestion integration  
**Full regression:** deferred to a separate release-validation gate after implementation and manual real-mail validation

Manual validation MUST include at least one real message received by `share@tackbar.eu` and processed end-to-end through Admin into the existing Activity/Session/Viewer flow.
