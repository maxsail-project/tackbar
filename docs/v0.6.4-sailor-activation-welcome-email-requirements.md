# TackBar v0.6.4 — Sailor Activation Welcome Email Requirements

**Status:** Proposed requirements based on closed product decisions  
**Scope:** complete the Sailor activation flow with one operational welcome email and Admin resend support  
**Baseline:** TackBar v0.6.3 — Usability & Maintenance  
**Decision source:** `docs/v0.6.4-decisions.md`

---

## 1. Relationship to v0.6.3

v0.6.4 is a focused operational follow-up. It promotes one outbound-email use
case deliberately excluded from v0.6.1 without reopening established product
semantics. Unless explicitly overridden, it preserves Sailor → Activity →
Session, normalized-email Sailor identity, PENDING / ACTIVE / REVOKED consent
and consent events, ACTIVE-only shared visibility, Session matching, Personal
TackBar, Session capability/expiration/renewal, OVH ingestion through
`share@tackbar.eu`, manual Admin mailbox review, Vakaros CSV/CSV.GZ ingestion,
JSON/filesystem persistence and current Session Viewer semantics.

The SailorDetail Session-history presentation fix committed after the published
v0.6.3 tag is included in the v0.6.4 package. It is a presentation fix, not a
second v0.6.4 product objective.

## 2. Release objective

### V6.4-OBJ-01 — Complete Sailor activation

After a successful Admin consent confirmation, TackBar MUST attempt one
operational welcome email to the activated Sailor.

### V6.4-OBJ-02 — Consent remains authoritative

SMTP success or failure MUST NOT determine whether consent is valid. A mail
failure MUST NOT revert ACTIVE consent or modify Session or Personal TackBar
capabilities.

### V6.4-OBJ-03 — Recoverable pilot operation

Admin MUST be able to inspect welcome-email delivery state and explicitly
resend the welcome email when the Sailor is eligible.

## 3. Activation sequence

The conceptual sequence is:

```text
confirm consent
→ persist ACTIVE Sailor
→ persist consent event
→ ensure Session capabilities
→ ensure Personal TackBar capability
→ attempt welcome email
```

An automatic attempt occurs only after a valid Admin PENDING → ACTIVE consent
confirmation. It MUST NOT be triggered by Admin refresh, reading Sailor data,
ingestion, Session creation, mailbox review or Personal TackBar access.
Explicit resend is a separate authenticated Admin operation.

## 4. SMTP transport and public URL configuration

### V6.4-OUT-01 — OVH SMTP baseline

The production baseline is authenticated OVHcloud SMTP from `share@tackbar.eu`
over SSL/TLS on expected port 465. Credentials are runtime configuration only.
The expected configuration boundary is equivalent to:

```text
TACKBAR_OVH_SMTP_HOST
TACKBAR_OVH_SMTP_PORT
TACKBAR_OVH_SMTP_USERNAME
TACKBAR_OVH_SMTP_PASSWORD
TACKBAR_OVH_SMTP_FROM
```

SMTP configuration MUST remain separate from existing IMAP configuration. This
does not require the SMTP password variable to reuse the IMAP password variable
even where production values are identical. SMTP remains infrastructure and
MUST NOT redefine Sailor, consent, Activity, Session or Viewer semantics.

### V6.4-OUT-02 — Public application origin

The public application URL MUST be runtime configuration equivalent to
`TACKBAR_PUBLIC_BASE_URL`, with expected production value
`https://app.tackbar.eu`. A Personal TackBar link MUST combine this configured
origin with the existing capability path. Externally shared URLs MUST NOT be
derived from untrusted request headers.

## 5. Recipient, content and format

### V6.4-MSG-01 — Recipient and subject

The recipient is the Sailor's persisted email. v0.6.4 provides no arbitrary
recipient override. Plain text is sufficient; no HTML or template framework is
required. The subject direction is `Welcome to TackBar / Bienvenido a TackBar`.

### V6.4-MSG-02 — One bilingual message

One email MUST contain English first and Spanish second. No language preference
or locale detection is introduced. Both sections MUST convey equivalent content:

- thank the Sailor for participating or confirming participation;
- instruct them to send tracks to `share@tackbar.eu`;
- name Vakaros Connect as the currently supported sharing workflow;
- include the appropriate Vakaros guide;
- include the Sailor's Personal TackBar URL and explain that existing
  availability rules apply; and
- advise keeping the personal URL private.

The canonical guide URLs are:

```text
English: https://tackbar.eu/share-vakaros/index.html
Spanish: https://tackbar.eu/es/compartir-vakaros/index.html
```

The message MUST NOT imply support for GPX, VKX, FIT or future sources.

## 6. Personal capability behavior

Automatic send and explicit resend MUST use the existing current Personal
TackBar capability. They MUST NOT regenerate it. Sending is not an
authorization or capability mutation. If an ACTIVE Sailor lacks usable personal
access, resend MUST NOT silently regenerate it. Existing explicit Admin
personal-capability controls remain authoritative.

## 7. Persisted delivery state

Sailor-level operational delivery state MUST determine whether a welcome email
was successfully sent, the latest successful submission time, whether the
latest attempt failed and a safe current failure indication. Fields may be
equivalent to `welcome_email_sent_at` and `welcome_email_last_error`; exact
names are implementation details.

A successful timestamp means SMTP-server acceptance, not guaranteed inbox
delivery or read. A complete message-delivery history is not required. Failure
state MUST NOT include SMTP credentials, Personal TackBar tokens,
authentication payloads or other secrets.

## 8. Admin behavior and failure handling

Admin Sailor detail MUST show delivery state separate from consent, equivalent
to `Not sent`, `Sent <timestamp>` or `Failed`. It MUST offer **Resend welcome
email** only when the Sailor is ACTIVE and has a current usable Personal TackBar
capability.

Resend MUST use the persisted Sailor email, current capability, bilingual
content and canonical guide URLs; update delivery state; and preserve
consent/capability/Activity/Session semantics. There is no automatic retry.
An SMTP failure after activation MUST leave the Sailor ACTIVE. Admin must make
clear that activation succeeded while welcome-email delivery failed.

## 9. Architecture and API

The smallest coherent service boundary is:

```text
welcome-email composition → outbound-mail abstraction → OVH SMTP transport
```

Composition MUST be testable without a real SMTP server. The pilot may send
synchronously after consent confirmation. v0.6.4 MUST NOT introduce queues,
workers, Celery, Redis, scheduled retries or transactional-email SaaS.

The existing consent-confirmation endpoint retains its domain-transition
purpose. The Admin Sailor representation may expose delivery state, and a
dedicated authenticated Admin resend operation is required. No public resend
endpoint is permitted.

## 10. Tests and validation

Focused implementation tests MUST cover:

- valid PENDING → ACTIVE consent, unchanged capability semantics, one automatic
  send attempt, no send for invalid transitions, and SMTP failure that does not
  roll back ACTIVE or change personal access;
- email composition with `share@tackbar.eu`, both guide URLs, English and
  Spanish content, an absolute Personal TackBar URL and a privacy instruction,
  without real SMTP dependency;
- resend eligibility, persisted recipient/current capability use, no implicit
  regeneration, successful state update and failed-resend preservation of
  consent/access;
- SMTP host/port, SSL/TLS, authenticated sender, successful submission,
  controlled secret-safe errors; and
- Admin delivery-state presentation, resend eligibility, refresh after resend,
  controlled failure and unchanged consent/Personal TackBar controls.

Later manual production validation MUST prove:

```text
Admin confirm consent → ACTIVE → personal capability usable
→ email received from share@tackbar.eu → EN guide works → ES guide works
→ Personal TackBar link works → explicit resend works
```

Production validation is not completed or claimed by this requirements document.

## 11. Explicit non-goals

v0.6.4 does not add automatic consent-request email, invitation campaigns,
automatic consent-reply processing, Activity processed or Session-ready
notifications, newsletters, language preferences, configurable templates, an
HTML requirement, delivery/open analytics, background retries, queues/workers,
third-party transactional-email service, mailbox polling, mailbox providers,
GPX/VKX/FIT, Session-matching or Viewer changes, or a Sailor account/login
system. Broader outbound email remains future scope.

## 12. Acceptance criteria

v0.6.4 is acceptable when:

1. A valid Admin consent confirmation activates the Sailor independently of SMTP.
2. Exactly one automatic welcome-email attempt follows that valid activation.
3. OVH SMTP and public-origin configuration are external runtime settings.
4. One plain-text English-and-Spanish message uses the canonical Vakaros URLs.
5. The Personal TackBar URL combines the configured origin and current capability.
6. Delivery state is persisted, safe and visible separately from consent.
7. An eligible Admin resend uses existing access without regeneration.
8. Delivery failure is recoverable and does not alter consent or access.
9. Existing Sailor, Activity, Session, ingestion, capability and Viewer behavior is preserved.
10. No messaging infrastructure or platform expansion is introduced.
