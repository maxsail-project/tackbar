# TackBar v0.5.0 — Decisiones consolidadas

**Estado:** Decisiones funcionales cerradas para preparar TackBar v0.5.0  
**Fecha:** 24 de agosto de 2026  
**Objetivo:** fijar las decisiones de producto, privacidad, operación y acceso debatidas para el Real Sailing Pilot, sin reabrir comportamiento ya validado en v0.4.x.

---

## 1. Regla de gobierno

TackBar v0.5.0 parte de la baseline funcional validada en v0.4.x.

No se revisa ni redefine una funcionalidad existente salvo que una decisión explícita de v0.5.0 la modifique.

Se mantienen, entre otros:

- el modelo Sailor → Activity → Session;
- Activity como un track recibido, sin inferir carrera/día/entrenamiento;
- el Session Viewer y sus semánticas validadas;
- Analysis Window compartida;
- replay y métricas ya entregadas;
- deduplicación existente;
- Session matching existente;
- persistencia JSON + filesystem como baseline PoC.

La regla actual de Session matching se mantiene sin cambios en v0.5.0: compatibilidad temporal de hasta 60 minutos y proximidad geográfica máxima de 3 NM, con selección determinista de Session. Cualquier revisión de esos umbrales deberá surgir del piloto real, no de rediseño previo.

---

## 2. Objetivo de v0.5.0

Validar un **Real Sailing Pilot** pequeño y controlado:

```text
invitación / consentimiento
        ↓
Sailor
        ↓
email con track
        ↓
ingesta controlada por admin
        ↓
Activity
        ↓
Session matching existente
        ↓
visibilidad según consentimiento
        ↓
capability URL
        ↓
debrief compartido
```

La prioridad es validar el flujo con regatistas reales, no automatizar completamente la operación.

---

## 3. Perímetro UE y RGPD para la PoC

### 3.1 Decisión

Para la PoC se exige residencia UE para:

- runtime TackBar;
- `TACKBAR_DATA_DIR`;
- tracks normalizados;
- originales recibidos;
- metadata personal;
- backups;
- logs que contengan datos personales.

No se exige soberanía integral de todo el stack. GitHub, CI, DNS, certificados o monitorización básica pueden quedar fuera de ese perímetro siempre que no reciban datos personales de runtime ni capability URLs privadas.

### 3.2 Gmail como excepción PoC

Gmail se acepta como excepción temporal para el canal de entrada/salida de correo.

Esto debe documentarse explícitamente: Gmail forma parte del tratamiento porque recibe email y adjuntos GPS, pero no será el repositorio operativo de TackBar.

### 3.3 Terreno gris

Para la PoC no se profundiza ahora en tiles/CDN u otros terceros de bajo impacto. Se revisarán si el piloto evoluciona a operación más formal.

---

## 4. Hosting y despliegue

### 4.1 v0.5.0 primero

v0.5.0 se desarrolla y valida primero sin introducir infraestructura compleja.

### 4.2 Prioridad posterior

Inmediatamente después de cerrar v0.5.0, la prioridad será publicar la PoC en un **VPS alojado en la UE**, con:

- dominio/subdominio público;
- HTTPS;
- frontend React;
- FastAPI;
- almacenamiento persistente TackBar.

El proveedor concreto de VPS se decidirá después de v0.5.0. Hetzner, OVHcloud y Scaleway permanecen como candidatos a evaluar.

---

## 5. Email como canal de producto

Compartir el track mediante email es una decisión de producto y **no es negociable para la PoC**.

Para v0.5.0 se mantiene Gmail como proveedor.

La arquitectura debe seguir manteniendo Gmail como adapter reemplazable, sin trasladar comportamiento específico del proveedor al dominio TackBar.

## 6. Consentimiento del Sailor

### 6.1 Estados

Cada Sailor tiene un estado actual de consentimiento:

- `PENDING` — amarillo;
- `ACTIVE` — verde;
- `REVOKED` — rojo.

### 6.2 Regla de visibilidad

Todas las Activities válidas pueden procesarse y asociarse técnicamente a Sessions con independencia del estado de consentimiento.

La regla compartida es:

```text
Activity visible / compartible ⇔ Sailor.consent_status == ACTIVE
```

El filtrado debe hacerse en backend. Una Activity PENDING o REVOKED no debe enviarse al navegador mediante las APIs compartidas.

### 6.3 Ciclo

Nuevo Sailor:

```text
nuevo → PENDING → ACTIVE si acepta
```

Rechazo o retirada:

```text
PENDING → REVOKED si rechaza participar antes de confirmar el consentimiento
ACTIVE → REVOKED
```

Reentrada posterior:

```text
REVOKED
   ↓ nuevo track / nueva participación
PENDING
   ↓ nueva aceptación
ACTIVE
```

REVOKED no es una exclusión permanente.

El estado `REVOKED` puede proceder tanto de un rechazo explícito mientras el
Sailor estaba `PENDING` como de la retirada de un consentimiento previamente
concedido. El historial distingue ambos casos mediante eventos diferentes; no
se introduce un cuarto estado de consentimiento.

### 6.4 Historial de consentimiento

Además del estado actual se conserva un historial mínimo estructurado de eventos, por ejemplo:

- solicitud de consentimiento;
- consentimiento confirmado;
- consentimiento rechazado antes de su confirmación;
- consentimiento retirado;
- nueva solicitud.

Cada evento debe tener al menos timestamp y origen.

No se necesita conservar en TackBar el contenido completo de cada correo para construir ese historial.

---

## 7. Flujo de consentimiento de v0.5.0

### 7.1 PoC asistida por administrador

La solución profesional con página web `/consent/<token>` queda fuera de v0.5.0.

Para la PoC:

1. el administrador envía desde Gmail una invitación/acuerdo;
2. el Sailor responde explícitamente aceptando;
3. el administrador revisa el correo en Gmail;
4. en TackBar Admin ejecuta **Confirmar consentimiento**;
5. TackBar registra automáticamente:
   - estado `ACTIVE`;
   - timestamp;
   - versión vigente del acuerdo;
   - origen `admin_confirmed_email` o equivalente;
6. desde ese momento sus Activities son visibles.

No se requiere que TackBar interprete automáticamente texto libre del correo en v0.5.0.

### 7.2 Versión del acuerdo

La versión vigente del acuerdo es configuración de TackBar, no un dato que el administrador introduzca manualmente en cada aceptación.

### 7.3 Pendientes de consentimiento

El sistema debe distinguir operativamente:

```text
PENDING + consent_request_sent_at = null
→ necesita solicitud de consentimiento

PENDING + consent_request_sent_at != null
→ solicitud enviada; esperando respuesta
```

Esto permite al administrador saber a quién debe escribir y quién está esperando respuesta.

Idealmente el consentimiento se pedirá antes de recibir tracks, pero el modelo debe soportar que el primer track llegue antes.

## 8. Ingesta Gmail de v0.5.0

### 8.1 Operación manual

La ingesta automática periódica deja de ser requisito de v0.5.0.

Para la PoC, solo el administrador lanza la revisión del buzón desde:

- `/admin` mediante **Revisar buzón**;
- script backend equivalente como mecanismo de respaldo.

Ambas vías deben reutilizar el mismo servicio backend de ingesta.

### 8.2 `unread`

El estado `unread` de Gmail no gobierna el procesamiento TackBar.

TackBar mantiene su propio registro de ingesta.

### 8.3 Reproceso

El sistema debe conservar suficiente información para saber:

- qué mensaje se recibió;
- qué adjunto contenía;
- dónde se conserva el original;
- si se procesó o falló;
- qué Activity produjo;
- qué Session resultó;
- cuántos intentos se hicieron;
- cuál fue el último error.

El reproceso debe ser idempotente: no debe duplicar Activities, Sessions ni efectos ya realizados.

### 8.4 Concurrencia

Solo una ejecución de ingesta puede modificar la persistencia a la vez.

En v0.5.0 esto se simplifica por la operación manual. Cuando se automatice, deberá existir lock/exclusión explícita.

### 8.5 Email saliente

Para v0.5.0 no se exige automatizar los correos salientes.

El administrador puede utilizar Gmail para:

- enviar la solicitud/acuerdo de consentimiento;
- responder con el enlace de Session cuando corresponda.

La automatización de estos correos queda en backlog posterior.

---

## 9. Datos operativos consultables

### 9.1 Sailor

`sailors.json` o su repositorio equivalente debe permitir consultar el estado actual del consentimiento.

Conceptualmente deben estar disponibles datos equivalentes a:

- `consent_status`;
- `consent_request_sent_at`;
- `consent_granted_at`;
- `consent_revoked_at`.

La forma exacta debe mantenerse simple y coherente con el modelo JSON actual.

### 9.2 Historial de consentimiento

Se mantiene separado del historial de ingesta para no mezclar responsabilidades.

### 9.3 Ingestion history

El historial de ingesta responde a:

> ¿Tengo procesado este correo/track?

El estado del Sailor responde a:

> ¿Puedo compartir sus Activities?

### 9.4 Consulta y modificación

Para la PoC:

- los JSON pueden inspeccionarse directamente para diagnóstico;
- scripts backend pueden listar Sailors pendientes;
- `/admin` será la interfaz operativa principal;
- las modificaciones no deben realizarse editando JSON manualmente como procedimiento normal.

---

## 10. Backoffice/Admin

### 10.1 Alcance

Se crea una zona `/admin` deliberadamente simple.

Solo el administrador de la PoC necesita acceso.

### 10.2 Protección

La PoC utilizará una única credencial administrativa/configuración secreta, sin introducir un sistema complejo de usuarios y roles.

### 10.3 Capacidades

El Admin debe permitir como mínimo:

- consultar Sailors;
- identificar PENDING que necesitan solicitud;
- identificar PENDING esperando respuesta;
- confirmar consentimiento;
- registrar retirada de consentimiento;
- consultar historial mínimo de consentimiento;
- revisar buzón ahora;
- consultar ingestas, errores y estado;
- reprocesar una ingesta;
- consultar Sessions;
- conocer Activities internas y visibles;
- consultar caducidad;
- renovar explícitamente la vigencia de una Session;
- consultar/copiar capability URL;
- regenerar/revocar capability URL cuando sea necesario.

Las acciones de consentimiento deben ser semánticas (`Confirmar consentimiento`, `Registrar retirada`) y generar trazabilidad automática; no deben ser edición arbitraria del estado.

### 10.4 Scripts

Las operaciones administrativas relevantes deben existir como servicios backend reutilizables y, cuando sea útil, poder invocarse también desde scripts.

La UI Admin no debe duplicar reglas de dominio.

## 11. Capability URL y acceso a Sessions

### 11.1 Sin login de Sailor

Para la PoC no hay login ni identificación de Sailor al abrir una Session.

La posesión del enlace equivale a autorización para acceder a la Session compartida.

### 11.2 Token separado

La capability URL utiliza un token público aleatorio y no el `session_id` interno como credencial.

Ejemplo conceptual:

```text
/s/<access-token>
```

### 11.3 Creación

Una Session puede existir internamente con Activities no visibles.

El capability token se genera cuando la Session dispone por primera vez de al menos una Activity perteneciente a un Sailor `ACTIVE`.

### 11.4 Visibilidad

Resolver el token debe devolver únicamente Activities de Sailors `ACTIVE`.

### 11.5 Compartición

Compartir el enlace equivale a compartir acceso. Para esta PoC se acepta conscientemente este modelo.

### 11.6 Regeneración

El administrador puede revocar/regenerar el token. El token anterior deja de ser válido.

---

## 12. Session viva y caducidad

### 12.1 Session viva

Una Session puede recibir Activities compatibles horas o días después de su creación, según el Session matching existente.

La fecha de recepción del email no determina el matching; lo hacen los datos temporales/geográficos de la Activity.

Esta capacidad continúa después de `expires_at`: la caducidad cierra el acceso compartido, no la membresía técnica de la Session. Por tanto, `Session.activity_ids` puede seguir creciendo con Activities compatibles sin cambiar los umbrales ni la selección del Session matching existente.

### 12.2 Caducidad PoC

Cada Session debe incorporar:

- `created_at`;
- `expires_at`.

Para la creación inicial en v0.5.0:

```text
expires_at = created_at + 60 días
```

La capability URL es estable durante la vigencia de la Session.

### 12.3 Efecto

Cuando la Session caduca:

- deja de ser accesible mediante capability URL;
- no implica borrar automáticamente Activities o tracks;
- puede seguir recibiendo internamente Activities compatibles;
- una nueva Activity no reactiva el acceso compartido ni crea o rota una capability;
- la caducidad de acceso y la retención de datos son conceptos diferentes.

La duración de Session se considera una decisión PoC y puede convertirse posteriormente en una variable de producto/monetización.

v0.5 incorpora la renovación administrativa como operación explícita para
reabrir el acceso compartido. La renovación sustituye `expires_at` por la hora
UTC actual más 30 días por defecto, o por una duración explícita positiva de
hasta 365 días; no suma tiempo a la caducidad anterior.

La operación conserva `created_at`, `activity_ids`, el capability token y su
estado de revocación. Por ello, un token existente y no revocado vuelve a ser
utilizable tras renovar una Session expirada si contiene Activities visibles de
Sailors `ACTIVE`. Un token revocado sigue revocado y una Session que nunca tuvo
token sigue sin él. Renovar no crea, rota, regenera ni desrevoca una capability;
la regeneración posterior continúa siendo una acción administrativa separada.

No existe renovación automática por matching de una nueva Activity, cambio de
un Sailor a `ACTIVE`, regeneración de capability ni lectura de la Session.

## 13. Conservación de Activities

El valor de TackBar incluye el histórico de navegación y el procesamiento/análisis de Activities.

Para la PoC:

- las Activities de un Sailor `ACTIVE` se conservan internamente;
- la expiración de una Session compartida no elimina esas Activities;
- si un Sailor retira consentimiento, sus Activities dejan inmediatamente de compartirse;
- la eliminación/anonimización posterior se tratará mediante una política de mantenimiento más madura cuando el producto lo necesite.

Las condiciones de participación deben explicar de forma sencilla que TackBar conserva y procesa Activities para prestar el servicio, mantener histórico y desarrollar capacidades de análisis, evitando formulaciones de “propiedad para siempre”.

El acceso administrativo a datos personales se limita a operación, soporte, mantenimiento, reproceso y gestión del consentimiento.

---

## 14. QR

El QR es una mejora importante para compartir una Session en una mesa de debrief, pero no es requisito de v0.5.0.

Cuando se implemente:

- usará exactamente la misma capability URL;
- no introducirá un segundo token ni mecanismo de autorización.

---

## 15. Futuro cercano: Mi TackBar

Se registra como evolución cercana, fuera de v0.5.0.

Cada Sailor `ACTIVE` podrá disponer de una URL personal estable con listado de sus Activities.

Ejemplo:

```text
Mi TackBar
└── Mis actividades
    ├── Activity 1 → Session A [Abrir]
    ├── Activity 2 → Sin Session activa
    └── Activity 3 → Session expired
```

Características decididas:

- la URL personal del Sailor es estable;
- nuevas Activities se añaden automáticamente al listado;
- las Activities personales no caducan mientras el Sailor permanezca ACTIVE;
- si una Activity pertenece a una Session todavía activa, se muestra su enlace;
- si la Session ha caducado, se muestra `Session expired`.

No se crea un bloque separado de “Sessions activas”; la relación se muestra desde cada Activity.

---

## 16. Soluciones deliberadamente diferidas

No forman parte de v0.5.0:

- consentimiento web mediante `/consent/<token>`;
- interpretación automática de respuestas de consentimiento;
- envío automático de correos;
- polling Gmail periódico/desatendido;
- Gmail History API u otra estrategia incremental sofisticada;
- QR;
- Mi TackBar / histórico personal visible;
- monetización;
- políticas avanzadas de borrado/anonimización;
- proveedor de correo alternativo;
- sistema completo de autenticación/roles;
- migración de persistencia a base de datos;
- cambios al Session matching existente salvo evidencia del piloto.

---

## 17. Relación con documentación anterior

Este documento complementa la baseline entregada de v0.4.x.

Las decisiones de despliegue anteriores que asumían una demo exclusivamente TEST/read-only, Gmail desactivado inicialmente o una allowlist como mecanismo principal de autorización quedan superadas para el Real Sailing Pilot v0.5.0.

El acceso real pasa a gobernarse por:

```text
consentimiento del Sailor
        +
visibilidad backend ACTIVE-only
        +
capability URL de Session
```
