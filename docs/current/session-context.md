# Session Context

This specification owns accepted Session geographic and historical-conditions context. [The index](index.md) defines the documentation route.

## Current contract

### Session-owned geographic context

- Geographic context is optional descriptive data owned by the Session. The Activity that created the Session supplies its persisted start latitude and longitude for a Geoapify reverse lookup through a replaceable provider boundary; later match-time city completion and Admin **Enrich Session** may use other member Activities' start coordinates as described under [Enrichment lifecycle and maintenance](#enrichment-lifecycle-and-maintenance). Location does not affect Activity identity, Session membership or matching.
- The normal reverse lookup uses the first result without a city-type filter. It normalizes available `city`, `state`, `country` and `country_code` into `location_label`, `location_region`, `location_country` and `location_country_code` respectively. A city is not required: any non-empty supported field makes the result usable, while a result with none of those fields supplies no geographic context. `location_label` retains its city-only meaning.
- A successful lookup persists only those normalized fields plus `location_provider`, UTC `location_resolved_at` and `location_source_activity_id`. Precise addresses, coordinates beyond the existing Activity source context, new geographic fields, full provider responses and provider credentials are not Session data.
- A missing provider configuration, failed lookup or unsuitable result leaves the Session usable without geographic context. Normal Session reads use persisted data and make no geocoding request.

### Historical weather and marine context

- Optional Session-owned conditions are **historical/modelled context**. They are neither onboard measurements nor substitutes for missing Activity sensors. Persisted modelled wind direction may supply the Session Viewer's time-aware TWD map orientation, while current maneuver detection, metrics, classification and replay do not consume it. Separately approved future TWD-dependent analytics may use original source-aware evidence under their own eligibility rules.
- A persisted series can contain hourly air temperature (°C), optional Open-Meteo WMO `weather_code` as an integer, 10 m wind speed and gusts (kt), 10 m wind direction (degrees), cloud cover (%), wave height (m), wave direction (degrees) and wave period (s). Missing values remain unavailable; weather codes are never inferred from cloud cover. Existing Session records without `weather_code` remain readable with that field unavailable. Atmospheric and marine sources may succeed independently; a partial series is valid.
- The requested coverage is the current Session sailing interval, from the earliest member Activity start through the latest member Activity end, expanded by three hours at both ends. TackBar persists that exact requested interval, the requested coordinate, available hourly samples, and separate weather and marine provenance: provider, route/dataset, retrieval time and returned grid coordinate. Coverage metadata is the *requested* interval; it does not promise an observation at every hour or that both sources returned data.
- The requested coordinate is the derived Session center, with the creator Activity's start coordinate as an exceptional fallback when that center cannot be derived. It is distinct from the coordinate used for the geographic lookup and from each provider's returned grid coordinate.
- Open-Meteo supplies the current modelled series through a replaceable historical-conditions provider boundary. Recent atmospheric requests use Forecast; older requests outside the 92-day archived-forecast window use Historical Weather. Recent marine requests use best-match routing; older requests use ERA5-Ocean. Requests use GMT and sea-cell selection, with one request per source for the complete interval. TackBar retains only returned hourly values within the requested interval and does not fabricate denser samples.
- Provider failure, missing data or partial availability does not block the Session or its Viewer. Normal reads use persisted conditions and do not request weather or marine data.

### Enrichment lifecycle and maintenance

- After authoritative Activity persistence and creation of a **new** Session, TackBar attempts geographic, atmospheric and marine enrichment as best-effort secondary work. Failure or unavailability in one source does not prevent the others and cannot roll back ingestion or Session creation.
- When a later Activity is matched into an existing Session whose persisted city (`location_label`) is blank, including a Session with no geographic context, TackBar attempts one best-effort geographic completion from that newly matched Activity's persisted start latitude and longitude. A Session that already has a city makes no geocoding request; a missing region alone does not trigger a lookup. The result is accepted only if it has a nonblank city, retains a nonblank value for every currently populated geographic field and does not change any currently populated value (trimmed, case-insensitive comparison); otherwise it is discarded, so a different country or a city-less result leaves the Session unchanged. Before persistence, the rule is checked against the latest persisted Session. An accepted result replaces all four geographic fields and their provider, UTC resolution time and source Activity ID, set to the matched Activity, as one snapshot. No `ACTIVE` consent is required for the matched Activity's coordinate. Provider absence, failure or an unusable result does not affect ingestion, persistence or Session membership.
- Apart from that additive city completion, matching a later Activity into an existing Session does not call context providers, request conditions, check persisted coverage, mark context stale or automatically refresh or correct context. Persisted context can therefore predate the Session's later expanded membership.
- Admin **Enrich Session** is an explicit, one-Session-at-a-time maintenance action. Every invocation attempts geography, including when context already exists. An initially empty Session accepts any usable normalized result. With existing context, a result is accepted only if it retains a nonblank value for every currently populated geographic field type; it may add missing fields or correct existing values. Before persistence, the rule is checked against the latest persisted Session. An accepted result replaces all four geographic fields and their provider, UTC resolution time and source Activity ID as one snapshot. The creator Activity's persisted start coordinate is looked up first. If its result is not accepted with a nonblank city, the remaining member Activities' persisted start coordinates are tried in persisted `activity_ids` order, at most one lookup per member Activity per invocation, and the first result accepted under the same rule with a nonblank city is persisted, with the source Activity ID set to the Activity whose coordinate produced it. A failed, unusable or rejected candidate, or a missing member Activity record, moves on to the next member; no `ACTIVE` consent is required for member coordinates. If no member yields an accepted result with a city, the creator result is applied under the same rule, so the outcome equals creator-only refresh. At most one snapshot is persisted per invocation, and a missing provider configuration makes no lookup. An unavailable, failed, unusable or incomplete result preserves the prior snapshot. The action also requests conditions for the complete *current* Session interval plus three hours at each end; a successful result replaces the prior conditions series atomically. Failure or no usable result preserves the previous series. Geography and conditions refresh independently. This action supports older Sessions, missing conditions context and Sessions whose membership later expanded.
- Automatic new-Session geography enrichment remains missing-only; matching a later Activity triggers only the additive city completion above, never a refresh or correction of existing values. Context enrichment does not create a bulk job or manual location override. [Domain and Sessions](domain-and-sessions.md) owns matching, membership and lifetime; [Ingestion and Data](ingestion-and-data.md) owns authoritative Activity processing and persistence boundaries.

### Read and presentation boundary

- Permitted original and temporary shared Session reads expose the same persisted Session location and normalized hourly conditions. They expose minimal source identity for the series, not credentials or the Admin diagnostic payload. [Access and Consent](access-and-consent.md) owns which Session and Activities a caller may see; context adds no access path.
- Compact Session identity follows **City > Country > nothing**: a non-empty city is the sole location label; otherwise a non-empty country is the sole label; otherwise the existing date or date/time fallback remains. Region is never a compact display fallback. Admin applies the same rule to Session identity and search while keeping fuller persisted geographic and conditions provenance in Session details. Activity selectors retain Activity-specific identity. Detailed layouts belong in [Session Viewer](session-viewer.md), [Personal TackBar](personal-tackbar.md) and [Admin](admin.md).
- The Viewer and Personal TackBar read persisted Session conditions; their compact cues select observations for different temporal midpoints. Their respective display and selection rules belong in [Session Viewer](session-viewer.md#maneuver-interaction-and-session-context) and [Personal TackBar](personal-tackbar.md#session-recognition-and-search). Normal reads do not call context providers.

### Unresolved transition findings

1. **Low — requested coverage versus available samples.** The stored bounds describe the exact interval requested, while providers may return only some hours or one of the two source types. No complete-hourly-coverage guarantee is supported.

Session context does not change Session matching, consent, capability, Activity telemetry, analytics or Viewer replay rules.
