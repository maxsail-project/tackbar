# Access and Consent

This specification owns accepted consent, capability and shared-visibility rules. Its separately marked unresolved findings do not grant new access or settle missing product decisions. [The index](index.md) defines the documentation route.

The **Current contract** states access and consent rules. **Provenance and review** records their sources and evidence gaps; it does not create new authorization rules.

## Current contract

### Consent lifecycle and shared visibility

| Sailor state | Consent meaning and access consequence |
| --- | --- |
| `PENDING` | Consent has not been confirmed. Technical Activity ingestion and Session matching may proceed, but the Sailor's Activities are excluded from shared Session responses and Personal TackBar history is unavailable. A new Sailor without confirmed consent enters this state. |
| `ACTIVE` | Explicit consent has been confirmed. The Sailor's Activities may appear through otherwise valid shared Session access, and a valid personal capability may open Personal TackBar. |
| `REVOKED` | A pre-consent decline or withdrawal of earlier consent. The Sailor's Activities immediately cease to appear through shared Session access; personal access is unavailable. Stored Activities and Session membership are not automatically deleted. |

- Consent is a Sailor state, separate from whether a track was received, processed or matched. Declining while `PENDING` and withdrawing while `ACTIVE` both lead to `REVOKED`, with distinct consent events. A valid new track from a `REVOKED` Sailor starts a new `PENDING` cycle; it does not restore `ACTIVE` status.
- A grant requires an explicit affirmative web submission or controlled Admin confirmation of an explicit acceptance. Consent events retain the event type, time and source; a grant also records the applicable agreement version. An Admin confirmation uses the configured current version. A web grant uses the version bound to its request at issuance, preserving prior evidence if the configured version later changes.
- The backend evaluates current Sailor status for every shared Session read. Shared Session details, Activity tracks and Activity analytics expose only member Activities whose Sailors are `ACTIVE` at request time. A valid token with no visible Activities yields no shared Session response. Changing consent changes visibility without changing Session membership or automatically destroying an existing capability.

### Track-first web consent

- The normal pilot entry is a supported track sent to `share@tackbar.eu`. Successful technical processing can create or resolve a `PENDING` Sailor and associate the Activity with a Session. Track submission, opening a consent link and viewing participation conditions are not consent.
- For a qualifying `PENDING` cycle, TackBar makes at most one automatic consent-request delivery attempt after successful track processing. Later tracks, duplicate processing and routine reads do not repeat that automatic attempt. A controlled delivery failure leaves the Sailor `PENDING` and the request usable; recovery is an explicit Admin operation.
- The internal staged OVH attachment processor preserves the technical `PENDING` and `REVOKED` transitions and deterministic onboarding association, but it makes no automatic consent-request or Session-result delivery attempt on first processing or explicit Reprocess. The staged path remains outside the normal mailbox trigger until per-mail communication is integrated. The current ordinary one-file OVH path retains its existing delivery behavior.
- A consent-request token is a separate, non-guessable bearer capability for the consent decision only. An unaccepted request expires 28 days after issuance and cannot activate a Sailor at or after expiry. A request is bound to the current consent cycle and to its agreement version; an earlier cycle's token cannot authorize a later cycle. The current version for newly issued requests is `v0.6.5`.
- The TackBar application serves the token decision page at `/consent/<token>` and the bilingual, read-only conditions at `/consent/conditions`. The conditions page needs no token and has no consent action. The token page exposes only decision context, not private Sailor, Activity, Session or access details. Unknown, expired and otherwise unusable requests fail without disclosing those details.
- Only the affirmative acceptance action may perform `PENDING → ACTIVE`. Repeating an accepted submission must not duplicate the grant event or activation effects. Activation ensures the established Session and Personal TackBar capabilities and then attempts the welcome email. The web and manual paths use the same consent transition semantics.
- Admin may explicitly resend a still-valid request using its existing token, or reissue an expired request with a new token. An accepted request is not resent as pending. Sending or reissuing does not itself grant consent. Controlled manual confirmation remains the fallback when explicit acceptance has been verified outside the web flow.

### Manual-source consent and communication

- Admin upload initially requires an existing `ACTIVE` Sailor, checked by the backend at durable acceptance. It does not create a Sailor or grant consent. Accepted technical processing retains explicit ownership even if consent changes afterward; shared Session reads continue enforcing current `ACTIVE`-only visibility.
- Manual-source Reprocess preserves the original Sailor and source. A valid track for a now-`REVOKED` Sailor follows the existing ingestion transition `REVOKED → PENDING`, starting a new consent cycle without granting consent. Technical Activity reuse/creation and Session matching remain subject to existing rules.
- `admin_upload` processing and its Reprocess are silent: no automatic consent-request, welcome or Session-result emails. Suppression is not recorded as an outbound attempt or successful delivery and does not consume an email-source automatic delivery reservation. Existing explicit Admin consent/communication actions retain their separate eligibility rules. OVH's automatic communication rules above and below remain unchanged.

### Purpose-specific capabilities

| Capability | What possession authorizes | Current boundary |
| --- | --- | --- |
| Consent request, `/consent/<token>` | The consent decision for one current request and cycle | No Session or Personal TackBar access; no passive acceptance. |
| Original Session, `/s/<token>` | Shared access to one Session while its access is usable | Separate from the internal Session ID; backend applies expiry, revocation and current `ACTIVE` visibility. No Sailor login is required. |
| Personal TackBar, `/me/<token>` | One Sailor's personal Session history while that Sailor is `ACTIVE` | Separate from Sailor ID, email and Session capabilities; does not independently authorize a Session Viewer or another Sailor's history. |
| Temporary QR share, `/q/<token>` | Short-lived access to the same underlying Session | Derived from a usable original Session capability; cannot create another temporary share or reveal the original credential. |

- These bearer credentials are generated separately and are not public representations of internal Sailor or Session IDs. A Session may exist without a shared capability. The original shared capability is ensured when an unexpired Session first has shareable `ACTIVE` content and otherwise remains stable unless Admin explicitly regenerates or revokes it; a revoked capability is not silently restored. Admin regeneration replaces the original token and invalidates the old one; Admin revocation makes it unusable. Regeneration requires an unexpired Session with `ACTIVE` content.
- An `ACTIVE` Sailor can have one current Personal TackBar capability. Consent changes gate its use at request time but do not automatically destroy the token. Explicit Admin regeneration invalidates the previous personal token; explicit revocation blocks its use without changing consent. A later consent grant does not silently undo explicit personal-capability revocation.
- A personal capability opens only the Sailor's own participation history. Opening a listed Session still requires a currently usable original Session capability and the shared Session's authorization checks. An expired, revoked or otherwise unavailable Session may remain in personal history without an opening link; Personal TackBar does not fabricate or renew shared access. History presentation belongs in [Personal TackBar](personal-tackbar.md).

### Temporary QR sharing

- A temporary share can be created or reused only through currently usable original Session access with visible shared content. Reopening the share action reuses an existing usable share for that Session and originating capability; when none remains usable, a new share may be created. The QR carries only the temporary URL. Its recipient opens the same Session Viewer through temporary endpoints and never receives or is redirected to the original capability URL.
- A new temporary share expires at the earlier of 48 hours after creation and the Session expiry in force at creation. Its record persists across backend restart without copying Session or Activity content. Its fixed expiry is not extended or revived by later Session renewal. The share remains dependent on the current originating capability: revoking or regenerating that original immediately invalidates the derived share. Session content changes do not themselves invalidate it; current `ACTIVE` visibility still governs each response.
- The backend rechecks the temporary token, its fixed expiry, the Session and the originating capability on access. Unknown, expired and invalidated temporary access have distinct safe unavailable outcomes. Temporary access cannot authorize another QR share. The Viewer identifies temporary access and omits the share action; its presentation details belong in [Session Viewer](session-viewer.md).

### Session lifetime and outbound access messages

- Session expiry closes original and temporary shared access without deleting Activities or preventing later technical Session matching. Explicit Admin renewal may make an existing non-revoked original capability usable again if `ACTIVE` content remains; it does not create, rotate or restore a revoked capability. It does not extend an already-created temporary share. [Domain and Sessions](domain-and-sessions.md) owns Session lifetime, renewal and retention rules.
- The ordinary successful `PENDING → ACTIVE` path attempts one welcome email after consent and access state are established. For a deterministically identified track-first onboarding Activity, the welcome message uses its currently usable Session link as the immediate action and the existing Personal TackBar link as the persistent entry point. If no usable onboarding Session link exists, the existing personal-link welcome path remains. Explicit Admin welcome resend requires `ACTIVE` consent and usable personal access; it uses existing capabilities and does not regenerate them. The case of an explicitly revoked personal capability at activation is left for review below.
- A later newly created Activity for an already `ACTIVE` Sailor can receive one Session-result email after successful processing and Session association, when both current Session and Personal TackBar access are usable. The onboarding Activity is not also sent a separate Session-result email while `PENDING` or after activation. Duplicate input, Activity reuse and ordinary reprocessing do not trigger another automatic Session-result delivery. Sending does not create, regenerate or renew access.
- Consent-request, welcome and Session-result delivery outcomes are operational state, not consent or authorization decisions. Controlled SMTP failure does not roll back `ACTIVE` consent, Activity processing, Session membership or capabilities. The subsequent-track Session-result attempt is recorded before SMTP; controlled failure is terminal for automatic delivery. [Ingestion and Data](ingestion-and-data.md) owns durable processing and delivery-attempt state; Admin presentation and resend controls belong in [Admin](admin.md).

### Authorization boundaries

- Shared and temporary Session endpoints use backend authorization for details, tracks and analytics. An internal Session ID, Activity ID, personal token or consent token is not a substitute for the required shared bearer capability. The frontend renders permitted API responses and does not establish shared visibility by hiding data locally.
- No access path here grants Sailor login, recipient identity, per-recipient permissions or a standalone Activity Viewer. Consent withdrawal changes sharing immediately but is not a physical deletion operation. Data processing and persistence belong in [Ingestion and Data](ingestion-and-data.md); Session membership and retention belong in [Domain and Sessions](domain-and-sessions.md).

**UNRESOLVED — personal history aggregate visibility:** [v0.6 requirements](../v0.6-personal-tackbar-pilot-operations-requirements.md), §3 V6-PER-04 permits derived Session context, while [v0.5 pilot requirements](../v0.5-real-sailing-pilot-requirements.md), §3 V5-CNS-03 requires `ACTIVE`-only Activities in shared responses. `backend/app/services/sailor_sessions.py` and `backend/tests/test_admin_api.py` deliberately include a non-`ACTIVE` member in a personal history card's Session interval and Sailor count, while shared details exclude that member. The sources do not explicitly settle whether those aggregates are within the privacy restriction. The current contract states the shared Activity boundary and leaves the aggregate policy for human review.

**UNRESOLVED — accepted consent link after expiry:** [v0.6.5 onboarding requirements](../v0.6.5-simplified-pilot-onboarding-requirements.md), §5 V6.5-TOK-02 calls the consent token valid for exactly 28 days. `backend/app/services/consent_requests.py` classifies an already accepted current-cycle request as `ACCEPTED` before checking expiry. `backend/app/services/web_consent.py` can then return the confirmed state and complete an interrupted activation for an already-`ACTIVE` Sailor after day 28. Unaccepted requests cannot be accepted after expiry. Decide whether this post-acceptance recovery remains authorized after token expiry; this specification does not resolve the discrepancy.

**UNRESOLVED — welcome attempt after explicit personal revocation:** [v0.6.4 welcome requirements](../v0.6.4-sailor-activation-welcome-email-requirements.md), §2 V6.4-OBJ-01 says a successful Admin confirmation attempts one welcome email, while §6 forbids capability regeneration for sending. `backend/app/services/sailor_consent.py` skips automatic welcome sending if the personal capability was explicitly revoked, and `backend/tests/test_personal_capabilities.py` confirms revocation survives a later consent cycle. The intended notification outcome for this edge case should be stated explicitly.

**Evidence gap — concurrent QR creation:** [Completed #25](https://github.com/maxsail-project/tackbar/issues/25) calls for at most one usable temporary share per Session and originating capability. The reviewed service uses a process-local lock and JSON repository validation checks unique IDs/tokens, but does not show cross-process exclusion for simultaneous creation requests. The accepted reuse rule is recorded above; cross-process enforcement needs review before claiming a stronger concurrency guarantee.
