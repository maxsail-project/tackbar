# Personal TackBar

This specification owns accepted Personal TackBar behavior. Its separately marked unresolved privacy question is not a new guarantee. [The index](index.md) defines the documentation route.

## Current contract

### Purpose and access

- Personal TackBar's current UI shows an `ACTIVE` Sailor's **My Sessions** participation history, **My Activities** context and editable **My Profile** name. Entry uses that Sailor's current personal capability, without a Sailor login. Invalid or unusable access does not disclose the Sailor or history. [Access and Consent](access-and-consent.md) owns the authorization, consent and capability rules.
- A Session appears once when at least one of the Sailor's Activities belongs to it, including when that Sailor has multiple Activities in the Session. Membership is derived through Sailor → Activity → Session. Sessions with a currently usable opening link appear first, followed by unavailable Sessions; within each group, history keeps its newest-first sailing chronology and deterministic ties. The last-sailing summary remains the latest sailing end across all participation history, regardless of availability. The current UI does not offer email editing, track upload or Session administration. [Domain and Sessions](domain-and-sessions.md) owns Activity and Session relationships.

### Personal context APIs

- `PATCH /api/me/{token}/profile` accepts only `name` for the current `ACTIVE` Sailor and returns the updated optional name. It trims surrounding whitespace and stores empty or whitespace-only input as `null`. Email, Sailor ID, consent, capabilities, default Boat and Activity/Session records remain unchanged. An invalid or unusable capability cannot use the operation.
- The backend exposes `GET /api/me/{token}/activities` for the current Sailor's Activities, including original source, filename, parsed Device name, optional descriptive Device label and Boat context. `PATCH /api/me/{token}/activities/{activity_id}` changes only that Sailor's optional `boat_id` and `device_label`. Omitted fields retain their values; `null` clears them. A newly assigned Boat must belong to the Sailor. Historical Boat references remain readable but cannot be assigned anew unless owned.
- `GET /api/me/{token}/boats` lists only the Sailor's owned Boat catalogue. `POST /api/me/{token}/boats` creates a Boat with a server-generated ID and owner; `PATCH /api/me/{token}/boats/{boat_id}` changes only an owned Boat's name, sailing class or sail number. Omitted fields are retained and `null` clears a field, provided at least one metadata field remains nonblank. Foreign and legacy Boats cannot be edited. `GET /api/me/{token}/boat-classes` returns only known canonical Class names, without Boat records or Sailor identities.
- A submitted Class reuses a known canonical spelling after case and whitespace normalization. A likely typo returns HTTP 409 with `detail.code=class_confirmation_required`, `submitted_class` and `suggested_class`, without writing the Boat. The client may resubmit the suggested spelling, or resubmit the original spelling with `confirm_new_class=true` to retain it. New accepted names become available to other Sailors as names only.
- `GET` and `PATCH /api/me/{token}/default-boat` read, set or clear the optional default; a non-null new default must be in that catalogue.

### My Activities

- A separate compact section lists the current Sailor's Activities, keyed by stable Activity IDs, with sailing date/time, current Boat and Device context, and read-only source, original filename and extracted Device name. An absent Device or Boat is shown explicitly. The section can be empty even when Sessions history is present.
- One Activity at a time can be edited inline. Its Boat choice includes the Sailor's owned catalogue and an explicit No Boat option. A historical legacy or unavailable Boat association is displayed as current context and may be retained, but is not offered as a new assignment. The Device editor starts with the nonblank custom label, otherwise the nonblank extracted Device name, otherwise empty. Original provenance remains read-only.
- Save sends only changed fields. Choosing No Boat or clearing a custom Device label sends `null`; clearing restores the extracted Device name when available. An unchanged effective Device value does not write a redundant label. Clearing an inherited extracted name without a custom label does not change provenance or write an override; changing a custom label to the extracted name clears the override. Changing only the label preserves an existing historical Boat reference. Cancel discards unsaved input. The UI shows loading, save success and generic failure feedback, supports retrying a failed read or write, and prevents repeated submissions while a write is pending. Invalidated personal access removes personal content.

### My Profile

- The compact profile displays the current name, or an unset state, and the read-only email near the Sailor identity. Edit Name opens an inline Name input initialized from the loaded value. Save sends a changed value to the personal profile API and displays the returned name; clearing the input removes the optional name and restores the email identity fallback. An unchanged normalized name does not cause a write. Cancel discards the draft.
- The editor shows pending, success and generic recoverable failure feedback, preserves the draft after a failed write and prevents duplicate submissions. Invalidated access removes private content. Its native input and buttons support keyboard and touch interaction.

### My Boats

- A compact section lists only the Sailor's owned Boats and uses one Add/Edit form with Name, optional free-text Class and Sail Number. At least one field must be nonblank. Cancel discards unsaved form changes; recoverable save errors retain the input. Successful saves use the canonical Boat metadata returned by the backend. Creating a Boat neither assigns it to an existing Activity nor makes it the default.
- The form loads known Class names once with the Boat context. As the Sailor types, it offers a short filtered list of selectable names and still accepts unrestricted new text. A likely typo response presents both the submitted and suggested Class inline: the Sailor may explicitly use the suggestion or confirm keeping the submitted spelling. Changing the Class input clears a stale confirmation. The backend remains authoritative for normalization and validation.
- The section displays the optional Default Boat and permits selecting an owned Boat or clearing the default. A historical or unavailable default remains selected until the Sailor explicitly changes or clears it. A default change affects later Activity creation only; existing Activities remain as they were.
- Newly created owned Boats become available in the Activity editor without a reload. Editing Boat metadata refreshes displayed context for Activities referring to it while preserving any unsaved Activity edits. Loading, write and generic failure feedback, retry and duplicate-submit protection apply to Boat and default controls. A denied personal capability removes personal content.

### Session recognition and search

- The compact, single-column list shows the Sailor's identity and Session count. Each row identifies the Session by its persisted city when non-empty, otherwise its persisted country when non-empty, plus sailing date. City and country are never concatenated, region is not a fallback, and without city or country the date remains the identity. A second line gives the sailing time range and a Sailor count. The list remains useful without geographic or weather context.
- A third, optional line shows persisted historical/modelled wind direction, wind speed and air temperature from the hourly observation nearest the Session interval midpoint. An equal-distance tie uses the earlier observation. The line is omitted when no usable values exist. It does not show gusts, cloud, wave or provider detail. [Session Context](session-context.md) owns acquisition, provenance and availability of these Session-owned values.
- Search filters the displayed Session list by its selected city-or-country display location and sailing date. It does not search region, weather, counts, Activity details, technical IDs or diagnostics. Search and rows remain compact and usable on mobile and tablet; no thumbnail or row expansion is part of the accepted Personal view.

### Opening and unavailable Sessions

- An available row opens the existing collaborative [Session Viewer](session-viewer.md) directly through a currently usable shared Session capability. Personal access does not grant Viewer access on its own. The Viewer still applies shared capability, Session lifetime and `ACTIVE`-only visibility checks. [Access and Consent](access-and-consent.md) owns those checks.
- An expired, revoked or otherwise unavailable Session remains in participation history, visibly unavailable and without a usable opening action. Personal TackBar does not fabricate a shared link, renew a Session or change Activity retention. Explicit Admin renewal may restore access only under the existing Session and capability rules in [Domain and Sessions](domain-and-sessions.md) and [Access and Consent](access-and-consent.md).
- The public header offers About without changing the page route or Session list. Where release metadata is available, the exact deployed tag and release family appear beneath the public logo and within About; absent metadata is omitted. [Completed #116](https://github.com/maxsail-project/tackbar/issues/116) records the accepted placement.

### Unresolved contract

**High — personal history aggregate visibility.** `backend/app/services/sailor_sessions.py` derives a row's sailing interval and Sailor count from all member Activities, including those owned by non-`ACTIVE` Sailors; `backend/tests/test_admin_api.py` exercises this, while shared Viewer details filter those Activities. [V6-PER-04](../v0.6-personal-tackbar-pilot-operations-requirements.md) permits derived recognition context and [V5-CNS-03](../v0.5-real-sailing-pilot-requirements.md) requires `ACTIVE`-only shared Activity visibility, but neither settles whether personal aggregate interval/count may reveal non-`ACTIVE` participation. The rule needs a human decision; the current contract above does not prescribe the membership basis for those displayed aggregates.

Open [#117](https://github.com/maxsail-project/tackbar/issues/117) is research on a possible minimap, not an accepted thumbnail requirement. Open [#120](https://github.com/maxsail-project/tackbar/issues/120) and [#121](https://github.com/maxsail-project/tackbar/issues/121) do not change Personal TackBar behavior.
