# Admin — transitional current-product draft

**Status: Phase B6 review draft.** This consolidates accepted Admin behavior without activating the Living Documentation hierarchy. Until Phase C is approved and activated, the existing instruction and documentation precedence described in the [index](index.md) remains in force. The [Admin UX/UI Guidelines](../admin-ux-ui-guidelines.md) remain the source of truth for detailed Admin interaction and visual conventions.

## Current contract

### Operational surface and navigation

- TackBar provides a small, protected Admin surface separate from public Session and Personal TackBar capabilities. Admin reads and maintenance actions use backend APIs and services, not direct frontend access to persistence files. [Access and Consent](access-and-consent.md) owns access authorization.
- The top-level operational order is **Ingestions → Activities → Sailors → Sessions**, starting at Ingestions. Each entity's full detail opens in its own section; relationships navigate to that section. A section presents a compact single-column list and at most one full-width expanded detail. Summary, operational detail, Advanced and read-only Admin diagnostic JSON provide progressively deeper evidence. Human-readable identities lead; exact IDs belong mainly in Advanced. Data, relations, actions, statuses and disclosures have distinct affordances on mobile, tablet and desktop.

### Ingestions and Activities

- Admin can review the mailbox on demand, inspect ingestion history and errors, and explicitly reprocess from a preserved original when available. Ingestion technical outcome (`processed`/`failed`) and administrative disposition (`active`/`discarded`) are separate. Admin can discard or restore a record without physically deleting it; restore does not reprocess automatically. [Ingestion and Data](ingestion-and-data.md) owns processing, deduplication and persistence effects.
- Ingestion lists support combined technical-status, disposition and Sailor filters, including unresolved Sailor relationships, plus text search. Ingestion detail shows source, processing attempts/errors, related Sailor/Activity/Session, derived sailing context and outbound Session-result notification state. A resolved Sailor's displayed consent status is current at read time, not a persisted ingestion snapshot.
- For a processed Ingestion with an Activity, Admin distinguishes **Activity created**, **existing Activity reused** and **unknown legacy provenance**. Reuse is a successful processed outcome and does not imply failed or discarded status. This is the accepted [#60](https://github.com/maxsail-project/tackbar/issues/60) observability contract.
- Activity list/detail exposes its sailing and canonical-track evidence, owning Sailor, Session and source Ingestion relationships, while keeping source metadata separate from entity traceability. If an Ingestion relation is absent or ambiguous, Admin does not invent an authoritative source. Activity detail shows maneuver artifact currency and detector evidence and offers explicit recalculation when the normalized track is available. [Analytics](analytics.md) owns maneuver calculation and artifact validity.

### Sailors, consent and communication

- Sailor overview distinguishes `ACTIVE`, `REVOKED`, `PENDING` needing a request and `PENDING` awaiting a response. Detail shows current consent, structured consent timeline, Activity and Session participation, personal-access state and communication state. Historical participation remains inspectable to Admin for non-`ACTIVE` Sailors; that does not make their Activities publicly shareable.
- Admin offers semantic consent actions appropriate to state: mark a request sent manually, explicitly send/resend a valid request, reissue an expired request, confirm explicit acceptance, record decline or withdrawal, and start a new consent cycle. An accepted request is not resent as pending; sending or reissuing does not grant consent. [Access and Consent](access-and-consent.md) owns consent transitions, token validity and shared visibility.
- Admin can inspect and copy/open a usable Personal TackBar link, regenerate or revoke the personal capability, and inspect welcome-email delivery state. **Resend welcome email** is offered only for an `ACTIVE` Sailor with usable personal access; it reuses current access rather than regenerating it. Delivery failure is operational state, not a reversal of consent or Session membership. SMTP acceptance is not proof of inbox delivery. Admin also shows Session-result notification attempt state on the related Ingestion.

### Sessions and contextual maintenance

- Session summaries identify the sailing outing, total associated Activities, currently shareable Activities, Sailors, sailing interval and lifetime. The prominent `ACTIVE`/`EXPIRED` lifetime state derives from Session expiry; original capability state is shown separately. Detail shows member Activities, owning Sailors and current shareability. [Domain and Sessions](domain-and-sessions.md) owns membership and lifetime; [Access and Consent](access-and-consent.md) owns capability and visibility rules.
- Admin can copy/open a usable original Session link, explicitly renew Session lifetime, and regenerate or revoke the original capability. Renewal sets expiry from the current time using a selected duration and preserves capability state; it does not silently create or restore a revoked capability. Maintenance controls remain distinct from read-only access state and entity relations.
- Admin shows active, expired and unavailable temporary QR share counts separately from original Session access. It can inspect the currently active temporary share and copy/open its usable link. The Admin surface does not offer creation, renewal, regeneration or revocation controls for a temporary share. Temporary sharing remains access to the same Session, governed by [Access and Consent](access-and-consent.md).
- Admin shows persisted Session location, acquisition provenance and historical hourly weather/marine conditions when available, and offers an explicit per-Session **Enrich Session** action. That action fills missing geography and requests current interval coverage; context failure does not redefine the Session. [Session Context](session-context.md) owns acquisition, persistence and availability.
- Admin provides search within Activities, Sailors and Sessions as well as Ingestions. Session search includes its displayed location and sailing date and represented Sailor/Activity identities; missing or ambiguous relations are shown as unavailable rather than guessed.

### Superseded, pending and unresolved

- **Superseded navigation:** [v0.6.3 requirements](../v0.6.3-usability-and-maintenance-requirements.md) §6 recorded Ingestions → Sailors → Sessions. The later [Admin guidelines](../admin-ux-ui-guidelines.md#admin-navigation-model), current UI and focused tests include Activities between Ingestions and Sailors. The old order remains historical.
- **Pending #118 location identity:** The accepted [v0.7 city-only contract](../v0.7-collaborative-debrief-analytics-requirements.md) §9 V7-CTX-01/03 and [v0.7 decisions](../v0.7-decisions.md) §12 do not permit country-only compact identity. [Issue #118](https://github.com/maxsail-project/tackbar/issues/118) approves **City > Country > nothing**, including Admin title/search, but local acceptance is not closed. Current local Admin code/tests contain country fallback; it is not promoted here. See [Session Context](session-context.md#approved-presentation-delta-pending-local-acceptance).
- **High — personal aggregate privacy:** Admin's own participation inspection includes non-`ACTIVE` Sailors as required by [v0.5.1 U-02](../v0.5.1-pilot-fix-and-usability-requirements.md); whether the same aggregate interval/count may appear on a public Personal row remains unresolved in [Personal TackBar](personal-tackbar.md#pending-presentation-delta-and-unresolved-contract) and [Access and Consent](access-and-consent.md#provenance-and-review).
- **Medium — welcome after explicit personal revocation:** The existing [Access and Consent review](access-and-consent.md#provenance-and-review) records a conflict between automatic welcome-at-activation wording and the implementation's preservation of explicit personal revocation. This draft specifies the supported Admin resend eligibility, not a new automatic-delivery outcome for that edge case.

Open [#117](https://github.com/maxsail-project/tackbar/issues/117) does not add Admin minimap generation; [#120](https://github.com/maxsail-project/tackbar/issues/120) does not change Session matching; [#121](https://github.com/maxsail-project/tackbar/issues/121) does not establish a new ingestion concurrency guarantee. Broader deletion and Session maintenance proposals remain outside the accepted Admin contract.
