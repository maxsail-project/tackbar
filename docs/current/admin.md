# Admin

This specification owns accepted functional Admin behavior. The [Admin UX/UI Guidelines](../admin-ux-ui-guidelines.md) retain their specialist role for detailed interaction and visual conventions; a material conflict with this functional contract requires review. [The index](index.md) defines the documentation route.

## Current contract

### Operational surface and navigation

- TackBar provides a small, protected Admin surface separate from public Session and Personal TackBar capabilities. Admin reads and maintenance actions use backend APIs and services, not direct frontend access to persistence files. [Access and Consent](access-and-consent.md) owns access authorization.
- The top-level operational order is **Ingestions → Activities → Sailors → Sessions → Courses**, starting at Ingestions. Courses is a stateless tool section, not a persisted entity. Each entity's full detail opens in its own section; relationships navigate to that section. A section presents a compact single-column list and at most one full-width expanded detail. Summary, operational detail, Advanced and read-only Admin diagnostic JSON provide progressively deeper evidence. Human-readable identities lead; exact IDs belong mainly in Advanced. Data, relations, actions, statuses and disclosures have distinct affordances on mobile, tablet and desktop.
- Each protected Ingestion, Activity, Sailor and Session detail's Diagnostic JSON separates `persisted_record` from `operational_context`. The persisted section covers every canonical field with its original field name and safe value, including Activity spatial metadata and all persisted auxiliary observations, Ingestion technical notice and onboarding reservation, and Session historical context. Activity observation timestamps use UTC millisecond precision; Ingestion string timestamps retain their persisted representation. Bearer tokens are represented as `[REDACTED]` when present and `null` when absent; raw communication errors are replaced by controlled failure indicators, including in the Sailor detail's welcome-email status field. Track and archived-original references appear only when they match the expected relative storage shape; other path values are redacted. The Activity `gap_summary` exposes only its aggregate `count` and `total_seconds` (`null` until derived), never the gap UTC intervals. Derived availability, relationship and access states remain under `operational_context`. This is an Admin-only, read-only view of the selected record; it does not expose track bytes, global collections or credentials. New persisted fields require explicit diagnostic safety classification before exposure.
- Admin actions that open usable product/runtime links, including Personal TackBar, original Session and temporary share links, use native links that request a new browser context and preserve the current Admin page. They include referrer and opener protections. Internal Admin entity relations continue navigating to their owning sections; Copy and maintenance actions keep their existing semantics. The browser decides whether a new context appears as a tab or window.

### Ingestions and Activities

- Admin can review the mailbox on demand, inspect ingestion history and errors, and explicitly reprocess from a preserved original when available. Email technical outcome (`processed`/`failed`) and manual lifecycle (`pending`/`processing`/`processed`/`failed`) are separate from administrative disposition (`active`/`discarded`). Admin can discard or restore a record without physically deleting it; restore does not reprocess automatically. [Ingestion and Data](ingestion-and-data.md) owns processing, deduplication and persistence effects.
- **Upload track** in Ingestions opens a compact, single-file form in local or protected production Admin. It requires explicit selection from existing `ACTIVE` Sailors, with no free email/Sailor creation or Boat override. It accepts `.gpx`, `.csv`, `.csv.gz`, `.vkx` and `.vkx.gz` case-insensitively, up to 16 MiB per file. Client validation explains missing choices, empty/oversized files and unsupported suffixes; backend checks remain authoritative. There is no bulk upload, percentage progress or processing-cancellation action.
- Feedback shows **Uploading** until durable server acceptance, then the returned **Pending**, **Processing**, **Processed** or **Failed** state. A `202` is not a success result. Other Admin sections remain usable; accepted processing continues independently of navigation/browser lifetime. Lightweight polling reads only active Ingestions while Ingestions is open, stops after terminal results or navigation, and reports inspection errors with explicit Refresh recovery. Returning to Ingestions or refreshing inspects persisted results.
- Manual records show `admin_upload` source, the selected Sailor, acceptance time, preserved-original availability, attempts and controlled errors, including the complete plain-GPX temporal-quality diagnostic and activation/interruption failures. Unexpected manual-processing errors remain generic. No sender, email receipt or provider-message identity is invented. Operational detail exposes related Sailor/Activity/Session navigation in their owning sections, created/reused Activity provenance and explicit automatic-email suppression. Reprocess and disposition actions are disabled while pending/processing; failed/interrupted originals remain available for explicit Reprocess. Upload/network errors with uncertain acceptance advise inspection before resubmission to avoid accidental duplicate attempts.
- Ingestion lists support combined technical-status, disposition and Sailor filters, including unresolved Sailor relationships, plus text search. Ingestion detail shows source, processing attempts/errors, related Sailor/Activity/Session, derived sailing context and outbound Session-result notification state. A resolved Sailor's displayed consent status is current at read time, not a persisted ingestion snapshot.
- For a processed Ingestion with an Activity, Admin distinguishes **Activity created**, **existing Activity reused** and **unknown legacy provenance**. Reuse is a successful processed outcome and does not imply failed or discarded status. This is the accepted [#60](https://github.com/maxsail-project/tackbar/issues/60) observability contract.
- Activity summaries identify the Activity's currently associated Boat and effective Device (nonblank descriptive label, otherwise original Device name, otherwise unavailable). Operational detail separates this context from read-only source, original Device and filename provenance, while retaining sailing and canonical-track evidence and navigable Sailor, Session and source Ingestion relationships. It never substitutes a Sailor's Default Boat for the Activity's own association. If an Ingestion relation is absent or ambiguous, Admin does not invent an authoritative source. Activity detail shows maneuver artifact currency and detector evidence and offers explicit recalculation when the normalized track is available. [Analytics](analytics.md) owns maneuver calculation and artifact validity.
- Expanded protected detail for a VKX/VKX.GZ Activity includes a read-only **VKX Record Summary**. It inventories every structurally recognized row type in that Activity's preserved original on demand, with code, source-spec name or neutral internal label, row count and truthful handling status. It separately shows source navigation, timer, line-position and Shift Angle (`0x06`) rows, actual normalized navigation samples and the Activity's persisted timer, line-position and Shift Angle observation counts. `0x06` is classified as an Activity-observation type. Zero counts, missing originals and unreadable originals remain distinct; a source-to-persisted difference has no inferred cause. Internal/page and ignored sensor rows are counted without decoding their payloads. The Activity list does not scan originals. This Admin-only summary exposes no raw observations and does not reprocess or modify the Activity.

### Sailors, consent and communication

- Sailor overview distinguishes `ACTIVE`, `REVOKED`, `PENDING` needing a request and `PENDING` awaiting a response. Detail shows current consent, structured consent timeline, Activity and Session participation, personal-access state and communication state. Fresh Sailor and Activity reads use the current Sailor name when set and email otherwise. Sailor detail also shows a read-only catalogue of explicitly Sailor-owned Boats and distinguishes no Default Boat, an owned Default Boat, a legacy default and an unavailable reference. Activity use or a historical default does not grant Boat ownership. Historical participation remains inspectable to Admin for non-`ACTIVE` Sailors; that does not make their Activities publicly shareable.
- Admin offers semantic consent actions appropriate to state: mark a request sent manually, explicitly send/resend a valid request, reissue an expired request, confirm explicit acceptance, record decline or withdrawal, and start a new consent cycle. An accepted request is not resent as pending; sending or reissuing does not grant consent. [Access and Consent](access-and-consent.md) owns consent transitions, token validity and shared visibility.
- Admin can inspect and copy/open a usable Personal TackBar link, regenerate or revoke the personal capability, and inspect welcome-email delivery state. **Resend welcome email** is offered only for an `ACTIVE` Sailor with usable personal access; it reuses current access rather than regenerating it. Delivery failure is operational state, not a reversal of consent or Session membership. SMTP acceptance is not proof of inbox delivery. Admin also shows Session-result notification attempt state on the related Ingestion.

### Sessions and contextual maintenance

- Session summaries identify the sailing outing, total associated Activities, currently shareable Activities, Sailors, sailing interval and lifetime. The prominent `ACTIVE`/`EXPIRED` lifetime state derives from Session expiry; original capability state is shown separately. Detail shows member Activities, owning Sailors and current shareability. [Domain and Sessions](domain-and-sessions.md) owns membership and lifetime; [Access and Consent](access-and-consent.md) owns capability and visibility rules.
- Admin can copy/open a usable original Session link, explicitly renew Session lifetime, and regenerate or revoke the original capability. Renewal sets expiry from the current time using a selected duration and preserves capability state; it does not silently create or restore a revoked capability. Maintenance controls remain distinct from read-only access state and entity relations.
- Admin shows active, expired and unavailable temporary QR share counts separately from original Session access. It can inspect the currently active temporary share and copy/open its usable link. The Admin surface does not offer creation, renewal, regeneration or revocation controls for a temporary share. Temporary sharing remains access to the same Session, governed by [Access and Consent](access-and-consent.md).
- Admin shows persisted Session location, acquisition provenance and historical hourly weather/marine conditions when available, and offers an explicit per-Session **Enrich Session** action. That action attempts to refresh geography even when already populated, replacing its snapshot only when no populated geographic field type is lost, and independently requests current interval conditions coverage. A failed or incomplete result leaves that source's prior context unchanged. [Session Context](session-context.md) owns acquisition, persistence and availability.
- Admin provides search within Activities, Sailors and Sessions as well as Ingestions. Activity search matches the associated Boat's nonblank name, Class and sail number; Sailor search matches explicitly owned Boats and Boats referenced by that Sailor's Activities, including resolvable legacy references; Session search matches Boats referenced by any member Activity. These matches use protected Admin snapshots, not Default Boat substitution, global Class names or Ingestion Boat search. Compact Session identity and search use **City > Country > nothing** plus sailing date; city and country are not concatenated and region is not a display or search fallback. Search also includes represented Sailor/Activity identities; missing or ambiguous relations are shown as unavailable rather than guessed.

### Course import (GeoRacing, draft and validation)

- Protected Admin provides a stateless course import API, separate from track ingestion. It never creates or changes an Ingestion, Activity, Sailor or Session, and persists nothing. Its draft is a proposal for human review; it is not attached to a Session and not shown in the Viewer.
- `POST /api/admin/course-imports/georacing/draft` accepts one raw GeoRacing elements GPX body with one `filename` query value (`.gpx`, uncompressed) under existing Admin authentication. The provider is selected by the path, not detected. It uses the plain GPX safe-XML protections (no DTD or entities, structural ceilings) and the **16 MiB** limit, and accepts **1 to 32** `trk` elements, each with exactly one segment of at least two trackpoints with finite WGS84 coordinates and explicit timezone-aware timestamps, strictly increasing per track. Multipart (`415`), oversized (`413`) and ambiguous (`400`) requests are rejected; a parse rejection is a controlled `422` without file content.
- The draft lists every track in source order with its label (the provider's track name), a suggested role and gate id from the GeoRacing name table, a never-moved flag, a duplicate-of reference and its segments. A **stable interval** keeps every sample within **15 m** of its median position for at least **120 s**, without a silence above 120 s; the median is its position. Other stretches are **relocation** and carry no position. Duplicate trackers agree within 15 m at the 95th percentile of shared whole-second timestamps covering at least half of the shorter track. The draft also returns a pre-filled reviewed course: suggested elements with their stable intervals, start and finish lines when exactly one committee boat and one matching pin are suggested, no gun, and ignored tracks with a reason. Unrecognized names are suggested as ignored.
- `POST /api/admin/course-imports/validate` reads its JSON body only after Admin authorization, rejects a body above **1 MiB** with `413` before parsing, accepts a reviewed course and returns `{"course": …}`, a course context of schema version 1, or `422` with the validation errors. It assigns a `course_id` when absent. Roles use the vocabulary `committee_boat`, `start_pin`, `finish_pin`, `gate` (with a gate id), `mark`, `change_mark` and `ignored` (listed in `ignored_tracks`). The start line references a committee boat and a start pin; the finish line references a committee boat and a finish pin. Positions are ordered, non-overlapping and inside the course time range. A gun is optional, Admin-entered only (`gun_source: "admin_entered"`) and inside the time range; an optional race end follows the gun. Timestamps are UTC.
- The **Courses** section (last in Admin navigation, loaded on demand) is the Admin tool for these endpoints. The Admin uploads one elements GPX (the client checks only the `.gpx` suffix; `401`, `413` and `422` show controlled errors). One review row per track shows label, samples, first/last UTC, suggested role and its basis, and never-moved and duplicate flags. The Admin can change the role (including `ignored`), edit the gate id, and inspect stable intervals and relocation stretches. Stable intervals can be trimmed within their original bounds, split at a UTC time (both halves keep the same median position and touch at the split) or deleted; relocation stretches never become positions. A non-ignored role without any remaining interval, an invalid UTC entry, or a missing race label or gate id is reported and blocks validation. Race label, gun and optional end are entered and displayed in explicit UTC (`YYYY-MM-DD HH:MM:SS`), never in the browser time zone. Start and finish lines are built from the single committee boat, start pin and finish pin. Validation errors (`422`) are listed readably; a valid result can be downloaded as JSON named after the race label, and any later edit invalidates it. A map preview with a UTC time slider and a gun marker draws each non-ignored element whose edited interval contains the slider time, with its label, and the start or finish line only while both referenced elements are present; an interval contains its bounds, and at a touching instant the later interval applies. Course marks and lines use `#B46B42`; the change mark uses red `#D62828`. The review survives switching Admin sections and is discarded when Admin access ends; nothing is persisted or attached to a Session.

### Superseded and unresolved

- **Superseded navigation:** [v0.6.3 requirements](../v0.6.3-usability-and-maintenance-requirements.md) §6 recorded Ingestions → Sailors → Sessions. The later [Admin guidelines](../admin-ux-ui-guidelines.md#admin-navigation-model), current UI and focused tests include Activities between Ingestions and Sailors. The old order remains historical.
- **High — personal aggregate privacy:** Admin's own participation inspection includes non-`ACTIVE` Sailors as required by [v0.5.1 U-02](../v0.5.1-pilot-fix-and-usability-requirements.md); whether the same aggregate interval/count may appear on a public Personal row remains unresolved in [Personal TackBar](personal-tackbar.md#unresolved-contract) and [Access and Consent](access-and-consent.md#provenance-and-review).
- **Medium — welcome after explicit personal revocation:** The existing [Access and Consent review](access-and-consent.md#provenance-and-review) records a conflict between automatic welcome-at-activation wording and the implementation's preservation of explicit personal revocation. The current contract states the supported Admin resend eligibility, not a new automatic-delivery outcome for that edge case.

Open [#117](https://github.com/maxsail-project/tackbar/issues/117) does not add Admin minimap generation; [#120](https://github.com/maxsail-project/tackbar/issues/120) does not change Session matching; [#121](https://github.com/maxsail-project/tackbar/issues/121) does not establish a new ingestion concurrency guarantee. Broader deletion and Session maintenance proposals remain outside the accepted Admin contract.
