# Ingestion and Data

This specification owns accepted acquisition, normalization, ingestion state and persistence behavior. [The index](index.md) defines the documentation route.

The **Current contract** below states product and operational guarantees. The **Provenance and review** section identifies supporting evidence and gaps; it does not add requirements.

## Current contract

### Email acquisition and identity

- Email remains the normal Sailor track-sharing channel. Production acquires inbound mail from the configured OVHcloud mailbox over IMAP/TLS. Automatic scheduled review is the normal trigger; Admin **Review mailbox now** remains a manual fallback. Both use the same downstream ingestion service. Protected Admin upload is the exceptional operator/testing acquisition path described below.
- The outer email sender is the email identity used to resolve the Sailor. A forward sent by another person uses that forwarder's outer address; TackBar does not recover an original sender from forwarded headers. The subject is informational and does not determine Sailor, Boat, Activity or Session identity.
- Each candidate has a provider identity and stable provider-message ID. For OVH, that ID includes the mailbox `UIDVALIDITY` and message UID. The pair `provider + provider_message_id` identifies a mail; a mail Ingestion is distinguished by that pair plus a positive attachment ordinal. Its immutable Ingestion ID remains the operational record identity. The persistence model can distinguish explicit named-MIME-occurrence traversal ordinals from logical ordinal `1` on current and migrated single-file records; the latter is not a verified historical MIME position. Original filenames remain attached to each Ingestion.
- A message with exactly one supported track attachment can enter the track pipeline. A message with multiple supported attachments is rejected as ambiguous, including mixed GPX/Vakaros attachments; an unsupported or malformed message does not silently create an Activity. The supported attachment formats are `.csv`, `.csv.gz`, `.vkx`, `.vkx.gz` and plain `.gpx`, selected by case-insensitive filename extension. Compressed GPX (`.gpx.gz`, `.gpx.gzip`, `.gpx.zip`) and ZIP archives remain unsupported.
- Historical Gmail ingestion records remain readable and can be explicitly reprocessed from their preserved originals. Gmail acquisition and OAuth are no longer part of the current runtime mailbox path.
- A versioned `mail_receipts.json` store is available for later acquisition and feedback increments. It keeps receipt state, referenced Ingestion IDs and mail feedback state/attempts separate from each Ingestion's processing result and from Sailor consent/welcome delivery. Historical mail receipts are marked complete with feedback suppressed, so the new model alone creates no retrospective processing or mail. Legacy Session-result SMTP evidence remains on its original Ingestion record. Admin uploads have no mail receipt.

### Manual Admin acquisition and lifecycle

- Protected Admin accepts one track file with an explicit existing `ACTIVE` Sailor. It uses the Sailor's existing default Boat without a Boat override or Sailor creation. Supported suffixes are `.gpx`, `.csv`, `.csv.gz`, `.vkx` and `.vkx.gz`, case-insensitively. The received file limit is **16 MiB**, including compressed bytes for supported gzip formats; bounded HTTP intake rejects oversized input before creating an Ingestion or retaining it. Compressed GPX and ZIP remain unsupported.
- Each accepted upload preserves the exact original and registers a distinct Ingestion before acknowledgment. Its source is `admin_upload`, with a unique operation identity, explicit owner Sailor ID and acceptance time; it has no email sender, provider-message ID or email receipt. Historical mail records retain their original identity and interpretation.
- `POST /api/admin/ingestions/upload` accepts the raw file body with `sailor_id` and `filename` query metadata under existing Admin authentication. HTTP `202` acknowledges durable acceptance, not successful processing; its returned Ingestion status is authoritative. Unsupported or corrupt accepted-size input that is safely accepted becomes a controlled failed Ingestion retaining its original. The UI checks supported suffixes before submission; the backend remains responsible for validation.
- Manual work has durable `pending`, `processing`, `processed` and `failed` states. Acceptance immediately submits work to a backend-lifespan-owned executor, independently of the HTTP request and browser. Activation failure leaves an inspectable failed Ingestion. The existing parser, normalizer, Sailor-scoped exact-byte Activity reuse and Session matching pipeline are shared with email processing. Re-upload creates another Ingestion even when it reuses an Activity.
- A per-operation OS lease covers both queueing and execution. Startup, Admin inspection and worker completion reconcile abandoned pending/processing operations as failed/interrupted while preserving their originals. Live queued/running work is not treated as interrupted. Inspection can defer reconciliation while another ingestion writer holds the shared lock. There is **no automatic retry or recovery execution**; explicit Admin Reprocess uses the original file, source and Sailor ownership.
- Persistence-mutating ingestion is serialized across cooperating backend and mailbox processes using one reentrant OS lock per persistence root, covering deduplication and Activity/Session writes through ingestion consent/notification effects. This includes manual upload, worker processing, Admin Reprocess and OVH processing; it does not change OVH acquisition or cursor semantics or provide crash rollback across JSON collections. Manual communication and consent rules belong in [Access and Consent](access-and-consent.md).

### Normalized Activity data

- Supported Vakaros CSV, VKX and plain GPX attachments are parsed, then normalized into a common provider-independent track model. A valid track supplies UTC time, latitude and longitude; unavailable optional telemetry remains absent rather than being invented.
- The current normalized track schema contains `activity_id`, `utc`, `lat`, `lon`, `cog`, `sog`, `dist`, `hdg`, `heel`, `trim`, `quat_w`, `quat_x`, `quat_y` and `quat_z`. The four quaternion fields preserve available VKX orientation data. Historical normalized tracks without those fields remain readable, with absent quaternion values treated as null.
- VKX-derived HDG, HEEL and TRIM require unambiguous evidence that the device was fixed to the body frame. When that condition is not met, those derived values remain absent. HDG is not inferred from COG. FIT and logical cross-format track identity remain unsupported.

### Plain GPX validation and movement

- One GPX file represents one Activity, subject to the existing exact-file reuse rule. Accept exactly one `trk` with exactly one nonempty `trkseg`; reject additional tracks or segments even when empty. Only direct `trkpt` samples in that segment contribute data. Waypoints and routepoints are ignored. GPX 1.0/1.1 namespaces and unqualified GPX are accepted; misplaced track structure is rejected. Do not join segments, sort samples, split Activities or drop malformed or repeated points.
- Require at least two trackpoints, each with finite WGS84 latitude/longitude and an explicit timezone-aware timestamp. Normalize timestamps to UTC and require them to increase strictly in source order. Reject missing or invalid coordinates/times, equal/decreasing timestamps, and adjacent timestamp gaps **greater than 10 seconds**; exactly 10 seconds is accepted. Preserve every accepted sample, including identical consecutive coordinates.
- Derive SOG in knots and circular COG in `[0°, 360°)` from deterministic great-circle displacement and actual elapsed UTC time. For each sample choose the real sample nearest two seconds before and two seconds after, on each available side; equal-distance ties choose the earlier UTC. Coarse cadence uses the nearest available neighbor on that side. At track boundaries use one-sided evidence. This approximates a centered ±2-second neighborhood without assuming 1 Hz or interpolating input. Coincident or numerically indeterminate bearing evidence leaves COG unavailable; stationary evidence may yield SOG zero. No GPS jitter/noise threshold is applied. Canonical `dist` remains the existing consecutive-position calculation in `normalize_track()`.
- GPX extension telemetry mapping is deferred. HDG, HEEL, TRIM and quaternion measurements remain absent; none is derived from GPS or extension metadata. GPX-derived canonical COG/SOG may support LOW maneuver analytics under the accepted HIGH-first/LOW selection rules; insufficient evidence remains unavailable without failing ingestion. [Analytics](analytics.md) owns detector selection and availability. Existing Viewer sample-gap/coverage policies remain unchanged.
- Reject malformed or unsafe XML with a controlled failure. The plain XML parser rejects DTDs/entity declarations and applies implementation resource ceilings of 16 MiB of source bytes, 500,000 elements, nesting depth 32 and 100,000 trackpoints. These bounds exceed the representative pilot fixtures and do not add compressed GPX support. Source bytes remain preserved through the common ingestion path, including on a parsing failure.

### Processing, deduplication and persistence

- The common pipeline records the ingestion attempt, preserves the received original, parses and normalizes the track, resolves or creates the Sailor, creates or reuses an Activity, persists its normalized track and associates it with a Session through the existing matching service. An Activity requires a Sailor; consent state does not prevent technical ingestion or matching. [Domain and Sessions](domain-and-sessions.md) owns Activity and Session meaning and matching rules.
- Re-reviewing an already processed `provider + provider_message_id` does not process that message into another Activity. A different provider message may contain the same attachment: within one Sailor, the SHA-256 of the **received attachment bytes** identifies an existing Activity for reuse. This is an exact-file boundary. Different bytes, including differently encoded or compressed copies of the same samples, are not declared the same Activity by logical track comparison.
- Activity reuse does not imply that the later ingestion failed or was discarded. Ingestion history distinguishes an Activity newly created by that ingestion, one reused from earlier processing, and legacy/unknown provenance. Session membership and matching are separate from both message and file deduplication.
- TackBar retains JSON ingestion/domain metadata, the received original file and the normalized Activity track under private backend-managed storage. The normalized track is persisted as compressed CSV; historical normalized tracks remain readable. The frontend accesses data through backend APIs, not the storage files. Session expiry does not itself delete Activities or originals; see [Domain and Sessions](domain-and-sessions.md).
- The versioned history migration is an explicit maintenance operation with read-only `check`, `migrate` and read-only `verify`. `check` does not normalize legacy history, assign persistent IDs or create lock/artifact files. Migration is idempotent, preserves existing IDs and source references, rejects conflicting attachment identities, and leaves Activity/Session associations and legacy notification/onboarding evidence intact. It does not run at application startup or touch the mailbox cursor. Production execution requires separate release/operations authorization.

### Processing state, mailbox cursor and failure boundaries

- An email ingestion has a technical `processed` or `failed` status; manual ingestion additionally exposes `pending` and `processing`. Both retain an attempt count, a last-attempt timestamp and a controlled last error. Their separate administrative disposition is `active` or `discarded`. Discard and restore change administrative disposition without undoing processing, deduplication, Activity/Session links or preserved originals. Restore does not automatically reprocess. Physical deletion requires a separately defined policy and workflow; it is not an ingestion-maintenance action.
- Known failed provider messages are not automatically retried by ordinary mailbox review. Admin may explicitly reprocess an ingestion when its original attachment is available; an absent original is recorded as a controlled failure. Reprocessing remains subject to exact-file Activity idempotency. A failed attempt may have left partial domain side effects, so the status alone must not be read as proof that no Activity or Session exists.
- OVH acquisition uses a persisted `UIDVALIDITY`/UID cursor to resume review. Unsupported, malformed and downstream-failed messages can count as examined and advance that cursor. A provider fetch failure preserves only the safely examined prefix; a changed `UIDVALIDITY` fails review rather than silently reusing the prior UID cursor. Mailbox `Seen`/`Unread` flags are not TackBar processing, retry or disposition state.
- Provider connection or authentication failures surface as mailbox-review failures without changing ingestion records for unfetched messages. Failure reporting must not disclose credentials or private track content. A failure while processing one candidate does not prevent review of later candidates when acquisition can continue.
- Geographic or historical context enrichment for a new Session and eager analytical artifact generation are best-effort follow-up work: their failure does not turn an otherwise completed track ingestion into a failed one. Their product semantics belong in [Session Context](session-context.md) and [Analytics](analytics.md).

### Onboarding and delivery state at the ingestion boundary

- A first supported email track can create or resolve a Sailor and proceed through Activity creation and Session matching while that Sailor is `PENDING`. A successful qualifying email track can initiate the consent-request workflow. Manual uploads and their Reprocess do not initiate automatic communications. Consent authorization, message eligibility and shared visibility belong in [Access and Consent](access-and-consent.md).
- For Session-result email, ingestion history records whether a newly created Activity is a delivery candidate and persists an attempt before outbound sending. A controlled send failure is recorded as a failed attempt; ordinary reprocessing or Activity reuse does not create a duplicate delivery attempt. Recipient eligibility and consent rules belong in [Access and Consent](access-and-consent.md).

### Ownership boundaries

- [Domain and Sessions](domain-and-sessions.md) owns Sailor, Boat, Activity and Session definitions, matching and lifetime. This document owns acquisition, normalization, exact-file deduplication, ingestion state and data persistence.
- [Access and Consent](access-and-consent.md) owns consent, capabilities and ACTIVE-only authorization. [Admin](admin.md) owns Admin interactions. The [production runbook](../production-runbook.md) owns credentials, service commands, deployment and operational recovery instructions.
