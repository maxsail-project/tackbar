# TackBar v0.7.x Californian — Collaborative Debrief Analytics Requirements

**Status:** v0.7.1 implementation delivered; automated release validation passed; production validation pending\
**Scope:** Vakaros-based collaborative debrief analytics\
**Baseline:** Delivered v0.6.x Activity / Session / Viewer behavior\
**Decision source:** [v0.7 decisions](v0.7-decisions.md)

This document replaces the former v0.7 multi-format ingestion requirements.
It governs the Californian release family, without freezing all capabilities
or metrics into a single v0.7.0 delivery.

---

## 1. Confirmed product objective

### V7-OBJ-01 — Useful moments for collaborative debrief

TackBar v0.7.x MUST extract useful post-sailing insights from the richer
telemetry already available in Vakaros-derived canonical TackBar Activities.
Analytics MUST extend the existing collaborative debrief flow, not create a
separate analytics product or require new source ingestion.

The conceptual flow is:

Vakaros telemetry → canonical TackBar Activity → analytical event detection /
summaries → existing Session Viewer → sailors jump to useful moments →
collaborative debrief.

Collaboration retains its existing meaning: sailors inspect and discuss the
same Viewer together around a phone or tablet. Multi-user synchronization,
chat and automated advice are not implied.

## 2. Delivered v0.7.0 analytical capability

### V7-EVT-01 — Maneuver-oriented analysis

The first analytical capability identifies useful maneuver events or
significant sailing-direction changes in existing normalized Activity data.
These events are analytical annotations of a track, not new Activities,
races, legs or Saved Segments.

The delivered detector consumes complete canonical HDG samples, splits input at
gaps longer than 1.5 seconds, handles headings circularly and smooths locally.
It seeds candidates at an absolute turn rate of at least 4 degrees per second,
extends directional motion at 0.5 degrees per second, and accepts a 3-to-30
second event only when the heading change, direction coherence, sample quality
and available COG/HEEL/SOG context support it. At least 20 valid HDG samples are
required in a continuous segment. Missing or insufficient HDG produces an
unavailable analytical result rather than invented events.

Each accepted event has deterministic start, center and end GPS/UTC timestamps.
The center is the cumulative-rotation midpoint and is the navigation timestamp.
The detector remains an evidence-driven v0.7 implementation rather than a
permanent maneuver-classification schema.

### V7-EVT-02 — Neutral event semantics

A detected maneuver MUST NOT automatically be labelled a tack or gybe.
Use neutral terminology such as “maneuver”, “detected maneuver event” or
“significant sailing-direction change” until reliable classification is
validated with real sailing data and explicitly promoted into scope.

TackBar MUST NOT reconstruct or invent wind information merely to classify
maneuvers. A course change alone does not establish tack/gybe meaning.

## 3. Provisional, evidence-driven metrics

### V7-MET-01 — Flexible metric set

The analytical metric set MUST remain **evidence-driven, provisional and
expected to evolve during v0.7.x**. Metrics MAY be added, removed or adjusted
following validation with real sailing data without redefining the whole
release family each time.

The delivered v0.7.0 event contract contains:

- maneuver timestamp and duration;
- circular HDG change;
- entry, minimum and exit SOG;
- recovery time;
- Loss distance and equivalent Loss time.

Unavailable metric inputs produce `null` in the API and an em dash in the
Viewer. HEEL and TRIM remain detector-supporting context where available; they
are not published as maneuver metrics in v0.7.0. Later metrics remain subject
to V7-MET-02 and do not become required by appearing in historical examples.

### V7-MET-02 — Bounded refinement and validation

Each promoted metric or small additional analytical capability MUST:

- answer a concrete post-sailing debrief question within V7-OBJ-01;
- have representative sailing evidence and a documented reason to include,
  adjust or remove it;
- define its inputs, units, time interval, calculation and unavailable-data
  behavior clearly enough for repeatable validation;
- receive focused scope review and proportional regression checks;
- preserve the baseline constraints below.

Flexibility applies to analytical selection, not to undocumented or arbitrary
calculation behavior. Each delivered rule MUST be deterministic and tested,
including circular angles and missing data where relevant. Calculation changes
MUST be documented in the affected increment; a validated decision may update
these requirements without freezing the entire metric set.

This policy is not blanket permission for unrelated features, advanced
analytics, speculative architecture or any explicit non-goal. Such promotion
requires a separate explicit scope decision.

### V7-MET-03 — Delivered maneuver Loss definition

Maneuver Loss is the equivalent distance deficit caused by canonical SOG
falling below the pre-maneuver entry speed. Entry SOG is the median of valid,
finite, non-negative canonical SOG samples from 25 seconds through 8 seconds
before the maneuver start, inclusive.

From the maneuver start through the existing recovery sample, Loss distance
MUST integrate `max(entry SOG - actual SOG, 0)` over the actual canonical
sample timestamps, using piecewise-linear integration across each valid
sample interval and converting knot-seconds to metres with `1 kt = 0.514444
m/s`. Irregular sampling intervals MUST retain their actual duration. SOG
above entry speed contributes zero rather than a negative Loss or gain.

Loss time MUST equal Loss distance divided by entry SOG converted to metres
per second. It is available only when the existing calculation has a valid
positive entry SOG, comparable exit regime, recovery sample and at least two
valid SOG samples in the Loss interval; otherwise existing unavailable-data
behavior remains unchanged.

The recovery definition and interval remain unchanged: exit SOG is the median
from 25 through 45 seconds after the maneuver end; entry and exit are
comparable when their absolute difference is at most the greater of `0.75 kt`
and `15%` of entry SOG; recovery is the first valid sample from the maneuver
end through 60 seconds afterward whose SOG is at least `95%` of exit SOG.

Loss is not tactical gained/lost, VMG, mark-relative performance,
opponent-relative performance or a maneuver score. It uses no reconstructed
wind, course geometry, mark or opponent reference.

### V7-MET-04 — Persistence, invalidation and API ownership

The backend owns detection and metric calculation. Results are persisted as
per-Activity `.maneuvers.json` analytical artifacts next to other private
runtime analytics, with the Activity identifier, canonical-track SHA-256 and
algorithm version. The delivered v0.7.0 algorithm version is `6`.

Artifacts are generated lazily on the first authorized read and regenerated
when absent, malformed, from another algorithm version or tied to a different
canonical-track hash. Strict validation prevents stale or partial artifacts
from being served.

The capability-scoped endpoint is
`GET /api/shared/sessions/{token}/activities/{activity_id}/maneuvers`. It MUST
retain the existing Session capability and ACTIVE-only visibility enforcement,
and MUST reject an Activity outside that visible Session. The frontend consumes
this API; it does not calculate maneuvers or read analytical files directly.

## 4. Domain and telemetry safety

### V7-BASE-01 — Preserve the delivered baseline

Unless a future requirement explicitly changes them, v0.7.x MUST preserve:

- Sailor → Activity → Session, stable Sailor identity and optional Boat context;
- Activity as one received track, with no automatic merging or splitting;
- existing Session matching, consent, ACTIVE-only shared visibility, Personal
  TackBar and Session capability / expiration / renewal semantics;
- current Vakaros CSV/CSV.GZ ingestion, Gmail/OVH acquisition boundaries,
  original preservation and raw attachment SHA-256 exact-file deduplication;
- JSON metadata plus filesystem tracks; no database migration;
- backend storage isolation and canonical-track consumption by the frontend;
- private runtime sailing data outside the public repository.

### V7-DATA-01 — No invented telemetry

Missing sensor values MUST remain unavailable. Analytics MUST NOT invent
positions, samples, HEEL, TRIM, heading or wind. Derived analytical values
MUST use actual available normalized telemetry and documented rules; derivation
is not permission to fabricate missing source measurements.

HDG and COG MUST remain distinct. HDG MUST NOT be derived from COG. Angular
changes, comparisons and aggregation MUST use circular handling across
0°/360°. HEEL/TRIM sign MUST NOT gain unvalidated port/starboard or
bow-up/bow-down meaning.

Analytical results MUST use the complete relevant valid normalized sample
population, not a visual downsampling of the map or chart.

## 5. Existing Session Viewer extension

### V7-VIEW-01 — Delivered analytical section

The Session Viewer includes a collapsible Maneuvers section and a compact table
with one chronological row per detected event. The delivered column order is:

`Time | Act | Loss (m) | Loss (s) | Rec (s) | SOG in (kt) | SOG min (kt) | SOG out (kt) | ΔHDG (°) | Dur (s)`

Time sorting can be reversed without changing event semantics. Numeric columns
use compact, tabular alignment; the header remains sticky within the scrolling
table container; narrow screens retain horizontal scrolling without hiding or
wrapping away metrics. Primary/Comparison identity and unavailable values use
the existing Viewer presentation.

Events MUST remain attributable to the selected Activity. Analytics MUST
respect the same selected one or two Activities and shared GPS/UTC Analysis
Window. Empty results or insufficient telemetry MUST be presented clearly
without breaking the existing Viewer.

### V7-VIEW-02 — Event selection and shared time

Selecting a table row or timeline marker moves the existing shared
`playbackTime` to the event center GPS/UTC timestamp within the current Analysis
Window, highlights the corresponding table row, and issues a role-aware map
focus request. The map focus is offset toward the visible area above the fixed
telemetry overlay. It MUST NOT introduce an
independent analytical clock, silently change the Analysis Window, or
reinterpret an event as a new Activity/Session.

The existing map/replay model, current charts and current Summary behavior
MUST remain intact. The extension MUST retain the mobile/tablet debrief flow
rather than introduce a separate dashboard or Viewer redesign.

Only events whose center lies inside the selected Analysis Window are shown.
Selection near an edge keeps the Analysis Window unchanged. The SOG timeline
shows separate Primary/Comparison markers and preserves drag selection, zoom
and the integrated shared replay controls. Selection is cleared when its
Activity or Analysis Window no longer makes the event valid.

### V7-VIEW-03 — Selected maneuver metrics in compact context

The v0.7.1 Viewer shows Loss distance, equivalent Loss time and Recovery time
for the explicitly selected maneuver directly beneath the compact Analysis
Window summary of the Activity that owns the event. Primary and Comparison
attribution uses the existing functional visual treatment.

The detail uses the existing maneuver formatting and unavailable-value
semantics. It appears only for explicit maneuver selection, remains unchanged
when replay moves independently, and disappears when selection is cleared or
the selected event is no longer inside the displayed Analysis Window.

The interval-level compact summaries remain separate and retain Avg SOG,
distance and whole-degree Dominant COG. v0.7.1 removes only the visible `COG`
label from that compact presentation; it does not change the calculation,
rounding or Summary-table presentation. Selected maneuver metrics do not appear
in the instantaneous map telemetry overlay.

## 6. Explicit scope boundaries

The following are not committed to the initial analytical scope:

- start analysis;
- automatic leg detection;
- gained/lost analysis;
- tactical recommendations or automated coaching;
- AI-generated sailing advice;
- maneuver scoring or ranking;
- advanced tack/gybe classification unless reliably validated and separately
  promoted later;
- wind reconstruction or race reconstruction;
- Saved Segments unless separately promoted;
- Garmin Connect integration;
- GPX, VKX or FIT ingestion;
- canonical cross-format logical fingerprint / deduplication and related
  cross-format normalization;
- new ingestion providers;
- database migration.

Future analytical ideas in the backlog do not become v0.7.x commitments by
proximity to maneuver analysis. Small evidence-backed refinements are allowed
only within section 3 and the confirmed collaborative debrief objective.

## 7. Deferred multi-format direction

GPX, VKX and FIT ingestion, cross-format normalization and canonical logical
fingerprint / deduplication are **Status: Future / Release: Unassigned**.
No commitment to v0.7.0, v0.7.x, v0.8.x or another release is created.

TackBar may become source-format independent later, converging supported
sources on canonical Activities and the existing Session/Viewer flow.
The former GPX → VKX → FIT order is not a current delivery commitment.
Garmin Connect remains separate Future / Unassigned work.

The [product backlog](product-backlog.md) preserves this future work. Detailed
parser, normalization and logical-identity contracts must be reviewed when
that scope is explicitly promoted; they do not govern this analytics release.

## 8. Evidence-driven maintenance

### V7-MAINT-01 — Small focused maintenance

Small corrective, technical-debt or operational-maintenance increments MAY
remain within v0.7.x when justified by pilot/production evidence or concrete
implementation findings. Examples include demonstrated defect fixes,
obsolete-script removal, localized maintainability improvements, operational
cleanup, affected documentation cleanup and focused regression hardening.

Each increment MUST state the evidence, narrow scope and proportional checks.
Maintenance MUST remain backward compatible unless an explicit approved
requirement changes that behavior. It MUST NOT become speculative feature
expansion, unrelated refactoring or a silent change to domain, ingestion,
consent, persistence or Viewer semantics.

## 9. v0.7.x acceptance and release decisions

An analytical increment is acceptable when it:

1. demonstrates a useful maneuver-oriented debrief outcome on representative
   real sailing data, using safe public fixtures for committed tests;
2. documents the chosen detection rules, metrics and data limitations without
   presenting unvalidated candidates as mandatory;
3. preserves neutral maneuver semantics unless reliable classification has
   been explicitly validated and promoted;
4. supports event-to-shared-replay navigation while preserving the Analysis
   Window, map, charts, Summary and Activity/Session semantics;
5. passes proportional calculation and Viewer regression checks;
6. does not silently promote any deferred format or excluded analytical scope.

For v0.7.0, the detector inputs/rules and thresholds, event boundaries,
published metric subset, missing/noisy-data and time-gap behavior, Analysis
Window edge policy, center-time navigation, backend calculation ownership,
artifact invalidation and capability-scoped API are closed as described above
and in the consolidated decisions.

For v0.7.1, the compact selected-event placement, Primary/Comparison
attribution, three-metric subset, explicit-selection lifetime and removal of
only the visible compact `COG` label are closed as described in V7-VIEW-03.
This is a presentation refinement over existing selected-event data; it does
not change maneuver calculation, API, persistence, replay or Analysis Window
semantics.

Real sailing validation may still justify a later bounded v0.7.x refinement.
Individual normalized maneuver profiles and aggregate Primary/Comparison
profiles remain Future / Unassigned work tracked separately in the backlog;
they are not part of v0.7.0. Broader non-goals still require explicit promotion.
